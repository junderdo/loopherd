# Claude Code Bash deny rules: how strong are they?

Researched 2026-11-02. Local install: `claude --version` = 2.1.316 (matches top of CHANGELOG.md, `## 2.1.316`).
Docs below were fetched live from code.claude.com (as `.md` pages) on that date, so they describe ~2.1.316 unless a version is quoted.
All sources are primary (official docs, anthropics/claude-code CHANGELOG.md). No secondary sources used.

Doc URLs (base `https://code.claude.com/docs/en/`):
- P = `permissions` ; M = `permission-modes` ; S = `settings` ; H = `hooks` ; SA = `sub-agents`

## Bottom line

- Deny rules are enforced by Claude Code (not the model), apply in every mode including `auto` and `bypassPermissions`, and beat allow rules and the auto-mode classifier.
- But a Bash deny rule matches the command TEXT the model wrote. The docs say outright it "isn't a security boundary around the program". `bash -c '...'`, `sh -c`, absolute paths, and reordered options (`git -C . push`) are documented as NOT stopped.
- For `gh pr merge` the docs' listed gaps are most relevant: `bash -c "gh pr merge 1"`, `/usr/bin/gh pr merge 1`, and `gh api` (a different subcommand entirely) are not covered by `Bash(gh pr merge *)`.
- A PreToolUse hook that exits 2 is stronger (it sees the full command text and can normalise/regex it), but is still text inspection; the docs recommend sandboxing for enforcement independent of command text.

## 1. Do deny rules apply in `auto` and `bypassPermissions`? Precedence

Yes to both.

- M, "Permission modes" intro: "Deny rules block in every mode, including `bypassPermissions`. Deny and ask rules don't apply to `EndConversation` as long as Claude still has at least one other tool it can call. Allow rules have no effect in `bypassPermissions`."
- P, "Manage permissions": "Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order." and "An allow rule can't carve an exception out of a deny rule."
- P, same section: "Permission rules are enforced by Claude Code, not by the model."
- M, "How the classifier evaluates actions" (auto mode decision order, "first matching step wins"): "1. Actions matching your allow, ask, or deny rules resolve immediately, with these exceptions: ..." (exceptions are protected-path writes, rm critical paths, requiresUserInteraction MCP tools, etc.; none weaken deny). Step 3: "Everything else goes to the classifier". So deny rules are checked BEFORE the classifier and never reach it.
- M, auto-mode "Allowed by default" list: "`permissions.deny` rules can still block push commands as written in every mode." (explicitly about `git push` under auto mode; relevant to `git push --force`).
- M, auto-mode boundaries: "Boundaries are not stored as rules... For a hard guarantee, add a deny rule instead." (i.e. docs themselves recommend deny rules over prompt instructions.)
- Auto mode drops broad ALLOW rules on entry (`Bash(*)`, `Bash(python*)`, `Agent` allow...). Deny rules are not in that list.
- Auto-mode caveat: an ASK rule matching command content (e.g. `Bash(git push *)`) "fall[s] back to a permission prompt" in auto mode; in a non-interactive `-p`/dontAsk run ask rules are denied (M, dontAsk section: "Claude Code denies calls matching your explicit ask rules rather than prompting" - dontAsk mode only; for auto in a headless run this is unconfirmed). For an unattended agent, use `deny`, not `ask`.
- Mode selection note (M, "Which mode a session starts in"): `"auto"`/`"bypassPermissions"` as `defaultMode` in `.claude/settings.local.json` does not take effect. Deny rules in that file are unaffected; only the mode setting is. Use `--permission-mode auto` on the CLI.

## 2. Is `.claude/settings.local.json` loaded; cd; precedence

Loaded: yes, from the session's primary working directory (with a git-root wrinkle).

- S, "Where settings live" table: Project local = `.claude/settings.local.json`, "You, in this one project only."
- S (location section): "Claude Code reads the shared `.claude/settings.json` from the session's primary working directory, so to use a file committed at the repository root, start Claude Code there."
- P, "Working directories": "That directory is the session's primary working directory until you move the session with `/cd`." The primary dir changes only via `/cd` (user-run; `Cd` is "not a model-invocable tool: Claude can't call it").
- Agent `cd` in Bash does NOT move the project settings. Tools reference (`tools-reference`, Bash behavior): "When Claude runs `cd` in the main session, the new working directory carries over to later Bash commands as long as it stays inside the project directory or an additional working directory". That changes the shell cwd only; settings come from the primary working directory. After `/cd` (user action, v2.1.246+): "Claude Code reads both project files from the new directory instead" (S) and "applies the new directory's project configuration... including their permission rules and hooks" (P). I found no text saying an agent `cd` in Bash reloads or drops rules; the documented model implies it does not (inference, labelled as such).
- Git-root wrinkle (S, "Where settings live"): since v2.1.211 the local file lives at the git repo root, not the start dir: "If you start Claude Code in a subdirectory of a git repository, it reads and writes that file at the repository root... In a worktree, it uses the file at the main checkout's root." and "Before v2.1.211, Claude Code kept the file in the starting directory. It still reads a file an earlier version left there alongside the root file; ... permission rules from both files apply."
  - UNCONFIRMED: whether a hand-written `<cwd>/.claude/settings.local.json` in a subdirectory or a linked worktree is read when a root/main-checkout file also exists. The docs only state that a legacy file left in the start dir is still read. If loopherd runs agents in worktrees or subdirs, test with `claude -p` + `/status` / `claude doctor` (debug-your-config), or write the rules to the git root / main checkout file too. Fallback location noted by docs: outside a git repo, or when the repo root is the home dir, the file stays with `.claude/settings.json` (start dir).
- Trust (P, "When your local settings file needs trust"): `.claude/settings.local.json` allow rules apply without the trust dialog if the file is untracked; if it is tracked in git or `.claude` is a symlink it is "held until you trust the folder". Deny/ask rules are never gated: "`deny` and `ask` rules aren't affected, since they only restrict." So deny rules apply even in an untrusted dir.
- Precedence (S, "Settings precedence"): "Settings precedence, highest first: managed settings, command line, project local, shared project, user." `--settings` is "Command line", above project local and user.
- BUT lists merge, and deny wins across scopes (S, "Lists merge instead of overriding": "Claude Code combines the lists instead of picking one"). P, "Settings precedence": "If a tool is denied at any level, no other level can allow it." and "if user settings allow a permission and project settings deny it, the deny rule blocks it. The reverse is also true: a user-level deny blocks a project-level allow, because deny rules from any scope are evaluated before allow rules." So a deny in settings.local.json cannot be undone by `~/.claude/settings.json` or `--settings` allow rules; only by managed settings (n/a) or by the agent editing the file.
- Self-modification risk: the agent can edit `.claude/settings.local.json` unless protected. M "Protected paths": writes to `.claude` are "never auto-approved except in `bypassPermissions` mode"; in `auto` they route to the classifier. See M section "Protected paths" for the per-mode table (not quoted in full here). Settings file watcher picks up edits to hooks live (H: "Direct edits to hooks in settings files are normally picked up automatically by the file watcher."). So under `bypassPermissions` an agent could delete its own deny rules; under `auto` it is classifier-gated. Managed settings are the only tamper-proof place (P, "Managed settings").
- `--disallowedTools` CLI flag is another place for deny rules (P: "`--disallowedTools` can add restrictions beyond what managed settings define"; CLI ref lists it). It is highest of the non-managed sources and cannot be edited away by the agent: consider using it instead of or in addition to the file if loopherd launches the process.

## 3. Bash rule matching

Source: P, section "Tool-specific permission rules > Bash" (anchors: Wildcard patterns, Compound commands, Wrappers, "What a Bash rule doesn't match").

Syntax: "`Bash(ls:*)` matches the same commands as `Bash(ls *)`" ("The `:*` suffix is an equivalent way to write a trailing wildcard"; only recognised at end of pattern). "`Bash(ls *)` matches `ls`" (bare command too). So `Bash(gh pr merge:*)` == `Bash(gh pr merge *)`: matches `gh pr merge 1`, `gh pr merge`, not `gh pr mergex`.

| Command | Covered by `Bash(gh pr merge *)` deny? | Basis |
|---|---|---|
| `gh pr merge 1` | Yes | basic |
| `GH_TOKEN=x gh pr merge 1` | Yes | P Wrappers: "A deny or ask rule matches past any leading assignment, so `Bash(rm *)` in deny still matches `FOO=bar rm -rf tmp/`." (Allow rules only strip known-safe vars; deny strips any.) Related fixes: 2.1.290 "Fixed a deny or ask rule missing a command or path whose name came from a variable set as a prefix on `declare`, `typeset`, `export` or `readonly`"; 2.1.289 "Fixed Bash deny and ask rules missing a command behind an environment variable prefix with an expanded value (e.g. `TZ="$HOME" rm -rf build`) when the sandbox auto-allows commands". |
| `cd foo && gh pr merge 1` | Yes | P Compound commands: "Deny and ask rules apply when any subcommand matches them, including a command nested inside a subshell, a command substitution, or a control-flow body such as a `for` loop." Separators: "`&&`, `||`, `;`, `|`, `|&`, `&`, and newlines." Example given for ask rule: "still prompts you for `cd /tmp && git clean -f` or `echo "$(git clean -f)"`, even in auto mode." |
| `timeout 30 gh pr merge 1` (also `time`, `nice`, `nohup`, `stdbuf`, `command`, `builtin`, `noglob`, bare `xargs`) | Yes | P Wrappers: "Claude Code strips a fixed set of wrappers... The stripped wrappers are `timeout`, `time`, `nice`, `nohup`, and `stdbuf`, plus the shell builtins `command` and `builtin`, and zsh's `noglob`." "This wrapper list is built in and is not configurable." |
| `env gh ...`, `sudo gh ...`, `watch`, `ionice`, `setsid` | Probably yes for deny | Not in the P docs' stripped list, but CHANGELOG 2.1.113: "Security: Bash deny rules now match commands wrapped in `env`/`sudo`/`watch`/`ionice`/`setsid` and similar exec wrappers". UNCONFIRMED against current behaviour (docs list is narrower). Test it. |
| `devbox run`/`npx`/`docker exec`/`mise exec`/`direnv exec` wrapping | No (assume) | P: "Development environment runners such as `direnv exec`, `devbox run`, `mise exec`, `npx`, and `docker exec` are not in the list." |
| `bash -c "gh pr merge 1"` | NO | P "What a Bash rule doesn't match" table: `Bash(rm *)` "Doesn't stop `/bin/rm -rf build/`, `bash -c 'rm -rf build/'`"; `Bash(curl *)` doesn't stop `sh -c 'curl https://example.com'`. (Note the docs table's `* --version` row shows `bash -c 'echo hi' --version` as a match for a wildcard-program rule, i.e. text matching only; there is no unwrapping of the `-c` string for rules.) |
| `sh scripts/install` / `bash scripts/install` | n/a - rule `Bash(scripts/install *)` matches text starting `scripts/install` only. | Same principle: P "A Bash rule matches the command text Claude writes, after Claude Code splits compound commands and strips wrappers. It doesn't match the same program invoked in a different form". `sh scripts/install` starts with `sh`, so does not match `Bash(scripts/install *)`. To cover both spellings you need separate rules: `Bash(scripts/install *)`, `Bash(./scripts/install *)`, `Bash(sh scripts/install *)`, `Bash(bash scripts/install *)`, and absolute-path variants. The docs give no path normalisation for Bash command strings (unlike Read/Edit path rules). |
| `./scripts/install` vs `scripts/install` | Not equivalent | No docs claim they are normalised; docs' own examples (`/usr/bin/curl` vs `curl`) show path-qualified forms are separate. |
| absolute path `/usr/bin/gh pr merge 1` | NO | P table: `Bash(curl *)` "Doesn't stop `/usr/bin/curl https://example.com`"; `Bash(git push *)` doesn't stop `git -C . push origin main`, `git -c push.default=current push origin main`, `git 'push' origin main`. Analogous for gh: `gh -R owner/repo pr merge 1` (global flag before subcommand) is NOT matched by `gh pr merge *` (inference from the git `-C` example; docs do not mention gh). |
| `gh api -X PUT repos/o/r/pulls/1/merge` | NO | Different command text. Docs do not mention `gh api`. |
| `git push --force` via `git push -f`, `git push origin +main`, `git push --force-with-lease` | `Bash(git push --force *)` would not match `-f`; use `Bash(git push *)` to deny all pushes if acceptable | P Wildcard: "Claude Code matches everything before the first `*` as written". Note `Bash(git push *)` would also block normal pushes. |
| `git rebase` | `Bash(git rebase *)` stops `git rebase`; `git -C . rebase`, `git -c k=v rebase` not stopped | same table, by analogy |

Other relevant documented points:
- Wildcard rule: "Put the `*` after the subcommand." Everything before the first `*` is matched as written; space before `*` matters (`Bash(ls *)` vs `lsof`).
- Fragility warning (P, Read-only commands section): "Bash permission patterns that try to constrain command arguments are fragile." Docs recommend: deny + sandbox network allowlist, PreToolUse hooks, CLAUDE.md (which "doesn't enforce a boundary").
- Unparseable commands: "when Claude Code can't fully parse a command, it asks for approval instead of treating the command as read-only." (read-only classification; not a statement about deny matching.) CHANGELOG: "Reverted a 2.1.268 change that checked Read and Edit deny rules on Bash lines the permission checker can't analyze (`eval`, `env -C`)" (CHANGELOG 2.1.273) - i.e. `eval`/`env -C` lines are NOT deny-checked for file rules.
- Reading the quote that matters most for loopherd: "A Bash rule matches the command text Claude writes ... so a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." (P, "What a Bash rule doesn't match".)

## 4. Subagents; `gh api`; "not a security boundary" guidance

- Subagents are covered. SA ("Restrict which tools a subagent can use"): "To keep Bash and block specific commands, add a Bash deny rule such as `Bash(git push *)` to `permissions.deny` in your settings. The rule applies to the main conversation and to subagents." Also SA built-ins: "Each inherits the parent conversation's permission rules".
- Auto mode + subagents (M, "How auto mode handles subagents"): "each of its actions goes through the same decision order as in the parent session, with the same block and allow rules. Any `permissionMode` in the subagent's frontmatter is ignored." SA, Permission modes: when the main session is in `bypassPermissions`/`acceptEdits`/auto, subagent runs in that same mode.
- Teammate caveat: CHANGELOG (search "Fixed split-pane agent teammates not inheriting the tool deny and `--tools` rules given on the leader's command line") - a past bug for agent-team teammates. Listed under CHANGELOG 2.1.309. Only relevant if loopherd uses agent teams.
- Separate processes: a deny rule only covers the Claude Code process that loaded it. Anything the agent launches as a child (e.g. `claude -p ...` via Bash, `bash -c`, scripts like `scripts/install` that themselves call `gh pr merge`) is outside the rule text. A nested `claude` started in the same cwd would load the same settings.local.json, but this is not documented as a guarantee.
- "Not a security boundary": documented explicitly. P, "What a Bash rule doesn't match": "a deny or ask rule covers the invocation Claude usually produces and isn't a security boundary around the program." Then: "For filesystem and network enforcement that doesn't depend on the command text, use sandboxing. To inspect the full command text with your own logic before it runs, use a PreToolUse hook."
- `gh api`: the docs never mention `gh` or `gh api`. Not-covered-by-text-match logic above applies: `Bash(gh pr merge *)` does not cover `gh api .../merge`, `gh pr merge` via alias (`gh alias`), or `curl` to the GitHub REST API. To block those you need further deny rules (`Bash(gh api *)`, `Bash(curl *)`, ...), still bypassable by `sh -c`; or remove credentials from the agent's environment (not a Claude Code feature; outside this research). Sandbox network allowlist (sandboxing page, "Network isolation") is the documented way to block hosts regardless of command text.
- Pointers: sandbox page https://code.claude.com/docs/en/sandboxing.md ; P "How permissions interact with sandboxing".

## 5. PreToolUse hooks as a stronger alternative

- Exit 2 blocks. H, "Exit code 2": "Exit with code 2 to block the action. On events that can block, Claude Code stops the action: a `PreToolUse` hook blocks the tool call". Table "Exit code 2 behavior per event": `PreToolUse | Yes | Blocks the tool call`. Stderr becomes the message shown to Claude.
- Beats allow rules, and survives auto/bypass: P, "Precedence among rules, hooks, and mods": "A blocking hook also takes precedence over allow rules. A hook that exits with code 2 stops the tool call before permission rules are evaluated, so the block applies even when an allow rule would otherwise let the call proceed." Docs suggest the exact pattern: "add `"Bash"` to your allow list and register a PreToolUse hook that rejects those specific commands."
- Exit 1 is NOT a block: H: "Exit code 1 without valid JSON output is a non-blocking error unless the hook is one whose failure blocks the action... If your hook is meant to enforce a policy, use `exit 2`." (Also JSON `permissionDecision: "deny"` works; exit 2 wins over JSON `allow`: "Even a `permissionDecision` of `"allow"` doesn't let the action through.") Fail-open by default: H, "Block the action when a hook fails": "Without `onFailure` set, the same missing script is a non-blocking error and `ls` runs." With `"onFailure": "block"` on the hook handler, "a `PreToolUse` failure blocks the tool call" (failure = can't start, exit code other than 0 or 2, timeout, invalid output). Set `onFailure: "block"` for enforcement hooks.
- Hooks in `.claude/settings.local.json`: yes. H, hook locations table: `.claude/settings.local.json | Single project | No, gitignored when Claude Code saves a setting to it`. Hooks merge across levels (H: "Hook entries merge across settings levels rather than replacing each other").
  - Trust gate differs from deny rules: H "Workspace trust": "Claude Code checks workspace trust before it runs any hook from a settings file." Interactive: "holds back hooks from every settings file... until you accept the workspace trust dialog"; `-p`/SDK: treated as trusted. (P, "What runs before you trust a folder" table lists hooks in settings files as "Used" in the parent-trusted/-p columns.) Deny rules have no such gate. For a headless agent started with `claude -p` hooks run; for an interactive session in an untrusted dir the hooks are held back until trust is accepted (a risk for an unattended interactive session: verify the trust dialog was accepted for that folder).
  - `disableAllHooks`: a higher-precedence source can set it; `--settings` is above project local, so a stray `--settings '{"disableAllHooks":true}'` would turn hooks off. Not a concern unless you pass it.
- Hooks also run inside subagents: H: "Hooks from settings files, managed policy settings, and plugins also run inside subagents. When a subagent calls a tool, tool events such as `PreToolUse` and `PostToolUse` fire the same configured hooks as in the main conversation".
- Matching in hooks: the hook receives full tool input JSON (`tool_input.command`) so it can normalise: strip `bash -c`, resolve paths, regex `\bgh\s+(-\S+\s+)*pr\s+merge`, catch `gh api .*merge`. Also the declarative `if` field uses permission-rule syntax (H: "`if` uses permission rule syntax... `"Bash(git *)"` runs when any subcommand of the Bash input matches `git *`"). Fixed in 2.1.89: "hooks `if` condition filtering not matching compound commands (`ls && git push`) or commands with env-var prefixes (`FOO=bar git push`)". Prefer no `if` (or a broad matcher on tool `Bash`) and do the regex in the script, because `if` shares rule-syntax limits.
- Limits: a hook is still text inspection of the command (cannot see what `scripts/install` does internally unless you also inspect the file). Docs' own suggested stronger layer is the sandbox.
- Related stronger/alternate controls documented: `--disallowedTools` (CLI), sandbox (filesystem/network, command-text independent), managed settings (agent can't edit), `permissions.disableBypassPermissionsMode`.
