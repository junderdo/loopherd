# D88

## Decision

`S` in `loopherd view` brings up the shepherd: it focuses the live
shepherd's pane, or with none, splits the view's own pane `down` and starts
one there, so the view sits on top and the shepherd below.

- **Live shepherd.** An agent herdr names `shepherd` is focused with
  `agent focus`. Else, while the Claude process (PID and start time) that
  `shepherd.json` (D82) records still runs, used record or not, nothing
  starts and the record and handoff stay as they are: when its socket is
  the view's herdr and an agent is in its pane, that pane is focused;
  otherwise (another herdr, as a view on `loopherd-dev` reading the real
  state dir, or a pane that moved and got a new ID) the view notes `the
  shepherd's Claude (pid N) runs in <pane> on <socket>; not starting
  another`. A Claude that has exited doesn't count, so neither does another
  agent later in that pane, or its ID reused after a herdr restart.
- **Naming.** The skill's Shepherd section has every session of the
  human's shepherd, never a lead or member, run `herdr agent rename
  "$HERDR_PANE_ID" shepherd` at its start, so one started by hand is found
  too. herdr refuses a name another agent holds (`agent_name_taken`),
  which tells a second shepherd to stop and tell the human; on any other
  error it carries on and tells the human `S` can't find it. A lead must
  not: `tell`, restart and revive address it as `lead-<herd>`.
- **Starting.** With none, the view splits `$HERDR_PANE_ID` down with
  `--no-focus`, in the plugin context's `workspace_cwd` (a plugin pane's own
  cwd is the plugin's root) or else the view's cwd, passing the pinned
  roots below with `--env`. Once its shell is at the prompt it runs
  `agent start shepherd --kind claude`, then focuses it. The herdr name is
  what a second `S` finds. A failure before Claude is up closes the new
  pane, so a retry doesn't stack empty panes under the view; a failed
  focus after it leaves the running shepherd and notes `started the
  shepherd below, in <pane>; focus failed: …`. While the
  start runs, a second `S` is ignored, and `q`, `Esc` or Ctrl+C quits only
  once it settles, so the split isn't left empty; pressing one again quits
  at once, so a hung herdr can't trap the view.
- **Pinned roots.** A split pane gets the herdr server's environment, not
  the view's, so the view always passes the state and config roots it
  resolved (`XDG_STATE_HOME`, `LOOPHERD_CONFIG_DIR`), set in its own
  environment or not: the shepherd reads the state whose handoff the view
  consumed.
- **First prompt.** When `shepherd.json` is unused, names the view's herdr
  socket, and its `current` (D82) is unset or still the recorded session,
  and `handoffs/shepherd.md` was written after its time, the shepherd
  resumes from it as D82's resume does: the record is marked used, the
  handoff moves to `shepherd.prev.md`, and the prompt is D82's resume text.
  No record, a used one, or a `current` moved past the recorded session
  (as after D82's paste fallback) means the handoff is a leftover or was
  already acted on, and a record from another herdr (a view on
  `loopherd-dev` reading the real state dir) isn't this view's to consume;
  then, as with no handoff newer than the record, the shepherd gets the
  plain start: run `loopherd --skill` and follow its Shepherd section. A
  start that fails moves the handoff back and unmarks the record, so the
  next `S` resumes from it.
- **Popup.** A view without `$HERDR_PANE_ID` focuses a live shepherd (or
  notes one it can't focus), and otherwise says `no live shepherd; open
  the view as a pane to start one`.
- **Footer.** `S shepherd` is the last hint, after the toggles, so a narrow
  view cuts it before their state.

## Why

Asked by the human on LH-287 (2026-11-19), with the shepherd below the view
as the chosen layout. herdr splits only `right` or `down`, so the view must
exist first for it to sit on top. `s` and `a` toggle, and `t` switches theme
(D86), so the key is `S`.

Limits: a shepherd that hasn't named itself yet (before its first skill
read, or after a herdr restart drops names until its next session start),
with no record whose Claude still runs, isn't seen, so `S` starts a second
one. A recorded Claude that moved to another session by a continuation
D82's `live_session` would resolve, then exited, isn't resumed from. A
second quit key, or a stop signal, while summoning exits at once and can
leave the split. One that lands after the resume has moved the handoff
but before Claude starts strands it: the handoff sits in
`handoffs/shepherd.prev.md`, the record is marked used, and the next `S`
starts plain. The human recovers by pasting `continue as the loopherd
shepherd from <path to shepherd.prev.md>` into the shepherd that `S`
starts. The start runs on the view's reader thread, so reads (and an
Enter's focus) wait behind it, up to 30s for the new shell and a minute
for `agent start`; meanwhile the notes say `bringing up the shepherd…`
instead of calling herdr slow.
