# D58

## Decision

`loopherd retire <lead>` no longer trusts the pane environment alone. Besides
D50's pane check (the lead's entry holds the `HERDR_PANE_ID` and
`HERDR_SOCKET_PATH` loopherd runs with), it refuses when the lead's recorded
process is live, PID and start time matching, and is an ancestor of the
running loopherd, whatever those variables say. Both checks always run; a
lead with no recorded process, or none live, has only the pane check.

## Why

The pane check learns the pane from variables the caller controls, so
`env -u HERDR_PANE_ID` or `HERDR_PANE_ID=x` skipped it and let a lead retire
itself, dropping its own gates (D50). Process ancestry comes from `/proc`,
which a lead's shell can't rewrite. The start time keeps a reused PID from
passing as the lead, and a live lead loopherd doesn't run under (the
shepherd's or the human's) can still be retired. The pane check stays
because a command detached from the lead (`setsid -f`, `nohup … &`) is
reparented away from it while still carrying the pane's environment.

The two checks don't close every path: a command both detached from the
lead and run without the pane environment passes both. So does one in a
PID namespace with its own `/proc` (a sandbox such as bubblewrap), where
the walk can't see the lead, unless the pane check catches it.
