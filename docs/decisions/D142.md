# D142

Amends D124.

## Decision

A broker's move onto a new install (D124) checks more before it execs,
and follows every install that lands.

- **The probe is the new image's startup check.** Instead of
  `<install> --version`, the old broker runs `<install> broker <lead>
  --check`, which loads the lead's launch record, herd file and, for a
  herd that guards merges by credentials, its credentials, as a starting
  broker does (`lead_env`), then exits. A failure, or no answer within 10
  seconds, is noted once in the lead's mailbox with what the check
  printed, and the old broker serves on.
- **The old image says where the new one came from.** It execs with
  `LOOPHERD_BROKER_STARTED_FROM=<dev> <ino> <path>`, the install it
  probed. The new image reads it before anything slow, and only beside an
  inherited lock. The path is what it follows; the file is what it counts
  as running, so an install that is a script exec'ing another binary isn't
  moved onto again every second. Such a wrapper is followed only when the
  script itself changes, and doctor warns about its broker, which records
  the binary behind it. A broker started any other way reads its own path,
  with Linux's ` (deleted)` suffix stripped.
- **It execs what it probed.** An install whose dev/ino changed during
  the probe isn't exec'd; that's noted, and the next look probes the new
  file.
- **A non-executable install is noted.** The broker takes the first
  `loopherd` on its `PATH` that is executable or is its own install path,
  so its install landing without its x bit fails the probe and is noted
  once, rather than skipped silently as a shell would.
- **Doctor waits once.** Its 3-second grace is one deadline shared by
  every broker it checks, counted from its first wait, and it waits only for a broker whose recorded
  binary is the `PATH` install it follows. A broker on another build, as a
  dev build's, is warned about at once. Doctor run inside a lead's broker
  says that broker moves once answered only when it will.
- **A failed move is recorded for doctor.** A broker whose check of an
  install failed adds `failed <dev> <ino>` to its lock record. Doctor
  neither waits for it nor says it moves while that is the `PATH`
  install: it warns that the broker serves on its old build, and the fix
  is `broker-restart` once the install is fixed.

## Why

D124 noted the gaps in review: an install landing while the new image
started left the broker reading `<path> (deleted)` and never following
again; a config error the new image hit at startup ended a broker that
would have served on, dropping queued requests with no note; and doctor
waited 3 seconds per lead, serially, even for brokers that can't move.
Checking the new image's own startup catches the config case before the
exec, where the old broker can still serve. A downgrade to a loopherd
from before `--check` fails the probe and is noted, rather than ending
the broker as D124 left it.
