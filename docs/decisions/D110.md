# D110

## Decision

Amends D98. Every loopherd command run in a lead's pane is routed through
its broker, refused, or runs directly because it is harmless there (LH-314).
loopherd itself refuses, before touching herdr or a file, the commands that
are the shepherd's or the human's, naming why. The tool hook's denials of
some of them by name stay, but they are no longer the boundary.

"A lead's pane" is D98's: the lead whose sandboxed Claude is an ancestor,
else the unretired lead the ledger has in `$HERDR_PANE_ID` on
`$HERDR_SOCKET_PATH`. Inside the sandbox only the pane can name the lead,
so a refusal never depends on the parent-pid walk alone. A run that finds
no lead but can't write the ledger is taken to be in a sandbox, and is
refused too, saying it can't write the ledger (a lead's sandbox, or
permissions on the state dir). Commands that never touch the ledger
(`config set`, `herd set`, `init`, `setup --again`, `merge-guard` and the
other config and herd-file edits) run when its writability can't be told.
The shepherd's recorded pane is never a lead's, even when it carries a dead
lead's old id after a herdr restart.

A pane match alone, with a writable ledger, is the human's shell in that
pane as often as the lead's: it refuses only while the lead's recorded
Claude is alive, so the human can `revive`, `lead` or `pause` from a dead
lead's pane. When the ledger records no process for the lead, the refusal
says to run the command from another pane.

A sandboxed lead is refused however it spells a command, since the sandbox
hides nothing but the ledger's writability and its pane. A hook-only lead's
refusals are a guardrail, not a boundary: a spelling that drops what places
the lead (`env -u HERDR_PANE_ID loopherd pause h`) passes them, and only the
sandbox stops that. `revive --startup` from a hook-only lead whose lineage
is broken relies on the parent-pid walk alone; there is no check that herdr
is its parent.

Plain `setup` assumes Claude's Bash has no controlling terminal, so in a
lead's pane `/dev/tty` won't open and it names its flags instead of
prompting; a test pins that a run with no controlling terminal doesn't
prompt.

| Command | In a lead's pane | Why |
|---|---|---|
| `add`, `feed`, `tell`, `read`, `prompt`, `restart`, `restart --self`, `retire`, `release`, `status` | routed | D98: the broker carries them out on the lead's own herd |
| `spawn` | refused | add and feed start the herd's workers from its herd file (D98) |
| `broker-restart` | refused | the shepherd's or the human's (D106) |
| `lead` | refused | starting a lead is the shepherd's |
| `revive`, `--dry-run` included | refused | reviving members is the shepherd's; a dry run reads herdr too. `--startup` is refused by lineage or a sandbox only, never by pane: herdr's startup hook carries its focused pane's id, which may be a lead's |
| `pause`, `resume` | refused | pausing a herd is the human's |
| `herd set`, `herd unset`, `herd remove`, `init` | refused | a herd file is the human's to change |
| `lead-defaults --set`, `config set`, `config unset`, `setup` with `--again`, `--lead-defaults` or `--context` | refused | config.toml is the human's to change |
| `merge-guard` | refused | a herd's credentials are the human's to set up, with the human's gh login |
| `broker` (hidden) | refused | `lead` and `revive` start a lead's broker outside its sandbox |
| `restart-wait` (hidden) | refused | the broker starts the lead's restart waiter |
| `report` | routed | its broker writes the lead's own mailbox (D111); `--as` another member is refused |
| `handoff` | direct | writes the lead's own `handoffs/<lead>/handoff.md`, the one part of the state dir its sandbox allows (D111) |
| `watch` | direct | the lead's watch runs outside the sandbox (D104) |
| `herds`, `herd get`, `lead-defaults`, `config get`, `stats`, `reports`, `--skill` | direct | read files only; no herdr |
| plain `setup` | direct | without a terminal it only names its flags, and the installer a lead with `install = true` runs (D17) runs it so |
| `doctor` | direct | read-only; the installer runs it last. A sandboxed lead has no herdr socket (D105), so its herdr checks fail rather than reach herdr |
| `install-hook` | direct | writes Claude's settings, not herdr or the herd; the installer runs it (D17), and the tool hook lets a lead's Bash run it only when its herd sets `install = true` |
| `update`, `--version` included | refused unless the herd sets `install = true` | it replaces `~/.local/bin/loopherd` and runs the installer, which counts as `install` (D122); the refusal reads the switch from the herd file, the tool hook denies it under the same switch, and with the switch on the lead's sandbox runs a bare `loopherd update` outside it |
| `update --check` | direct | reads the latest release and changes nothing |
| `view`, `pr` | direct | herdr's plugin runs them for the human with the focused pane's id, which may be the lead's; in the sandbox they reach no herdr (D105) |
| `stop-hook`, `session-hook`, `prompt-hook`, `tool-hook`, `herdr-event-hook` | direct | Claude Code or herdr run them outside the sandbox, each for its own pane |
| `notify-run` (hidden) | direct | runs a notification command, which the lead's own Bash could run anyway |

## Why

LH-301 routed the herd changes through the broker but left `lead`,
`revive`, `pause` and `herd set` neither routed nor refused: in a sandboxed
lead they failed on a read-only file or an unreachable socket, and in a
hook-only lead only the tool hook, which matches commands by name, stood
in the way. Refusing in loopherd makes a sandboxed lead's answer the same
however the command is spelled, and says why instead of failing on a file.
Chasing every spelling in a hook-only lead buys little: the sandbox is the
boundary (LH-349).

A command is direct, rather than refused, where refusing it would break
the human (`view`, `pr` and the hooks run with the lead's pane id), break
what a lead is allowed to run (the installer's `setup`, `doctor` and
`install-hook`), or gain nothing because it reaches no herdr.
