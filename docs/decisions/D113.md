# D113

## Decision

**A param that reaches a name, branch or worktree is a plain word.** Each
`add` and `feed` checks every param a template's `name`, `branch` or
`worktree` pattern uses, and every param when it has no `name` pattern,
since the default name joins them all. A value must match
`[A-Za-z0-9][A-Za-z0-9._-]*` without `..`; otherwise the spawn fails before
anything is created, naming the param. A param only the prompt, `done` or
`merged` uses may hold any text. This holds for the human's commands too, not
only a lead's.

**A lead's workers meet the member-path guard first.** Before the broker
starts a worker for a lead's `add` or `feed`, dry runs included, it runs
`Guard::path_refusal`'s checks on that worker: its repo, and the worktree it
would get, which for a branch with a worktree already is that existing one.
It refuses a repo a lead can write, any lead's worktree, and a worktree not
beside the herd's others, as `retire --close` and `release` already refuse a
ledger entry naming them. A lead's worker may reuse a worktree that
already exists only when a ledger entry of the lead's own herd, retired or
not, records it, and no live entry of another herd, or of none, does. A refused `add` fails; a refused `feed` task is an
error line, and the feed goes on to the next. A lead's own ledger entry may
still name its own worktree, but a worker named like a lead may not take
that lead's.

## Why

A lead's params flowed into a worker's name, branch and worktree slug with
only `validate_name` and git's ref rules to stop them, and `ensure_worktree`
reuses a branch's existing worktree wherever it is. A param could name the
lead's own worktree as the slug, or a branch the human checked out elsewhere,
and the worker would start there, outside the sandbox. D98 said the lead's
words reach only its prompt; this makes that true for paths.

The charset holds for everyone because the queue's `source` often prints
text a lead can shape, such as card titles, and real params (numbers, card
keys, slugs, `feat`) are plain words already. Checking only params a path
uses keeps free text available to prompts.

The path checks alone only placed a worktree in the herd's worktrees
directory, and in the `<project>/<project>/` layout the human's own
worktrees, and another herd's workers' when two herds share a repo, live
there too (LH-354). A lead can't write the ledger (D97), so an entry of its
herd was written by its broker or the human, and naming a worktree there is
what vouches for it.

What the guard covers, for a lead's `add` and `feed`, dry runs included: a
repo inside the state dir or any lead's worktree, refused before git runs
on it; any lead's worktree, its own included, by branch or detached slug; a
worktree not beside the herd's others; an existing worktree a live entry
outside the herd records, even when a retired entry of the herd records it
too; and an existing worktree no entry of the herd records. Only each
entry's current run counts; a run moved into its `earlier` vouches for
nothing. It does not cover the human's own commands, which may reuse any
worktree. An entry vouches for its path for as long as the ledger keeps it:
if a recorded worktree is removed and the human checks out another at the
same path, a lead's worker can still start there, as it can in a worktree
the human's own `add` for the herd put a worker in. A worktree the human
uses by hand, with no live entry recording it, is protected only while no
entry of the herd records it.

The guard sees the worktree at planning time. A worktree created for the
branch between that check and `ensure_worktree` is still reused; the shared
`.git` is the lead's to write (D89), so this narrows the gap rather than
closing it.
