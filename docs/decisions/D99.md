# D99

## Decision

Amends D11 (LH-302). Every loopherd version loads and saves a ledger written
by any other, losing nothing it doesn't understand.

- **Unknown fields** on an `AgentRecord`, its `earlier` runs included, land
  in a catch-all map and are written back unchanged.
- **Unknown enum variants** (`Outcome`, `AfterMerge`, `Role`) load as an
  `Unknown` variant holding the raw JSON, and are written back unchanged.
- **Behaviour on an unknown variant** is the cautious one:
  - `stats` shows an unknown outcome as `-` and counts it `unrecorded`; its
    `--json` carries the raw value.
  - `feed` leaves a member with an unknown `after_merge` alone (no checks,
    no retire, no commands), and `watch` keeps its slot taken, as for a
    pending one.
  - An unknown role is not a lead, so it is treated as a worker.

Rules for future changes to the ledger:

- A new field is optional: `#[serde(default)]`, and `skip_serializing_if`
  when its absence means the default.
- A new enum stored in the ledger ends with an `#[serde(untagged)]
  Unknown(serde_json::Value)` variant, and code matching it decides what an
  unknown value means rather than failing.
- Never rename or repurpose a field or a variant's tag; add a new one.

## Why

Mixed versions are normal: the installed binary lags a merge until
`scripts/install` runs, and members run their worktree's build. Before
this, a variant one binary didn't know failed the whole ledger parse,
breaking every command and the Stop and session hooks, and every typed
load and save by an older binary silently dropped the newer fields. Keeping
the raw value, rather than a bare `Unknown` tag, means a round trip through
an older binary doesn't erase what a newer one recorded.
