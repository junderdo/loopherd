# D29

## Decision

Herd files change through `loopherd herd get|set|unset <herd> <key>`, with
dotted keys (`queue.max`, `lead.merge`, `template.card.args`) and values
parsed as TOML. Edits go through `toml_edit`, so the file's comments, key
order and formatting elsewhere survive, and missing tables are created. The
edited text must pass the same checks `loopherd herds` makes before it is
written, through a temp file and a rename; an edit that fails them is
refused and the file is left as it was. `get` of an unset key exits 1;
`unset` of one succeeds and writes nothing.

The PreToolUse hook denies `loopherd herd set` and `unset` in a lead's
pane whatever its switches (as with `pause`, D23), since a lead could
otherwise turn on its own `[lead]` switches (D17). `herd get` is allowed.

Concurrent edits of one herd file take turns: each holds a flock on a hidden
`.<herd>.toml.lock` beside the file from the read to the rename, and writes
through its own temp file, keeping the file's permissions. A symlinked herd
file is edited at its target, so the lock and the temp file sit beside the
target, not the link, and the lock is named after the target's file name.

**Limits.** The hook is a guardrail on the Bash command's text, not a
sandbox. Indirection gets past it: `$(command -v loopherd) herd set …`,
`L=loopherd; $L herd set …`, `find -exec`, a Python `os.system`, or
`bash <<<` with the command as its input when a `$` or a substitution
builds the script operand (`bash "$S" <<< …` with `S=/dev/stdin`) or a
symlink names the input. `pause` and `resume` share the same limit.

The lexer reads heredoc bodies as data up to their terminator line, decodes
`$'…'`, denies `$"…"`, undoes `\\` and `\$` in backticks and denies an
escaped backtick there, and denies a glob or brace expansion in the program
word and a brace expansion in a gated program's arguments (D17's "What the
hook can't read"). A heredoc body is read as commands unless every command
in the script is a known sink (D17 lists them). A body written to a file
that a later Bash call runs gets past it, and so does one that a sink runs
after all: a git hook or `-c core.pager=…`, a git alias that runs a
shell (one written into a config file other than through `git config`,
or read from a config under a changed `HOME` or `XDG_CONFIG_HOME`), or a
`gh` extension.
A glob in a gated program's arguments (`gh pr merg?` beside a file named
`merge`) gets past too, and so does a `$(…)` in an array subscript that
bash evaluates (`test -v 'a[$(…)]'`, `$((x))` with `x='a[$(…)]'`). So does `env -S '…'`, and so does `sudo`'s `-h`/`--host`, `-a`/`--auth-type` or `-c`/`--login-class` before the command (`sudo -c x gh pr merge 1`), which this hook reads as the program but Linux's sudo refuses to run; listing them would make `--login` read as `--login-class`. So do these forms
from LH-165 (D48): a script written to a file and then sourced
(`printf '…' > s.sh; source s.sh`); a program word that a variable
holds, split by `IFS` (`IFS=,; x=gh,pr,merge,1; $x`) or set by `read`
(`read -r c <<< gh; $c pr merge 1`); a program word that a
substitution prints (`` `printf %b 'g\x68'` pr merge 1 ``); and a
`GIT_CONFIG*` or `BASH_ALIASES` name that a `$` or a substitution builds
(`declare -n A=BASH_$X`), or that a read-only program redefined where the
command text doesn't show it sets: a function the Bash tool's shell
inherited or a sourced file defines (`. ./defs.sh; echo GIT_CONFIG_COUNT=1`),
a definition, `enable` or `trap` that a variable runs (`e=eval; $e 'echo() { …; }'`,
`t=trap; $t 'echo() { …; }' DEBUG`),
or an `echo` earlier on `PATH`. So does a name a read-only program prints that
arithmetic then evaluates (`echo GIT_CONFIG_COUNT=1 | read x` under
`lastpipe`, then `: $((x))`), which can set only an integer.

D53 denies such a name wherever it can't tell a mention from setting it, so
these are denied though they set nothing: one after anything before the
program (`time rg GIT_CONFIG`, `MSG=BASH_ALIASES true`), one in a program
outside D53's short list (`for f in GIT_CONFIG.md`, `sed -n /GIT_CONFIG/p
f`, `bash -c 'echo GIT_CONFIG'`), one inside a `${…}`, `$[…]` or `((…))`
even read-only or in single quotes, one after a `${`, `$[` or `((` left
open earlier, prose included (`git commit -m 'a (( b GIT_CONFIG'`), a
longer name holding one (`XGIT_CONFIGY=1`), `printf` with a `$` in its
arguments, `declare -p` with any option but `-p`, any mention in a script
that defines a function or holds a word `function`, `enable` or `trap`,
quoted or not (`f() { :; }; echo GIT_CONFIG`, `git commit -m trap; rg
GIT_CONFIG`),
and a heredoc body read as a script whose prose names one. A relative shell
operand ending in `stdin` or `fd/<n>`, or all digits, is denied as the
shell's input even when it is an ordinary file (`bash scripts/fd/3`).

The hook denies as unreadable the script of `trap`, `sh -c` (and the
other shells' `-c`), `flock -c` or `eval` when a `$(…)` or backtick
substitution builds any of it (`trap "$(echo gh pr merge 1)" EXIT`,
`bash -c "$(cat)" <<< 'gh pr merge 1'`), since bash runs whatever it
prints. It denies rather than naming these as limits because a lead can
single-quote the script instead: a `$(…)` inside single quotes is still
read as commands. The deny costs `eval "$(ssh-agent)"` and double-quoted
scripts holding a `$(…)`, such as `trap "kill $(jobs -p)" EXIT`; a `$((…))`
alone prints only a number, so it passes. A script that a variable or a
positional parameter holds gets past it (`x=$(cat f); eval "$x"`,
`bash -c 'eval "$1"' _ "$(cat f)"`), as a program word a variable holds
does. It reads bash's options as bash does: long ones first, with one dash
or two (`-login`, `-rcfile f`), then clusters in which each `o` or `O` takes
the next word (`bash -oc pipefail 'script'`). Other shells read them
differently: zsh reads a one-dash word only as a cluster
(`zsh -restricted 'script'` runs it), and its `o` takes the rest of the
cluster as the option's name (`zsh -conoclobber 'script'`). Any shell other
than bash, `sh` included since it may be bash, is judged under every
combination of those readings, and a `-c` script that any of them finds is
judged. zsh's `--emulate` takes the next word as its value
(`zsh --emulate csh -c 'script'`).

A `$` or a substitution that builds a shell's option word, or the operand
where no `-c` was read, may print `-c` (`bash "$(echo -c)" 'script'`,
`bash "-$(printf c)" 'script'`, `C=-c; bash "$C" 'script'`), so every word
after it is judged as a `-c` script. Only a word whose literal parts are `-`,
`+` and letters counts, so `bash "$f.sh" …` and `bash "$HOME/x.sh" …` don't.
Left unquoted, a word there is denied as unreadable when its literal text
before its first `$` or substitution is empty or a run of `-`, `+` and
letters starting with `-` or `+`, since it may split into both `-c` and the
script (`IFS=,; X='-c,gh pr merge 1'; bash $X`, or `gh${IFS}pr…` under the
default `IFS`), and the words after it are then only `$0` and the arguments.
Literal text after the expansion doesn't save it, since it may be left over
as `$0` (`bash $X.sh`, `bash $(cmd)/x`). So is a quoted `"$@"` or
`"${a[@]}"`, which expands to as many words (`set -- -c 'gh pr merge 1';
bash "$@"`). Past a word that may print `-c`, every later word counts, since
bash may still be reading options (`bash "$A" $B` with `A=-x`). Quoting a
plain variable costs nothing; the deny costs `bash $f`, `bash $HOME/x.sh`
and `bash $OPTS x.sh` written unquoted, and `bash "$A" $B`.
A guessed script that is a single line left inside a quote passes, since
bash parses the whole line before running any of it (`bash "$f" "don't
stop"`, `bash "$C" "gh pr merge 1; echo it's"`), but only when its source
holds no backslash, `$'` or `$"`, which the lexer may undo where bash keeps
them (`bash "$C" "gh pr merge 1; echo it\'s"` is judged as a merge). Any
other ordinary argument passes too, but one a substitution prints is
denied as above (`bash "$f" "$(date)"`).

The hook also denies `gh` as unreadable when a `$` or a substitution builds
its command, the subcommand after `pr`, or any word before them but a
value of a literal `-R` or `--repo` whose every `$` and substitution is
quoted (`gh pr "$(echo merge)" 1`, `gh pr $M 1`,
`gh pr -R $(echo 'o/r merge') 1`, `gh pr -R "a"$X 1`, and
`gh pr "-$X" o/r merge 1`, which shifts the subcommand when `X=R`), and so inside an `eval`, `trap`
or `-c` script too. On a `gh api` call whose path merges, any other word
that a `$` or a substitution builds denies it, since it may be the method
or a field (`gh api "$(echo -X)" PUT …/pulls/1/merge`); that denies
`-f "title=$T"` and `--jq "$J"` on a merge path too. It denies rather than
naming these as limits because the lead can write the word out, and the
reads it costs are rare: a word built after those passes
(`gh pr view "$(git branch --show-current)"`, `gh api "repos/$O/r"`), as
does a quoted repo (`gh -R "$REPO" pr view 1`, `--repo="$REPO"`). A
`gh api` merge path that a `$` or a substitution builds still gets past
(`gh api -X PUT repos/o/r/pulls/1/$M`).

`xargs` appends the words it reads from stdin to its command unless an
`-I`, `-i` or `--replace` option sets a replace string, read as getopt reads
xargs's options (`-E -i` sets an end-of-file string, not a replace), and no
later `-L`, `-l`, `--max-lines`, or `-n`/`--max-args` whose value is a
number other than 1 clears it (`xargs -I X -n 2 gh pr` appends; `-n 01`
and `-n +1` don't, as xargs reads the number). A `-n` value the hook can't
read as a number (`-n "$N"`) may do either, so both readings are judged.
Under
an `xargs` that appends, the hook denies as unreadable a command those words
may still choose: `gh` with no command (`xargs gh`), with `pr` or `alias`
and nothing after it (`echo merge 1 | xargs gh pr`, `xargs gh pr --repo`),
or any `gh api` call not already judged a merge, whose path or method may
arrive (`echo repos/o/r/pulls/1/merge | xargs gh api -X PUT`); a wrapper
with no command after it (`xargs env`, `xargs timeout 60`, `xargs xargs`);
a shell with no `-c` script or operand (`xargs bash -c`, `xargs bash`), or
with nothing after a word that may print `-c` (`xargs bash "$C"`);
`flock -c` with no script; and any `watch` or `find`, whose command or
`-exec` may arrive. It does the same for the other gated programs whose
switches those words may still choose, unless the command as written is
already judged: `git` with no subcommand or with `push`, `pull` or `config`
(`echo --force | xargs git push`); `loopherd` with no subcommand, `herd` or
`config` with nothing after it, or `lead-defaults`, `setup` or `restart`
(`echo set h k v | xargs loopherd herd`); `cargo` with no subcommand or with
`run`, or a subcommand that an alias set in the command names; any `curl` or `wget`, whose URL may arrive; and `scripts/install`
judged only as an install, which `--lead-defaults` may follow. `xargs` with
no command runs `echo`, so it passes, as do `xargs gh pr view`,
`xargs bash x.sh`, `xargs git add`, `xargs git log --`, `xargs loopherd herd
get h`, `xargs cargo fmt --check` and `xargs grep foo`. The deny costs
`xargs git push` of branch names, `xargs git pull`, `xargs git config`,
`xargs cargo run …`, `xargs loopherd setup|restart|lead-defaults …`,
`xargs curl`, `xargs wget`, and `xargs scripts/install`, which is denied
even with `install` on, where it was judged an install before; `xargs -I {}
git push origin {}` passes instead.

Under `-I`, `-i` or `--replace`, xargs puts each line into the words holding
the replace string as one argument, so it can't add a word. The hook reads
the replace string and denies `gh` as unreadable when a word holding it may
be gh's command, the subcommand after `pr` or `alias`, or a word before them
other than a repo value (`echo merge | xargs -I X gh pr X 1`), or any word
but the path of a `gh api` merge call, as it does for a `$`. It also denies
a program word holding a replace string, which a wrapper then runs
(`echo gh | xargs -I X env X pr merge 1`), though not the command word of
the xargs that set it, which xargs never fills (`xargs -I t git log -1 t`).
The match is on text, as xargs's is, so a replace string inside a longer
word counts (`xargs -I e gh pr view e` is denied, since xargs runs `gh pr
vi1w 1`). An assignment that holds one is read as one a `$` builds: in its
name, as a name the hook can't read, and in a `CARGO_ALIAS_*` value, as an
alias whose value it can't read (`xargs -I V env CARGO_ALIAS_Y=V cargo y`).
A shell's `-c` script is judged with the replace strings of the xargs that
runs it, so one in its program word or gh's command words is denied
(`echo 'gh pr merge 1' | xargs -I X bash -c X`, `xargs -I X bash -c 'gh pr
X 1'`). A `gh api` path the replace
string fills gets past (`echo repos/o/r/pulls/1/merge | xargs -I Z gh api
-X PUT Z`), as a `$`-built one does. A replace
string in another gated program's words gets past, as a `$` there does
(`echo +main | xargs -I X git push origin X`, `echo set | xargs -I X
loopherd herd X h k v`), since denying it would cost `xargs -I {} git push
origin {}`. So does one elsewhere in a shell's `-c` script, which xargs
splices into the script's text before the shell parses it, so a line can
add commands (`echo '; gh pr merge 1' | xargs -I X bash -c 'wc -l X'`);
denying it would cost `xargs -I {} bash -c 'wc -l {}'`.

The hook denies `gh` as unreadable after a `GH_CONFIG_DIR` assignment
before it in the command (a `NAME=value` word, after `env`, or among the
arguments of `export`, `declare` and the like), or after any assignment
whose name it can't read (so `export $(…)` denies a later `gh` too), since
gh would load aliases from that directory. A bare `export GH_CONFIG_DIR`
counts as setting it. One set any other way and not exported by name
(`read`, `printf -v`, `${GH_CONFIG_DIR:=…}`, `for GH_CONFIG_DIR in …`, the
lead's own environment) gets past it, and so does one set after a `trap`,
function or loop body whose `gh` runs later, and a changed `HOME` or
`XDG_CONFIG_HOME`, which moves gh's config too. So does a `gh` that a
program the hook doesn't look inside runs, such as `parallel gh …`
(it does look inside `watch` and `find -exec`).

The hook reads a `CARGO_ALIAS_*` from a `NAME=value` word before the
command (after `env` and the other wrappers too) or among the arguments of
`export`, `declare`, `typeset`, `local` or `readonly`. A value it can't
read, because a substitution or a `$` builds it, denies cargo run through
that alias only: `CARGO_ALIAS_X=$CMD cargo y` is allowed. A name it can't
read denies every cargo subcommand that isn't built in: one that a `$` or
a substitution may build (`export $N=…`, `env CARGO_ALIA$(…)=…`), one
appended to with `+=`, or a nameref from `declare -n`, `typeset -n` or
`local -n`. Assignments inside `eval` count. An alias set any other way
gets past it: `read CARGO_ALIAS_X <<<…`, `printf -v CARGO_ALIAS_X …`,
`for CARGO_ALIAS_X in …`, an `env` argument whose `=` only a `$` or a
substitution supplies (`env $A cargo x` with `A=CARGO_ALIAS_X=run`, or
`env CARGO_ALIA$(echo S_X=run) cargo x`), an alias from cargo's config
files given to `xargs cargo` (`xargs cargo x`, with the rest of the
command on stdin), or an assignment in a file the command sources. An
alias the hook reads, or any under an assignment whose name it can't read,
is denied under an appending `xargs` as `cargo run` is.

The hook also binds only leads' panes, so another member, or the shepherd,
can still turn a lead's switches on with `herd set`. Closing either gap is
out of scope here.

## Why

Hand-splicing TOML broke a herd file once already (a comment matched the
splice anchor while applying the routed queue, LH-107). Validating before
the write means a bad edit can't leave a herd that `feed` or `lead` then
rejects. A lead editing the file with other tools (sed, an Edit tool) is
out of reach of the hook, as for every switch.
