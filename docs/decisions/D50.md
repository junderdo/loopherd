# D50

## Decision

**Amended by D83** (LH-283): the hook now denies only `loopherd retire`
of a spelled-out `lead-` name; a name it can't read, `xargs` and `cargo
run` forms pass (D17).

The lead hook counts a pane as a lead's while the ledger records a lead
there and no unretired entry holds the same pane id and socket, so a
retired lead whose agent still runs keeps every gate. An unretired entry on
that pane wins: a live lead's own switches apply, and a worker's pane is
ungated. The hook also always denies, in a lead's pane, `loopherd retire`
of a name starting `lead-`, of no name, or of a name bash may expand (`$`,
a backtick, a glob or a brace), through the same wrappers, `cargo run`
forms and cargo aliases as its other denials. Under an `xargs` that may set
a replace string (any `I` or `i` in a short option, `--replace` or an
abbreviation of it, or a long option it can't read), any word holding
`retire`, a `sh -c` script included, is denied.
Retiring a lead is the shepherd's or the human's job; a lead still retires
its members by name.

Since LH-205, `loopherd retire` itself is the primary check: it refuses,
before touching the ledger, to retire a lead whose entry holds the pane id
and socket it runs in, whatever spelling the shell expanded to. The hook's
check stays as a backstop. Since LH-220 it doesn't trust the pane
environment alone: it also refuses a lead whose live process is an
ancestor of the running loopherd (D58).

## Why

Matching only unretired leads let a lead run `loopherd retire lead-<herd>`
in its own pane and then run everything its switches deny. herdr reuses
pane ids: across sessions (D21, D22), and across a restart of the same
server on the same socket (checked live, PR #165). So a retired lead's
pane id doesn't prove the command comes from that lead's agent, and the
retired record yields to any unretired entry on the same id. Without that, a lead
or worker given the id after a restart would be judged by the retired
lead's switches, which fails open for a live lead whose switches are
stricter. The command text can't say which lead a name belongs to beyond
the `lead-<herd>` naming every lead gets, so the hook denies retiring any
lead, and an unreadable name, rather than reading the ledger to match its
own name.

Retired records keep their pane ids rather than having them cleared on
`retire --close`. Clearing would not cover a lead retired without `--close`
whose herdr then restarted, the path by which an id comes back, and a
retired lead's running agent is exactly what must stay gated. What is left
fails closed:

- A Claude with no ledger entry, the shepherd's or the human's, in a pane
  whose id a retired lead held on the same socket is gated as that lead.
  Run such commands from another pane.
- `loopherd report` won't speak for a retired lead, though the hook's
  messages say to ask that way.
- A lead respawned under the same name replaces the retired record, so the
  old agent, if still running, is no longer matched; retire a lead with
  `--close` before spawning its successor.
