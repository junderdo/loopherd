# D98

## Decision

A lead's herdr-touching loopherd commands run in a **broker**, one per
lead, outside its sandbox. In a lead's pane, sandboxed or hook-only,
loopherd hands the operation to the broker and calls no herdr itself,
but for the lead's own watch, which runs outside the sandbox and calls
herdr directly (D104).
The shepherd's commands, and members of unled herds, keep calling herdr
directly. Builds on D89.

- **The gate is a whole loopherd operation.** A request names an
  operation and its arguments, never a herdr command. A herdr-command filter
  can't tell an honest feed from a hostile `agent start`; an operation can
  be checked against the herd.
- **Lifetime.** `loopherd lead` starts the broker detached, in a session
  of its own, as `restart --self` starts its waiter (`loopherd broker
  <lead>`, hidden), and waits until it holds its lock. `revive`, startup
  revive included, starts it for each unretired lead it revives on its
  own herdr whose broker isn't running, and fails when it can't; a lead
  recorded on another herdr's socket gets its broker from that herdr's
  revive, under that herdr's config dir. The broker exits once the ledger has
  its lead retired or gone. A flock on `<config dir>/broker/<lead>.lock`
  keeps it to one per lead: a second broker exits after retrying it for a
  second, which outlasts any probe of it. Neither starts a broker for a
  name that isn't a valid member name.
- **Start it from an unsandboxed shell.** Claude Code's sandbox ends
  every process a Bash call leaves behind (D89), `setsid` or not, so a
  broker started by `lead` or `revive` in a sandboxed Claude's Bash dies
  with that call, after `start` has reported it serving. The shepherd runs
  both from an unsandboxed shell or with its sandbox off for them; doctor
  fails for a lead whose broker died this way. herdr's startup revive runs
  outside any sandbox.
- **Identity is fixed at launch.** The broker takes its lead's name from
  its command line and its herd from `sandbox/<lead>.lead.json`, which
  `lead` writes into the config dir, where the lead can't write. It never
  reads either from a request, `HERDR_PANE_ID` or the ledger. The one
  exception is D89's: the human's `revive --name` adopting a lead with no
  kept record writes that record from the ledger's herd.
- **The transport is files, not a socket.** On Linux and WSL2 Claude
  Code's sandbox allows every Unix socket or none, so a lead that ends up
  with none can't reach a socket broker. The lead writes each request as
  one JSON file, renamed into `<state dir>/broker/<lead>/requests/`. The
  broker writes the reply to `<config dir>/broker/<lead>/replies/`, which
  the lead can read but not write, then removes the request. A broker
  takes every request in its folder as its lead's, so a lead that could
  write another lead's folder could act as that lead: a sandboxed lead's
  `allowWrite` names its own requests folder alone, which `lead` and
  `revive` make before it starts, and the file tools are denied the whole
  `broker/` folder (D97). A hook-only lead can still write every folder
  on the way to its requests, so each round the broker
  opens them one at a time without following symlinks, and reads and
  removes entries relative to that folder: a symlink never points it
  elsewhere, and it removes only the entry itself, a folder only when
  empty. It lists a folder from its descriptor, so it needs no `/proc`
  and serves on macOS too. The broker serves only a regular file under
  1 MiB with one link, holding exactly one known operation, and refuses
  anything else; the link count stops a hard link handing the broker a
  file the lead can't read. One whose file name can't name a reply
  is only removed. A panic answers that request as failed. A client that
  gives up withdraws its request, so no later broker carries it out.
  Replies are kept 10 minutes, read or not.
- **Reach.** The broker carries out an operation only on its own herd's
  unretired workers. It refuses, naming why, the shepherd, the lead
  itself, a member of another herd, a member in no herd, another lead,
  and a name with no unretired entry. `retire` and `release` may also
  name a retired worker of the herd, since `retire --close` reruns on
  one and `release` needs one. `restart --self` and report may name the
  lead itself. `read` reaches the same workers as `tell`.
- **A lead's status is its own herd's.** The broker shows the herd its
  launch record names, never one a request does: that herd's members,
  with its retired ones for `--all`, and its pause and task counts. It
  leaves out other herds, ungrouped members and strays, and refuses
  `--strays`, since strays are herdr's agents outside every herd, other
  herds' leads and the shepherd among them. Narrowing `--all` rather than
  refusing it keeps the lead's retired workers in sight without widening
  its reach. The lines it shows match the direct command's for that herd;
  the shepherd's and an unled herd's status run as before.
- **Starting workers comes only from the herd file.** `feed` and `add`
  must name the lead's own herd, and `add` one of its herd file's
  templates; the broker refuses `add` with claude args of the lead's
  own, so a worker's command line comes only from the herd file and the
  queue. The lead's params reach a worker's name, branch and worktree only
  as plain words (D111), and the broker refuses to start a worker for
  `add` or `feed` whose repo or worktree the member-path guard refuses;
  otherwise the lead's words reach only its prompt. A lead's raw
  `loopherd spawn` is refused, and the broker has no spawn to run.
- **after_merge runs in the broker.** It is part of the lead's `feed`, so
  it runs outside the sandbox, from the herd file's commands, gated as
  the lead's tool hook would gate them, by the switches of the herd the
  launch record names, never the ledger's. A held-back command runs none
  and notes the member, as before. With `feed` and `add` in the broker,
  the lead's sandbox no longer runs them as excluded commands. The
  commands run with the broker's environment, from whoever started it,
  so its `PATH` may lack the shepherd's. A broker whose herd guards
  merges by credentials (D95) first takes on its lead's narrowed ones,
  its `GH_TOKEN`, no ssh agent or credential helper, and the deploy
  key's `insteadOf`. Outside the sandbox the human's keys stay readable,
  so its git's ssh also reads loopherd's ssh config alone and offers only
  the deploy key, whatever `core.sshCommand` or `~/.ssh/config` say. A
  check or after_merge command that runs ssh or reads `~/.ssh` itself
  still could. So the checks, after_merge,
  and the origin calls of `retire --close` and `release` (its fetches,
  `gh pr list` and the `push --delete` of a branch) go out as the
  lead's. It fails to start while they are missing, or while its herd
  file can't be read to tell, or loopherd's ssh config lacks the herd's
  `Host` block. On a credentials herd, `after_merge` and a queue's
  `source` now run with those narrowed credentials too. A broker started
  before this change keeps its starter's environment for `feed` and
  `add` until its lead restarts. The `push --delete` runs the repo's
  pre-push hooks, and the shared `.git` is the lead's to write (D89). A broker
  outlives its feeds, so a feed that fails or panics after marking
  after_merge pending on it notes those members interrupted itself,
  saying the feed failed, rather than leaving them for a later feed, and
  answers with those lines.
- **Three lanes, one request at a time in each.** A broker runs its
  lead's herd changes (`feed`, `add`, `restart`, `retire`, `release`) in
  turn in one lane, so two feeds or adds for a lead never run at once;
  `status` in turn in a second; and everything else (`tell`, `read`,
  `prompt`, `restart --self`, the pane label) in turn in a third, so a
  long feed or a slow status holds up no `tell`. Its main thread only
  reads requests, hands each to its lane and watches the ledger, so it
  notices its lead retired within one poll even mid-op: it then refuses
  each new request at once and each queued one when its lane reaches it,
  starts none, and exits once none is in flight. It reads the ledger
  every round, so a lead that `lead` relaunches under the same name
  before then is served again rather than left without a broker. A quick request may
  reach a member while a herd change acts on it, as two commands run by
  hand could. Before carrying a request out the broker marks it started,
  in `replies/<id>.started`, then checks the request is still there; its
  lock records that it marks. The lead waits a bound per operation, then
  withdraws its request:
  - two minutes for `tell`, `read`, `prompt` and `restart --self`;
  - five minutes for `restart`;
  - twice the broker's git timeout, plus two minutes, for `status`,
    whose queue's `source` and `backlog` each take up to that timeout;
  - eighteen times the broker's git timeout, plus five minutes, for
    `retire` and `release`, whose origin calls each take up to that
    timeout;
  - the ready timeout asked for, plus five minutes, for `add`;
  - four hours for `feed`, which a feed of many slow members can outlast.

  The broker records its git timeout in its lock for these bounds. Having
  withdrawn, the lead looks for the mark: with none, the error says the
  request was not started and is withdrawn, so asking again is safe; with
  one, the broker may have begun it, and the error says to check before
  asking again. Withdrawing first means a broker that hasn't marked it
  never runs it. A broker whose lock doesn't record that it marks, one
  started before this change, gets the second error for every timeout, as
  before; a lead's loopherd from before this change reads such a lock's
  git timeout as unknown and sizes its waits by its own. A label that
  times out says only that the report went out. The broker refuses a
  ready timeout over an hour.
  An operation that fails after printing answers with what it printed,
  then its error, as it would run directly.
- **Failure is loud.** The lead's command checks the broker's lock
  first. With no broker running it fails at once, naming the broker and
  the shepherd's `loopherd revive --name <lead>`, which a sandboxed lead
  can't run itself. It also fails as soon as the broker stops without
  answering. `loopherd doctor` fails for each unretired lead on its own
  herdr with no broker.
- **The lead in a pane** is the one whose sandboxed Claude is an
  ancestor process (D89's `calling_lead`), else the lead the ledger has
  in `$HERDR_PANE_ID` on `$HERDR_SOCKET_PATH`, unretired. Finding it
  asks herdr nothing, and a ledger that can't be read names no lead, so
  the shepherd's own commands don't come to depend on it. Inside the
  sandbox the lead's Claude is out of sight (its own pid namespace), so
  only the ledger's pane can name it; after herdr renames a moved pane,
  that fails too. A command that finds no lead, can't write the ledger
  and so runs in a sandbox is refused before it reaches herdr, `spawn`
  included, rather than run there, naming the shepherd's
  `loopherd revive --name <lead>`: doctor checks only that a broker
  runs, so it doesn't see a moved pane.

Operations routed so far: `tell`, `feed` (with `after_merge`), `add`,
`prompt`, `restart`, `restart --self`, `retire`, `release`, `status`,
`read` and a lead's pane label for its question. `loopherd read <member>`
is new with the broker: `herdr agent read --source recent-unwrapped` for
a member, 40 lines unless `--lines` asks for up to 1000, so a lead needs
no raw herdr call to read a worker's screen; the shepherd's runs
directly, for any member in the ledger. The lead can write the mailboxes
directory, so the broker refuses a symlink, hard link or FIFO at that
label's files, and gives up on a lock held past two seconds. A hook's
clear gives up after those two seconds too, so a set holding the lock
across a slow herdr call can leave a stale label until the next
prompt. The broker refuses a lead's `restart --force`, which the tool hook alone held back before, since a
lead can now write the request itself; a forced restart stays the
human's. `restart --self` restarts only the lead the broker serves, and
the broker starts its waiter, keeping no copy of the waiter's claim and
reaping it. A broker whose binary a reinstall replaced starts the waiter
from `loopherd` on `PATH`, as the watch does. A broker started by an
older loopherd refuses these ops as unknown until it is restarted.

`retire` and `release` no longer run as excluded commands, so a lead's
sandbox excludes none of loopherd's own but the watch (D104). The broker
refuses a lead's `retire --force`, which the tool hook alone held back
before, and `release --drop-branch`, which `release`
refused for a lead already: a forced retire and a dropped branch stay
the human's.

A lead's `report` still writes its mailbox itself, since its sandbox
lets it write `reports/` and a report must not wait behind a long feed
in the broker. The broker labels the lead's pane for a question, from
the lead's own record, so the label needs no herdr socket in the
sandbox; the lead waits 10 seconds for it at most, and a broker that is
busy with another quick request, down or older costs only the label,
with a warning. A lead's
`report --as` naming another member is refused, as a guard against
mistakes rather than a boundary: the lead can write `reports/` anyway.
A worker's report runs as before.
The lead's watch, with its polls, notifications and pane labels, and the
hooks' pane labels stay out of the broker: the lead's watch runs outside
the sandbox instead, an exception to this decision (D104).

## Why

herdr has no auth, scoping or read-only mode, so whoever holds its socket
holds every pane. D89 named the socket as the sandbox's biggest gap: a
hijacked lead could `herdr agent start` a process outside its sandbox, or
prompt and read any pane. Moving every herdr call a lead needs into a
process the lead can't change lets a follow-up card take the lead's
sockets away, which D105 does. A herd whose `[lead]` sets
`unix_sockets = "all"` reopens the herdr socket to its lead, and with it
this whole gap.

One broker per lead, rather than a per-user daemon, the shepherd's watch
or herdr's plugin, keeps each broker's identity fixed at its launch and
its failures to one herd; the human chose it.

## What it still depends on

- **The ledger and the state dir (D97, LH-307).** The broker reads the
  ledger to learn a herd's workers. D97 makes the ledger, and every other
  lead's requests folder, read-only to a sandboxed lead. A hook-only lead
  can still write the whole state dir: it can forge a ledger entry that
  puts any pane's agent in its herd, and drop requests into another
  lead's folder, which that lead's broker answers as that lead.
- **Unsandboxed workers (LH-284).** `tell` and `add` text reaches a
  worker that runs outside any sandbox, so a lead can still have a worker
  do what its own sandbox refuses.
- **The binary.** The broker runs the `loopherd` that `lead` or `revive`
  ran. A lead with `install = true` can replace that binary (D17), and so
  its next broker.
- **Locks and retirement.** Every lead can read the config dir, so a lead
  can hold any lead's broker lock, its own or another's: no broker starts
  for that lead, and doctor reads the held lock as a running broker. A lead
  can also mark another lead retired in the ledger, which stops that
  lead's broker. Both deny service; neither widens anyone's reach.
