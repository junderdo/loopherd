# D51

## Decision

`loopherd release <name>` marks a retired ledger entry released
(`released_at`), and `feed` (and the watch's `claimable`) treats a released
name as free, so its task spawns again once claimable. The new member's
record replaces the released one as the name's entry, and the released
record moves into the new one's `earlier` list (oldest first), so `stats`
still gives that run its own row with its own times; `status`, `revive`
and the rest read only the current run, so the `(released)` marker goes
once the name is fed again. Release is its own command, not a
`retire --refeed` flag: it acts on an entry already retired, often long
after, and retire's job is unchanged.

Release refuses an entry that isn't retired, naming it; a lead, which feed
never spawns; one recorded on another herdr session; and one whose tab may
still be open, naming the command that closes it as `herd remove` does
(D43). It holds the feed lock throughout, so it never clears a worktree a
feed is spawning into. It then clears the
member's checkout so the new member starts from origin's default branch: it
removes the recorded worktree (detached or not) and any leftover worktree at
the path the new member spawns into, deletes the local branch, and deletes
the branch on origin (with a lease on the head it counted). When any of them
hold commits not on the base it refuses unless given `--keep-branch` (leave
them; the new member continues from them, from origin's branch when there's
no local one) or `--drop-branch` (delete them, printing each head sha and
how many commits are on neither the base nor another origin branch).
Whatever the flag, it refuses, changing nothing, when a worktree has
uncommitted or untracked changes, is mid-operation or locked; when the
branch is checked out in the main checkout or a worktree loopherd didn't
make; when a live entry uses the worktree; or when something that isn't a
worktree of the repo is in the way at the spawn path, naming it. With
`--keep-branch` it also refuses a leftover at the spawn path that isn't on
the branch, since the new member couldn't start there. Rerunning release on
a released entry clears and forgets again, so a second run with
`--drop-branch` finishes what `--keep-branch` left.

Release notes `released` in the member's mailbox, `status --all` shows the
entry as `<name> (released)` (and `released` in JSON), and it appends
`released: <name>` to its herd's lead's `watch-<lead>.fired`, which forgets
every key about that member: its own events and its checks' `failing` and
`recovered`. A lead may run it without a switch: it's part of feeding.

This amends D49's note that a retired name is never reused within a herd: a
released one is.

## Why

Feed skips every ledger name, retired or not, so a merged task whose card
is still open isn't spawned again; that protection stays for every entry
not released. A member retired before it finished (a tab closed by
accident, a rescoped card) had no way back but `loopherd add` by hand. An
explicit release keeps the default safe and makes re-feeding one command.
Clearing the branch, locally and on origin, by default gives the new member
a fresh start: a leftover origin branch, or a closed PR on that head, would
otherwise collide with its push, and a leftover worktree at its path would
fail its spawn. Refusing on commits not on the base, even pushed ones, means
work is only dropped when asked for, and then with its sha printed. Without forgetting the watch's keys, a released
name would never be announced claimable again, and a stale `failing` key
would hide the new member's first failure. Keeping the replaced run
inside the entry, rather than in a file of its own, keeps one writer under
the ledger lock and leaves every reader but `stats` unchanged.
