# D121

Amends D98 and D106.

## Decision

A lead's broker follows reinstalls of loopherd by itself.

- **When it looks.** Only while no request is in flight: after it
  answers one, and every second while idle. It resolves `loopherd` on its
  own `PATH`, canonicalized, and compares that file's dev/ino with the
  executable it runs (D119).
- **It follows only its own install.** A broker moves only when that
  `PATH` entry is the path it was started from, as `scripts/install`
  renames over it. One started from another loopherd, such as a dev build
  or a live test's, stays on it, and doctor warns as before.
- **How it moves.** Between requests nothing is in flight, so there is
  nothing to drain: a request still queued stays in `requests/` for the
  new image, as with `broker-restart` (D106), and a long feed never holds
  up the other lanes behind a pending move. It runs `<install> --version`,
  then re-execs it as `loopherd broker <lead>` in the same process. Its
  pid, and so its pid file and any stop naming it, stay the same. Of two
  quick reinstalls the newer wins: the first look after the second
  install, by either image, moves onto it.
- **It keeps its lock.** The lock's descriptor survives the exec, named by
  `LOOPHERD_BROKER_LOCK_FD`. The new broker adopts it only when it is that
  lead's lock file and holds its flock, and sets close-on-exec again at
  once, so nothing it starts holds the lock. The lock is never free, so a
  lead's request never finds no broker.
- **A failed move is noted once.** An install that is missing, can't run,
  fails `--version` or doesn't answer it within 10 seconds leaves the old
  broker serving. It notes the lead's mailbox once, naming the shepherd's
  `loopherd broker-restart <lead>`, and doesn't try that file again until
  the `PATH` binary changes. Doctor's stale-broker warning (D119) still
  flags that broker.
- **Doctor gives a broker a moment.** A broker not yet on the `PATH`
  install gets 3 seconds to move before doctor warns, since
  `scripts/install` runs doctor right after the rename. Doctor run inside a
  lead's broker, as its feed's `after_merge`, reports that broker as
  moving once its request is answered rather than warning.
- **`broker-restart` is for the failure case.** A stop from a restart
  wins over a move.

## Why

Every merge that changed the broker left it on the old binary until the
shepherd ran `broker-restart`, which a lead is refused, so leads asked the
human for it. Only the shepherd, or a lead whose `[lead]` sets
`install = true` through `scripts/install`, replaces the `PATH` binary, and
a lead's sandbox can't write it, so following it grants the lead nothing
`broker-restart` didn't. Re-exec rather than a new process keeps the lock
and pid without a gap clients would have to ride out.

A binary that passes `--version` but then fails as a broker ends the
broker, as a failed `broker-restart` would leave none; doctor fails for it
and `loopherd revive --name <lead>` starts one. So does a downgrade to a
loopherd from before this decision, which doesn't know the handed-over
lock and gives up on it.
