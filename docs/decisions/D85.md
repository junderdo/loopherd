# D85

## Decision

While a lead with `merge = false` and `merge_guard = "hook"` runs, its watch
tells the human of every pull request merged into its repo's default branch,
through `[notify]` (D32) as kind `merged`.

- **Config.** `[lead] merge_guard` names how a lead with `merge` off is kept
  from merging. `hook` (the default) is the PreToolUse hook alone; it is the
  only value for now, and an unknown one fails the herd file. A
  `merge = true` lead gets no alert: its merges are in its reports.
- **Who asks.** The lead's own watch, every minute with its other checks, so
  it runs exactly while the lead runs and needs no shepherd session.
- **What it asks.** `gh repo view` for the default branch, then `gh pr list
  --state merged --base <branch> --search merged:>=<lead's start>` against
  origin's GitHub repo. A failure warns once per streak on the watch's
  stderr and sends nothing.
- **Once per merge.** A send marks `merged <PR URL>` in the lead's
  `<lead>.notified`, as a question marks its time, so a restarted watch, or
  a second one, sends each PR once. The text is `#<number> <URL>`.
- **Kinds.** `merged` joins `kinds`' default; a table that lists its kinds
  sends it only when it lists `merged`.

## Why

A hook-guarded lead runs with the human's GitHub credentials, so a hijacked
lead could get a merge past the hook. The human is the only one who should
merge in such a herd, so a ping per merge lets them spot one they didn't
make. Which identity merged can't be told apart (same credentials), so every
merge pings. The lead's watch is the cheapest place that already runs for
exactly the lead's lifetime and already notifies the human directly (D32's
own-question path); the shepherd's watch may not be running. A later value
of `merge_guard` that keeps the credentials away from the lead can skip the
alert.
