# D53

## Decision

The lead hook stops reading where an alias variable or a heredoc operator
sits, and denies by what a command holds. It supersedes D48's alias-variable
and heredoc-feed rules, and the absolute-path rule for a shell's input in
D17. LH-195 built it.

- **Alias variables.** A `GIT_CONFIG*` or `BASH_ALIASES` name anywhere in a
  simple command's words, quoted or not, redirection targets included, is
  denied as `Switch::Alias` unless the command can only read its words: its
  first word, with no `$` or substitution, is `echo`, `rg`, `grep`, `git`,
  `gh`, `loopherd`, `cat` or `trello` (by file name), `printf` with no word
  starting `-v` or holding a `$` or substitution (which may expand to
  `-v`), or `declare -p`/`typeset -p` on plain names. The name is matched as
  a substring, so `XGIT_CONFIGY` counts too. Anything
  before the program (an assignment, `!`, `{`, `time`, `then`, `do`,
  `command`, `builtin`, `env`, any wrapper) denies, so no builtin position
  has to be parsed. A value counts as much as a name, which closes the
  two-step nameref (`declare -n r; r=BASH_ALIASES`). A script that
  defines a function (`name()` outside a heredoc body that isn't read as a
  script) or holds a word `function`, `enable` or `trap`, quoted or not, has
  no read-only programs, since each may give one of those names a body that
  sets variables (`echo() { export "$@"; }`, the same in a `DEBUG` or
  `RETURN` trap's action).
- **Expansions.** Such a name anywhere in the script's text, heredoc
  bodies included, while a `${`, `$[` or `((` is open is denied, since bash
  may assign it there (`${GIT_CONFIG_COUNT:=1}`, `${a[GIT_CONFIG_COUNT=1]}`,
  `$(( a[0], GIT_CONFIG_COUNT=1 ))`) whatever program runs. Brackets,
  braces and parentheses inside one nest, so an inner `]` doesn't close it;
  one left open runs to the end of the script. A quoted span or escaped
  character inside one is skipped, so it can't close it, and denies when it
  holds the name; a quote left open runs to the end of the script.
- **Heredoc feeds.** A shell reading its input is heredoc-fed only by a word
  the lexer read as a `<<` operator. A `$'…'` now marks its word quoted like
  any other quote, so `$'<<EOF'` is an argument.
- **Relative input.** A relative script operand (after `..`, `~` or a `cd`)
  ending in `stdin` reads the shell's input, and one ending in `fd/<n>` or
  that is all digits reads a descriptor the hook can't place, so it is
  denied whatever feeds it. `source --` and `. --` read the operand after
  the `--`.

The false positives this costs are listed in D29's Limits.

## Why

LH-165's three review rounds each patched the reported positions and
opened their neighbours (`{ read GIT_CONFIG_COUNT; }`, `! read
"BASH_ALIASES[g]"`, `$'<<EOF'`, `bash ../dev/stdin`), because the rules
asked where a word sat in bash's grammar. Asking what a command holds needs
no grammar: a variable set by name is set through the shell's own
builtins, keywords, assignments and expansions, so the rule rests on a
short list of programs that can't. What it misses is a name the command
text never shows: one a `$` builds, or one carried as data into arithmetic,
and a read-only program redefined where the command text doesn't show it:
a function inherited from the lead's shell or defined in a sourced file, a
definition run through `$e` with `e=eval` or `e=enable`, or a wrapper on
`PATH` (D29's Limits). Mentions in the lead's everyday
commands (`rg`, `git log -S`, `loopherd tell`, a PR body) still pass.
