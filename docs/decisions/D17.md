# D17

## Decision

A **lead** is a loopherd-run member that runs one herd's routine loop
unattended: feed, watch, verify PRs with a `reviewer` subagent, send in-scope
gaps back to members, and after-merge steps. Its playbook is
the shepherd's guide plus its lead section, now `loopherd --skill` (D19); the
first herd is `loopherd-cards`. **Herd file:** a `[lead]` table with `prompt`
xor `prompt_file` (templates as in D9, placeholders `{name}`, `{herd}`,
`{worktree}`, `{switches}`), optional `args` (default: the herd's `args`), and
six booleans, all default `false` (refined by D31: an unset one takes
`[lead_defaults]` from `config.toml`): `merge`, `install`, `rebase`, `new_cards`,
`design_escalation`, `blocked_dialogs`. Off means the human does it;
`{switches}` renders one `<switch> on|off` line each. Grilling is always the
human's, with no switch. **Start:** `loopherd lead <herd> [--dry-run] [--
args]` spawns member `lead-<herd>` through spawn, in a detached worktree
`lead-<herd>` at origin's default branch, with ledger `role = "lead"` (absent
means worker) and its herd recorded; it refuses without `[lead]`, while the
herd has a non-retired lead, while a non-retired non-lead entry holds the name
`lead-<herd>`, and for a herd name that can't make a valid member name (at
most 27 of `a-z0-9_-`). Leading again over a retired lead's entry is fine: it
replaces that entry and reuses the worktree if it's still there. `feed`
neither counts the lead toward `max` nor checks or reaps it; `status`,
`--json` (`lead: true`) and `view` list it first in its herd as `<name>
(lead)`. `retire --close` retires it like any member. **Enforcement** (LH-77):
`merge`, `install` and `rebase`, when off, are enforced by a user-level
PreToolUse hook on Bash (`loopherd tool-hook`, installed with the others,
D16), since deny rules in a worktree's `.claude/settings.local.json` may not
load and `--settings` is lost on herdr's resume
([claude-deny-rules.md](../research/claude-deny-rules.md)). Outside herdr (no
`$HERDR_PANE_ID` or `$HERDR_SOCKET_PATH`) it exits 0 without reading stdin or
the ledger. Inside, a command needing no switch exits 0 without reading the
ledger, and otherwise it reads the ledger without `ledger.lock`; a pane
matching no non-retired `role = "lead"` entry on socket and pane prints
nothing. In a lead's pane it binds whichever Claude fired, nested `claude -p`
and subagents included, re-reads the herd file's switches, and denies the call
when the command needs an off switch, printing `{"hookSpecificOutput":
{"hookEventName": "PreToolUse", "permissionDecision": "deny",
"permissionDecisionReason": "<one line naming the switch and the human's
part>"}}` and exiting 0 (it always exits 0; LH-81). A herd file it can't read,
or a lead with no herd recorded, counts every switch as off and denies the
same way (fail closed, leads only); so does a panic in the matcher, caught so
it can't print nothing. It lexes the whole command into simple commands (split
on `;`, `&`, `|`, newlines, parentheses, backticks and `$(`, including
substitutions inside double quotes; quotes and `#` comments removed; see
"What the hook can't read" below), checks every switch a chain needs, skips leading redirections
(`2>/dev/null`, `>file`, `2>&1`, `&>file`), `VAR=x` prefixes and wrappers
(`env`, `sudo`, `timeout`, `xargs`, `nohup`, `ionice`, `taskset`, `flock`,
this repo's `scripts/herdr-dev`, …), reads `function`, `coproc` and `trap`
bodies as commands, recurses into `sh`/`bash -c
[--]`, `flock -c` and `eval` scripts, and matches the program by file name: it leans
toward denying over parsing flags: `merge` is every `gh … pr merge` (`--help`
included), every `curl` or `wget` naming a `pulls/<n>/merge` path, and `gh
api` on such a path unless its args hold no `-X`/`--method` and no
`-f`/`-F`/`--field`/`--raw-field`/`--input` in any form (so a merged-check
goes through `gh api` with no flags, or `gh pr view --json state`); `install`
is any `…/scripts/install` (also as `sh`/`bash`'s script), `loopherd
install-hook`, or any `cargo` command with `install-hook` among its args;
`rebase` is every `git … rebase` (`--abort` and `--continue` included: a lead
asks the human to run those), `git pull --rebase`, or `git push` with
`--force`, `--force-with-lease`, a short `-f`, a `+` refspec or `--mirror`.
No switch allows `loopherd pause` or `loopherd resume` (D23): every `loopherd
pause|resume` (`--help` included) is denied, and so is any `cargo run` or
`cargo r` (after a `+toolchain` and cargo's global options) with `pause` or
`resume` among its later args, `--` or not; other cargo subcommands pass, so
`cargo test pause` and `cargo nextest run -- pause` stay test filters.
The other three switches are prompt-only. A guardrail, not a sandbox. Known
limits: `/fork` and `/background` copies under the shared `claude daemon run`
supervisor can inherit another pane's `HERDR_PANE_ID` (D16), so they may be
bound to a lead's switches or freed from them wrongly; and variables holding
the command, an alias the Bash tool's shell may load from the human's
profile, a GraphQL
`mergePullRequest`, `cd scripts && ./install`, a `pull.rebase` config, and
scripts that run these commands internally all pass. **Wake:** the lead keeps
`loopherd watch --timeout 3600` as a background task. Merges and newly
claimable cards produce no worker event, so a lead's watch checks for them
itself every 60s (fixed; LH-87). A template may set `merged`, a command
parsed and placeholder-checked like `done` and run in the herd's repo, exit 0
meaning merged. The watch prints `<member> merged` for a non-retired worker of
its herd whose `merged` exits 0 while its `done` exits 1 or is absent, and
`<name> claimable` for each member feed's plan would spawn (a task the
`source` lists with no member, while a slot is free under `max`, counting
members whose `done` passes as freed), `<name>` being the name feed would
give it. A herd with no `[queue]` still gets `merged`. A check or `source`
that fails is no event; a herd file the checks can't load is no event and
one warning on stderr until it loads again. One round runs each worker's
`done` once, and stops running commands 60s after it starts (each command
also within `LOOPHERD_GIT_TIMEOUT`, which only a lead's watch reads), so a
round can overrun `--timeout` by at most that. `claimable` is dropped for the
round while a feed holds `feed.lock`, since feed records a member only once
it's spawned; the watch probes the lock once, after the source runs, and
`feed` and a capped `add` wait up to 1s for the lock so the probe never fails
them. These
lines come after stop lines and before `blocked`/`gone`, and end the watch
like any wake. Each fires once per key (member, or would-be name), appended
on print to `watch-<lead>.fired` beside the lock, so a re-armed watch stays
quiet on an unchanged condition. The file's first line names the lead's
spawn time, so a re-created lead of the same name starts with none fired. A
claimable name the lead doesn't feed is not announced again; only the
heartbeat's `feed --dry-run` shows it. The shepherd's watch runs no such checks. On `merged`
the lead runs the after-merge steps, on `claimable` it feeds, and exit 2 is
still a heartbeat on which it checks Review cards' PRs and runs `feed
--dry-run`. The human may merge from the
lead's pane or the shepherd's. **Readers** (LH-78): a watch run from a lead's
pane (matched as `loopherd report` matches) is that lead's: it reads only its
herd's non-lead members, and naming another herd is an error. Any other watch
is the shepherd's: it reads leads, every member of a herd with no non-retired
lead (a `gone` lead still owns its herd), and members in no herd; naming a led
herd narrows it to that lead. Each event has one reader. Locks are per reader,
`watch.lock` for the shepherd and `watch-<lead>.lock` for a lead, so one watch
per reader at a time and the two run concurrently; wake rules, lines and the
watch cursor are otherwise D16's. A pane that matches a lead's entry on pane
but not socket is the shepherd's watch (D22). A lead's watch checks on each
poll, before reading any mailbox, that its lead is still its herd's
non-retired lead, and ends with an error otherwise, leaving the cursors for
the shepherd. Known limit: when a herd gains a lead while the shepherd's watch
has printed a wake but not yet saved the cursor, the lead's watch can print
the same event once more. **Restart** (LH-79): revive prompts each non-retired
lead that is alive (usually herdr resumed it itself) or that revive just
started, and that isn't `blocked` (D10), whenever its watch isn't running.
Running means a watch holds `watch-<lead>.lock`, which revive tries
non-blocking, the same way watch takes it. The prompt is a fixed text: you
were revived, run `loopherd status` and `loopherd reports --all --tail 40`,
then read only the skill's Lead section (`loopherd --skill --section lead`,
D19) and re-arm your watch. A lead whose lock is held is left
alone and its line says `(watch running)`. This is the one exception to D8's
no-prompt rule, since a lead without a watch has nothing to wake it. Workers
are never prompted; `--dry-run` shows which leads it would prompt; a refused
prompt fails the run without undoing the resume. **Escalation:** the lead runs
`loopherd report --kind question` and ends its turn; the shepherd's watch sees
it and relays. Desktop notifications later. **Lifetime:** long-lived until
retired, relying on auto-compaction; it re-reads `loopherd status` and
`loopherd reports --all` on each wake, and its state lives on the board,
ledger and mailbox. Built as LH-76 and LH-78; first live run LH-80.

Aliases are denied whatever the switches (D48), since one can hide any
gated command: `gh alias set` or `import`; a git `-c` or `--config-env`
key, or a `git config` argument, starting `alias.`, `include.` or
`includeIf.` (any case); a `GIT_CONFIG*` or `BASH_ALIASES` name in an
assignment, after `printf -v`, as a nameref's target, or as an argument of a
builtin that sets names (`read`, `export`, `declare`, `unset`, `for` and the
like), while a mention elsewhere (`rg GIT_CONFIG`) passes; and an `alias` builtin whose arguments hold a `=`, a `$` or
a substitution.

**What the hook can't read.** The lexer follows bash only so far, so the
hook fails closed: it denies, whatever the switches, any command holding

1. a backslash-newline, anywhere;
2. a `$'…'` left open or holding a `\c` escape (the other escapes decode as
   bash does, a NUL ending the text), or a `$"…"`, which bash may translate
   through a message catalog;
3. a `${…}` or `$[…]` holding anything that could hide its end or a
   heredoc: a parenthesis, `<`, `>`, `;`, `&`, `|`, a quote, a backslash, a
   backtick or whitespace, or one left open;
4. a `` \` `` in a backtick substitution, which is how backticks nest (the
   hook undoes `\\` and `\$` there before reading it, and `\"` inside double
   quotes, as bash does);
5. a quote, backtick or `$(` left open at the end of the script, or at the
   end of a heredoc's body read as a script of its own (below), delimiter
   line included;
6. a `<<` inside a top-level `((…))` or a `name[…]` subscript, where bash
   reads a shift and the hook would read a heredoc, and a space, tab,
   newline, `;`, `&`, `|` or parenthesis inside an assignment's `name[…]`
   or an array's `[…]` (outside `((…))`), which bash keeps open to its `]`;
7. a heredoc whose terminator line never comes, one inside a `<(…)` or
   `>(…)`, or one whose start line runs on into a `<(…)` or `((…))`
   spanning a newline;
8. a program word holding an unquoted glob (`*`, `?`, `[…]`) or brace
   expansion (`{gh,}`), which bash may expand to a gated command, or an
   extglob (`@(…)`, `+(…)`, `!(…)`) anywhere; a case pattern, a `name=(…)`
   array and `((…))` arithmetic aren't program words, and a `((` that turns
   out to open nested subshells is denied;
9. a brace expansion (`{merge,}`, `{e..e}`) in the arguments of `gh`,
   `git`, `loopherd`, `cargo`, `curl`, `wget` or `install`;

and a `$(…)` whose end it may place differently from bash: one holding a
`case … in`, a heredoc left open at the `)` or at the end of the script, a
heredoc line that starts with the delimiter and holds a `)`, a delimiter
holding a `$`, a backtick, or a backslash in double quotes, a `((` closed by a lone `)`, or a heredoc
whose start line runs on through a nested `$(…)` spanning a newline.
`$((…<<…))` is read as arithmetic and passes. A shell, `source` or `.`
whose script comes from its input is denied too: one with no script operand
(so `<(…)`, `<<<`, `< file` or a pipe feeds it), with `-s`, or naming `-`,
`/dev/stdin`, `/dev/fd/*` or `/proc/*/fd/*` (after `//`, `/./` and `/../`
are folded). It passes only when the last redirection of the descriptor it
reads is an unquoted `<<` heredoc operator (a quoted `"<<EOF"` is an argument), whose body is judged instead; a later `<<<`, `<`
or `<&` on that descriptor denies it.

**Heredoc bodies are data** (LH-138): the hook reads past a body to its
terminator line and judges what follows, and a body that only goes to a
file or a command's input passes whatever prose it holds. An unquoted
delimiter's body still runs its `$(…)` and backtick substitutions, so
those are judged. The check fails closed: a body is read as a script of
its own, with rule 5, unless every command in the script, its
substitutions included, runs a known sink (`cat`, `tee`, `echo`,
`gh`, `git`, `loopherd`, `mkdir`, `ls`, `rm`, `mv`, `cp`, `touch`, `wc`,
`head`, `tail`, `grep`, `diff`, `jq`, `true`, `false`, `test`, `cd`) by
its bare name, or nothing, and sets only lower-case
variables other than zsh's `path`, `cdpath`, `fpath` and `module_path`. So
a wrapper, a path, a `$` or a substitution in the program word, an
upper-case assignment (`PATH=`, `PAGER=`) or one of those zsh arrays
reads the bodies. A
`bash -c` or `eval` script always reads its heredoc bodies as scripts.

Like bash, the hook breaks words only on spaces and tabs, so a `\r` or
other whitespace is part of a word: `<<EOF\r` ends at `EOF\r`, and a `#`
after a `\r` starts no comment. A redirection glued to a word ends it
(`gh>/dev/null` runs `gh`), and one among the arguments is taken out of
them, its target too when it is bare: the word after `>`, `2>`, `>&` or
`<&` is the target, so `gh >& x pr merge 1` is a merge. A quoted `'case'` is no keyword. A body is judged right after its own
command, so a later `CARGO_ALIAS_*` can't hide the alias it saw, and a
body that assigns one makes every cargo alias opaque, since it may run in
this shell or a child.

These forms are denied for what they are, not what they do. A lead hits
them as:

| Denied | Rewrite |
|---|---|
| a heredoc body with one apostrophe, in a script that runs more than the sinks above | write the file in a Bash call of its own, or `--body-file` / `-F file` |
| `gh pr create \` line continuations | one line, or a file |
| `${x:-a default}` | a default without whitespace, or set it first |
| `echo $'\cA'`, `echo $"hi"` | `printf '\001'`, `echo "hi"` |
| `{gh,} pr view`, `/usr/bin/g? …`, `gh pr {view,diff} 1` | the program's name and subcommand spelled out |
| `git add src/{a,b}.rs`, `cargo test --test {a,b}` | each path or name spelled out |

A `` \` `` in double-quoted text outside a backtick substitution is a
literal backtick to both bash and the hook, and passes. Indirection still
gets past (D29's Limits).

**First live run** (LH-80, 2026-11-02, every switch off): the lead ran LH-82
(PR #75) end to end. It fed the card and had a `reviewer` verify the PR. It
sent an in-scope fix back to the worker, then asked the human to merge. After
the merge it moved the card to Done, fed to retire and close the worker, and
re-detached its checkout at `origin/main`. Its out-of-scope gaps went to the
human as a question, since `new_cards` is off. The hook denied `gh pr merge
--help` with the `merge` switch's line, and the lead didn't retry. The design
didn't change. Follow-ups:
- LH-83: the merge question should carry a ready-to-paste merge line.
- LH-84: an idle heartbeat costs a turn every 10 minutes and restates open
  questions.
- LH-85: new decisions collide on the next D number.
- LH-86: a test that breaks on a `..` target dir.

Two things to know:
- Claude Code labels the hook's deny "hook error" and a heartbeat's exit 2
  "failed"; both are its wording.
- A lead whose first feed ran before its card was filed picks the card up on
  a later feed.

## Why

The shepherd's routine loop (feed, watch, verify, clean up) needs no human for
most of a card's life; a lead runs it unattended while the human keeps the
decisions the switches leave off. Grilled with the human 2026-11-02, "lead
member".
