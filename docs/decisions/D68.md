# D68

## Decision

A manual `loopherd revive` touches only members recorded on the herdr
server it reaches. An entry whose recorded socket differs from that
server's is skipped with `skipped <name>: recorded on <socket>`, and
`--name` and `--dry-run` skip it the same way. An entry with no recorded
socket is revived as before and records the reached server's socket. When
herdr can't say which socket it serves, nothing is skipped, as before. A
skip, like any other, exits 0.

Revive never rewrites a recorded socket: it fills one only where the
entry has none, read fresh under the ledger lock. If the entry gained
another server's socket since revive read the ledger, the entry fails
with `ledger: recorded on <socket> since revive read the ledger` and
nothing is saved, rather than pairing this server's pane with that
server's socket.

This narrows D64's "a manual `revive` still walks every entry". The
startup hook is unchanged: it still leaves entries with no recorded
socket alone.

LH-252 settled it.

## Why

The live and dev sessions share one ledger. Unfiltered, a manual revive in
one session started the other's members wherever a workspace label
matched, then rewrote their recorded socket to its own server, so stops
and reports no longer matched the member's real pane. `scripts/herdr-dev`'s
label-collision check made that unlikely but didn't prevent it.

An entry with no socket predates socket recording, or was made outside
herdr; skipping it would strand it with no command to bring it back, so a
manual revive keeps resuming it. A herdr that names no socket is one
`herdr status server` couldn't answer for, and the settle step's agent
listing normally fails first; skipping there would only add a way for a
revive to do nothing. The startup hook runs unattended, so it
keeps leaving those entries to a human. Filling a missing socket but never
replacing one keeps a concurrent write from another server intact.
