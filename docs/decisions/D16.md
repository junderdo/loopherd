# D16

## Decision

**Stops land in the mailbox.** `scripts/install` builds, copies the binary to
`~/.local/bin/loopherd` through a temp file and a rename, then runs `loopherd
install-hook`. That merges a Stop, StopFailure and SessionStart hook into
`~/.claude/settings.json` in Rust: idempotent (it finds its own entry by
command and updates it), with a timestamped backup beside the file first;
malformed or non-object JSON is refused unchanged. The command is `'<abs
path>/loopherd' stop-hook || true` with `"timeout": 10`, since a Stop hook
exiting 2 keeps Claude from stopping in every session. A fourth hook,
PreToolUse with matcher `Bash`, runs `'<abs path>/loopherd' tool-hook || true`
with `"timeout": 5` and no `onFailure: "block"`; it blocks by printing a deny
decision, not by exit 2, so a missing, crashing or older loopherd (clap's
usage error for an unknown subcommand exits 2) never blocks every session
(LH-81); it enforces a lead's switches (D17) and `watch` doesn't need it.
`install-hook --remove` takes them all out; both take `--settings <file>` for
tests. **Matching:** the ledger records `HERDR_SOCKET_PATH` at spawn and
revive; the hook and `loopherd report` match a non-retired entry on socket and
pane, or on pane alone for entries without a socket. Outside herdr or with no
match the hook records nothing and exits 0. **Session check** (LH-70): a pane
identifies a pane, not a session (a nested `claude -p` inherits
`HERDR_PANE_ID` and runs the user's hooks, and panes get reused). The stop
hook compares its input's `session_id` with the ledger entry's: equal, or
either missing, records the stop (with `session`); different records nothing.
It never asks herdr, since herdr's own SessionStart hook reports a nested
session as the pane's current one, so adopting from herdr would drop the
member's real stops. A second hook, `loopherd session-hook || true` on
SessionStart (installed and removed by `install-hook` with the others; `watch`
needs all three), follows the member's session changes. It matches on an exact
socket (not the socketless pane-only fallback) and refuses a session another
non-retired entry already owns. **Process rule** (LH-71): a session is not a
member's identity (`/branch` changes it in the same process; a nested `claude
-p --resume` shares it from another), so the member is identified by its own
Claude process. The ledger's optional `process` is `{pid, start}`, the PID
plus its `/proc/<pid>/stat` start time, so a reused PID doesn't pass; hooks
read `$CLAUDE_PID`. A hook **claims** the process, writing only that (and the
session if the entry had none) under the ledger lock, when the entry has no
live process (none, or the start time differs), the pane matched on an exact
socket, the hook's session equals the entry's or the entry has none, and
`$CLAUDE_PID` is the pane's top-level Claude: walking up from its parent
reaches the herdr server (exe named `herdr`, with or without a trailing `
(deleted)`) without meeting another Claude: a process whose `/proc/<pid>/exe`
is under `…/claude/versions/` (native install), or whose exe file name starts
with `node` and whose `/proc/<pid>/cmdline` either has an argument containing
`@anthropic-ai/claude-code/` or has a first non-option argument (the script)
that resolves, relative to `/proc/<pid>/cwd` with symlinks followed, to a path
containing it (npm install, LH-73). The resolution is needed because npm's
`bin/claude` is a symlink to the package's `cli.js` with a `node` shebang, and
a shebang launch puts the invoked path, not the symlink's target, in argv. A
walk that ends any other way (init, a vanished process, 64 steps) is not
top-level, so a nested `nohup claude -p &` reparented to init never claims.
`$CLAUDE_PID` counts only if it is an ancestor of the hook process; otherwise
it is treated as missing. Revive clears `process` when it starts a new Claude
(LH-72), so the resumed Claude can claim even while the old one lingers; a
member revive finds alive keeps it. With a live process recorded, session-hook
adopts a session from that process whatever the source (`clear`, `resume`,
`fork`, `startup`) and ignores any other process; stop-hook files stops from
it (updating a differing session) and drops other processes' with a stderr
line. **A `$CLAUDE_PID` that is not the pane's top-level Claude is dropped by
both hooks** (a stderr line, nothing recorded, no session fallback). With none
recorded and a top-level `$CLAUDE_PID` whose claim fails for another reason
(no exact socket, a different session), session-hook adopts only `clear` and
`resume`, and stop-hook uses the session check. A stop from the member's
process is filed first and the ledger updated best-effort after, and a session
another live entry owns is not followed. No `$CLAUDE_PID` or no `/proc`: never
claim, the LH-70 rules. An unclaimed member that runs `/clear` before its
first stop is not followed (the stderr line and a revive cover it), and
`/background` ends the member's process, so it reads `gone` and reviving is
the human's call. Probe facts (Claude Code 2.1.316): `$CLAUDE_PID` is the
firing Claude (`$PPID` is `sh -c`); `/branch` is the same process with
SessionStart `fork`, a new session id and no parent id; `claude -p
--resume`/`--continue` is source `resume` with the same session id in a
separate process under the member's Claude; `/fork` and `/background` copies
run under a shared `claude daemon run` supervisor and can inherit another
pane's `HERDR_PANE_ID`; background-session Claude processes have comm
`<version>` rather than `claude`, but `/proc/<pid>/exe` is always under
`~/.local/share/claude/versions/`; `CLAUDECODE` and
`CLAUDE_CODE_CHILD_SESSION` can't detect nesting, since a herdr server started
from a Claude Bash tool passes them to every member. Interactive ancestry is
hook sh → claude → pane shell → herdr server. **Ledger lock:** every ledger
writer (spawn, revive, prompt, retire, session-hook, stop-hook) takes
`ledger.lock`. Revive, prompt, retire and session-hook re-read the entry under
it and change only their own fields, so none saves a stale copy over
another's; spawn records a whole new entry. **Entries:** kind `stop`, written
only by the hook: `{at, background: {shells, subagents, other} | "unknown",
crons: N | "unknown", error?, session?}`; a missing array is unknown, not
empty, and a StopFailure is a `stop` with `error`. `spawn` and `revive` append
a `start` boundary. One mailbox file per member, two cursors: `reports` reads
done/question/note and shows `stop`/`start` only with `--all`, which prints
the whole timeline in time order; a separate watch cursor reads `stop`.
**Watch** (LH-69): wakes come from unread `stop` entries, only on a change of
state: not paused → paused (anything in flight or unknown), finished (nothing
in flight), or failed (`error`); a paused stop after a paused one is quiet. A
finish reads `no report` unless a `done` or `question` lies between it and the
previous finish or `start`, judged from mailbox history, so it holds across
watch runs; a failed stop doesn't end that stretch. herdr wakes only for
`blocked` and `gone`, on change; `gone` takes two polls in a row with no agent
in the member's pane, so a herdr restart's resume doesn't fire it. Cursors
move only after the wake is printed. One watch per reader at a time (D17's
per-reader locks; the shepherd's is `watch.lock`, naming its holder's PID),
and it refuses to start without the hook installed. Built as LH-68 then LH-69.

## Why

Per-member `--settings` hooks with persisted marks (PR #63, LH-65) kept losing
or inventing wakes, and herdr's auto-resume drops `--settings` (LH-67). A
user-level hook survives resume, and the socket keeps the dev session's
members apart from the live one's. Grilled with the human 2026-11-02 ("mailbox
redesign"); research in
[claude-background-shells.md](../research/claude-background-shells.md).
