# D177

## Decision

The model window table lists every known model (LH-472). Amends D137.

- **Explicit.** The table names each (family, version) pair it knows, from
  the models overview: Opus 4.7, 4.8, 5 and 5.5, Sonnet 5 and 5.5, Haiku
  5.5, and Fable and Mythos 5, 5.1 and 5.2 have 1M; Opus 4, 4.1, 4.5 and
  4.6, Sonnet 4, 4.5 and 4.6, and Haiku 4.5 have 200K. Any other id,
  including a newer version of a known family, is unknown: 200K and the
  once-per-session note.
- **Per-model override.** `[context_windows]` in config.toml maps a model id
  to its window (`claude-opus-4-6 = 1000000`), set with `loopherd config
  set context_windows.<model> <tokens>`. It beats `context_window`, which
  still applies to every model, and the table. Each entry takes the
  10000-token minimum.
- **Note.** The unknown-model note names `config set
  context_windows.<model>`, not `context_window`.
- **Doctor.** A window from the override shows as `from config.toml's
  context_windows.<model>`.

## Why

D137's rule gave every Opus, Sonnet, Haiku and Fable version from 4.7 on a
1M window, so a future model with a smaller one would be sized wrong and
never noted; the safe failure is a 200K guess and a note. The rule also
left out Mythos, so its 1M sessions ran at 160K with a note in every
session. That note pointed at `context_window`, which sets every session on
the machine, so following its advice for one 1M model pushed a 200K Haiku
worker past its real window. A per-model key fixes the one model without
touching the rest. Opus and Sonnet 4.6 stay at 200K: Claude Code gives them
1M only through their `[1m]` variant, which the transcript doesn't record.
