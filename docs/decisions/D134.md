# D134

## Decision

`revive --startup` now runs whether or not `[herdr_plugin]
revive_on_startup` is set. With it off, the run only starts a broker for
each alive, unretired lead recorded on `HERDR_SOCKET_PATH` that has none.
It resumes no member, prompts no lead and leaves no note in any mailbox.
It prints that the full revive is off and names the key. An entry on that
socket that is neither alive nor retired reads `skipped <name>: revive on
startup is off`. The socket
rules are D64's and D68's: it refuses when `HERDR_SOCKET_PATH` is unset,
touches only entries recorded on that socket, and holds `revive.lock`.
With the key on, nothing changes.

`loopherd setup` asks for the key on a terminal while it is unset, after
the lead defaults and the handoff limits. The question says brokers start
regardless, and Enter writes `false`, so the choice is recorded and not
asked again. `--revive-on-startup [true|false]` sets the key without
asking, or asks again when given alone, and `scripts/install` passes the
flag through. `loopherd config get|set|unset herdr_plugin.revive_on_startup`
reads and edits it.

This amends D64's "prints that it is off and exits 0" when the key is
unset. LH-385 settled it, and LH-368's `<lead> no broker` watch line stays
as the backstop.

## Why

On 2026-11-21 WSL shut down overnight. herdr restored the lead's pane on
boot, but with the key unset the startup revive exited at once and no
broker started. The sandboxed lead couldn't even report until the shepherd
ran `loopherd broker-restart` by hand. D64 keeps the full revive opt-in
because it resumes Claude sessions and prompts leads nobody asked for at
that moment. Starting a broker for a lead that is already alive does
neither and costs nothing, so it doesn't need the opt-in. Asking in setup
means the human turns the full revive on or leaves it off knowingly, not
by default.
