# D83

## Decision

A lead is contained against both an honest-but-mistaken lead and an
adversarial or prompt-injected one. The hook only has to stop honest
mistakes; the sandbox and credentials do the real containment. Leads only:
workers are LH-284.

- **Files and installs: the sandbox.** Each lead's Claude runs in the
  Claude Code sandbox, started with a `--settings` file loopherd writes
  from its switches and keeps outside the lead's working directory. It
  denies writes to herd files, `config.toml` and `~/.claude`, allows the
  lead's worktree and loopherd's state dir, and adds the install paths only
  when `install = true`. `allowUnsandboxedCommands: false` makes the
  repo's loosening keys void, and `failIfUnavailable` fails closed. The
  file tools run outside the sandbox, so `Read(...)`/`Edit(...)` deny rules
  cover them, and every lead is kept from reading the human's GitHub
  credentials.
- **`[lead] sandbox = "require" | "prefer"`**, default `require`: a lead
  whose sandbox can't start isn't started. `prefer` starts it hook-only
  with a ledger warning; doctor names such herds.
- **Merging and force-pushing.** Token permissions can't separate push
  from merge, so:
  - `merge = true`: the lead keeps the human's credentials and merges as
    it does now; its reports are the record.
  - `merge = false`: `[lead] merge_guard = "credentials" | "hook"`,
    default `hook`. `init` asks, and doctor warns while a `merge = false`
    herd runs on `hook`.
  - `credentials`: a write deploy key for the lead's git (push and delete
    feature branches), a fine-grained PAT with Pull requests: write and
    Contents: read for its gh, a ruleset on `main` (Restrict updates and
    deletions; Repository admin bypasses for pull requests only), and a
    ruleset on all branches blocking force pushes, with deploy keys on its
    bypass list only when `rebase = true`. Doctor flags switches that
    disagree with the repo's rulesets, including two herds on one repo.
  - `hook`: the lead holds the human's credentials, so merging and
    force-pushing are contained only against an honest lead. While such a
    lead runs, the human is notified of every merge to the default branch.
- **The hook** shrinks to plain forms (`gh pr merge`, merge calls through
  `gh api`, force-pushes, rebases, `scripts/install`), each denied with a
  message naming who does it. Indirection (heredoc bodies, `eval`,
  `bash -c`, variables) is no longer inspected. D29's Limits become
  accepted; this supersedes the hand lexer of D48 and D53 where they
  conflict. LH-193 is superseded.
- **Prompt-only switches** (`new_cards`, `design_escalation`,
  `blocked_dialogs`) stay prompt-only.
- **Unverified until LH-279:** that GraphQL merges and `--auto` fail with
  the PR-only token, that rulesets stop deploy-key pushes, that the owner
  still merges in the UI, and the sandbox's socket, seccomp and network
  behaviour on WSL2. If the GitHub checks fail, `credentials` is dropped
  and `merge = false` herds run on `hook`.

## Why

- **Parsing can't contain a hostile lead.** About 40 commits in a month
  closed hook bypasses one at a time, D29 still lists about 15 groups, and
  the hook never covered Write/Edit. The sandbox's write denies reach child
  processes, which is what the bypasses exploit.
- **The sandbox can't stop a merge.** Its network filter is per host, and
  api.github.com is needed. Only the credential decides, and GitHub can't
  deny merge to a token that can push, so pushes move to a deploy key and
  the PAT drops Contents write.
- **No second identity.** A machine user or a GitHub App would let a
  ruleset stop the lead, but the human rejected both for their setup and
  token-minting cost. The split credentials stay on the human's account,
  and the PAT can be non-expiring.
- **`hook` is the default** because the PAT is a manual web-UI step per
  repo, so a fail-closed default would stall every new `merge = false`
  herd. Asking at `init` and a standing doctor warning keep the gap
  deliberate. The sandbox, which loopherd sets up itself, fails closed.
- **Merge alerts only for `hook`.** Under `merge = true` merges are
  expected and already reported. In a `merge = false` herd the human is the
  only one who should merge, so a ping per merge is cheap and recognisable.
  The lead and the human share an identity, so the alert can't tell whose
  merge it was.
