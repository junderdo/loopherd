# D64

## Decision

The herdr plugin declares one `[[startup]]` hook,
`sh loopherd.sh revive --startup`, so its `min_herdr_version` rises to
0.7.5, the release that added startup hooks.

`revive --startup` is opt-in: it prints that it is off and exits 0 unless
`config.toml` sets `[herdr_plugin] revive_on_startup = true`, a key
`loopherd herds` validates. On, it revives only ledger entries whose
recorded socket is `HERDR_SOCKET_PATH`, which herdr gives the hook, so the
`loopherd-dev` server's startup never touches the live session's members,
and the other way round; an entry with no recorded socket is left alone.
It refuses when `HERDR_SOCKET_PATH` is unset rather than ask the herdr CLI,
which outside a hook answers for whichever server it reaches. A manual
`revive` still walks every entry. herdr's docs promise only that a
startup hook's completion reaches the plugin command log, so it copies each lead's line into that lead's mailbox as a
`note` unless the lead's watch is running: leads it started, prompted,
failed, or skipped for a subagent's view all reach the shepherd's next
watch. A dry run writes no notes.

herdr runs startup hooks on a live handoff too, where every pane process
survives. Revive can't tell that from a restart, so a lead between watches
gets the re-arm prompt; its note makes that visible.

Every revive, startup or manual, holds `revive.lock` in the reports dir for
its whole run. A second says on stderr that it is waiting, then finds what
the first started alive, so nothing is resumed twice; it gives up after 10
minutes, longer than a revive's settle wait and starts take.

The card's live test (restart the dev server and see its lead revived) is
a test against the herdr fake instead: plugins are global to the user
(D62), so linking the plugin into the dev server's herdr would register it
in the human's live one too.

LH-225 settled it.

## Why

A revive that runs by itself prompts leads and starts Claude sessions
nobody asked for at that moment, so it stays off until the human turns it
on. Filtering by socket is what keeps the dev session's restarts away from
the live herd, since both share one ledger. Waiting on a lock, rather than
skipping when another revive runs, keeps a manual `revive` meaningful:
it still reports every member, after the startup one finishes.
