# D40

## Decision

`loopherd init` for a tracker it has no snippets for (D36's `other`: `--tracker
other`, or a doc not titled GitHub or Local Markdown) no longer assumes
GitHub, as built in LH-137:

- When origin is missing or isn't GitHub and `--repo` isn't given, the herd has
  no GitHub, as a local-markdown herd can (D39): init makes no gh call, needs
  no `--repo` or `--gh-account` (and refuses the latter), and writes no
  `merged`, warning that `after_merge` never runs. On a terminal, Enter at the
  GitHub question means none. With a GitHub origin, `merged` stays the GitHub
  PR check. Unlike a local-markdown herd, an origin isn't required.
- Without GitHub, the default branch comes from git without asking any
  remote: the local `origin/HEAD` when it's set, else the checked-out branch,
  with a warning naming `git remote set-head`. `--diff` reads the branch the
  herd file recorded before falling back to the checked-out one, so switching
  branches isn't drift. A detached HEAD with no `origin/HEAD` is an error
  naming both ways to fix it; on a terminal, init asks instead. With a GitHub
  origin the branch still comes from GitHub.
- The worker prompt's hand-in step follows `merged`: with a GitHub origin it
  asks for a pull request into the default branch, which the GitHub PR check
  and the lead's PR wording rely on; without one it says to open none.
- Whatever origin is, the herd names no GitHub issue, gh command or account in
  its header, issue template, lead prompt or `docs/agents/loopherd.md`. `source` stays empty, `done` is
  left out under a comment, and the worker prompt's tracker steps (read,
  claim, hand in, ask) and the lead's line on how a task closes are marked
  `(fill in)`; each placeholder says `Fill in from
  docs/agents/issue-tracker.md`. The printed next steps name every one: the
  herd file's `source`, `done` and prompt steps, the lead prompt's line, and
  `docs/agents/loopherd.md`'s sections, plus adding an origin when there is
  none.
- For every tracker, a `ready-for-agent` label that the built-in sources also
  read as a branch type (`bug`, `documentation`, any case) or a skill
  (`skill:…`) is refused before any gh call or write, naming the clash.

## Why

A tracker init can't drive gains nothing from GitHub, so demanding a GitHub
origin and an account blocked repos on GitLab or with no remote at all, and
GitHub commands in the placeholders read as working steps that would act on
the wrong tracker. Reading `origin/HEAD` locally avoids a network call to a
remote init can't otherwise use; members still need an origin to branch from,
so the printed steps tell the human to add one. A ready label that is
also a type or skill label would give every claimable issue that type or
skill, so it is refused rather than quietly misrouting work.
