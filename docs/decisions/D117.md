# D117

## Decision

Amends D98 (LH-333). A lead's broker keeps its lanes and lock honest:

- **Each lane holds at most 8 requests waiting** behind the one it runs.
  A request past that is answered at dispatch, refused as busy, so a lead
  that floods a lane holds no unbounded queue of read requests and open
  folders in the broker.
- **The lock's record is cleared on the way out**, and only a broker
  serving holds one. A held lock with an empty record is a broker exiting,
  so `broker::start` waits up to 5s for it to let go, then starts one: `lead`
  relaunching a just-retired name always ends with a broker running. An
  older broker after this one inherits no `marks` line, so its lead never
  calls a running request "not started".
- **Retirement is read fresh per request**, at dispatch and again when a
  lane takes it up, not once a round. A request written after a retirement
  is refused; one written after a relaunch is served. That holds in the
  final scan too: a request a relaunch let through is left for the broker
  the relaunch starts, not refused.
- **A broker exiting idle on retirement answers what is still waiting**
  "is retired", rather than leaving it to time out.

## Why

- **Refusing beats waiting.** A lead that queues past eight herd changes
  is better told "ask again later" at once than kept waiting hours behind a
  feed.
- **Clearing, not a per-start token.** The lead's sandbox has its own pid
  namespace, so it can't check a pid token against a live process; the
  record itself, cleared before the lock is let go, is what it can read. A
  broker killed outright still leaves its record; the next broker of this
  version rewrites it.
- **The exit re-reads the ledger after clearing**, so a relaunch that read
  the record before the clear finds the broker serving on, and one that read
  it after waits for the lock.
