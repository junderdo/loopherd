# D63

## Decision

`loopherd doctor [<herd>] [--trackers] [--verbose] [--json] [--settings
<file>]` reports whether this machine's loopherd setup is sound. It only
reads, and names the command that fixes each problem.

- **Who runs it.** The human after an install or upgrade, the shepherd at
  the start of each session (relaying any failure), and `scripts/install`
  and the release `install.sh` as their last step, where a doctor failure
  is printed but leaves the installer's exit code alone. Leads don't run
  it; the tool hook allows it all the same, as it gates nothing read-only.
- **It never fixes.** Each finding names its fix (`install-hook`, `setup`,
  `revive`, `retire`, `herd set` …) rather than applying it.
- **Shared checks.** It calls the checks `loopherd herds` runs (herd files,
  `[notify]`, the prompt hook), and `herds` keeps them.
- **Output.** Only problems, each with its fix, then `doctor: <n> ok, <n>
  warnings, <n> failures`. `--verbose` lists every check; `--json` gives
  the same as data.
- **Exit codes.** 0 clean or warnings only, 1 any failure, 2 when doctor
  couldn't run.
- **Install.** A missing Stop, StopFailure, SessionStart or PreToolUse hook
  fails; a missing UserPromptSubmit hook fails while `pane_label` is on and
  warns otherwise. Hooks calling a different binary than the `loopherd` on
  PATH fail. Running a binary other than PATH's (e.g. `cargo run`) warns.
  `--settings` checks another settings file. No release lookup.
- **herdr.** Unreachable on the pane's socket, else the default one, fails.
  A version below `MIN_HERDR` fails; it starts at 0.9.5, the oldest tested,
  until a research note finds the oldest herdr with every feature loopherd
  uses.
- **Config.** A `config.toml` or `[notify]` that doesn't load (bad TOML, an
  unknown key, a token value below the minimum) fails. Unset limits or lead
  defaults warn, naming `loopherd setup`. An invalid herd file, or a herd
  `repo` that is missing or not a git repo, fails. Commands inside herd
  files aren't parsed.
- **State.** An unparseable ledger, pause or mailbox file fails, naming it.
  An unretired member whose pane is gone warns, naming `revive`. Members on
  another herdr socket are counted in one line, not checked. Strays aren't
  reported.
- **`--trackers`.** Runs each herd's `source` and `backlog`, paused herds
  included, with a 30s timeout each; a nonzero exit or timeout fails. It
  prints exit status and task count, never task lines.
- **`<herd>`** limits the herd, repo, state and tracker checks to that herd;
  install, herdr and config always run.

- **herdr plugin** (D62). On a reachable herdr, doctor reads `herdr plugin
  list --plugin loopherd --json`. The plugin stays optional, so every
  finding warns and none fails: not installed names `herdr plugin install
  junderdo/loopherd/herdr-plugin`, disabled names `herdr plugin enable
  loopherd`, a plugin older than the running loopherd names `herdr plugin
  update loopherd`, or for a linked plugin its checkout, and a newer one
  names updating loopherd. A plugin list herdr refuses, or doesn't answer
  within 5s, warns too.

LH-241 settled it; LH-251 added the plugin check.

## Why

Health checks were spread out and partial: `watch` warns only about the
Stop, StopFailure and SessionStart hooks, `herds` only about the prompt
hook, and nothing checks the PreToolUse hook that gates a lead, the binary
the hooks call, or herdr's version. Problems showed up only when a command
that needed the missing piece failed.

Every fix already has its own command, so a read-only doctor stays safe to
run anywhere and adds no second way to change state. Printing only problems
keeps the shepherd's and installers' routine runs to one line. Exit codes
follow `init --diff` (D38), and an installer shouldn't fail over a warning
or a herdr that isn't started yet. A release lookup and tracker commands
need the network, so the first is left out and the second sits behind a
flag. Checking members on other herdr sockets would mean reaching into
sessions D21 and the dev-session rule keep apart. Strays are normal and
`status` already counts them. A missing plugin only takes away its actions,
popups and event hooks, which is worth a warning but never a failure;
disabled gets `enable` because reinstalling a registered plugin wouldn't
turn it on.
