# D144

## Decision

Amends D114 and D121 (LH-399). A credentials member's confinement also
covers the GitHub tokens that live outside D114's fixed list:

- **More of the human's files are denied** to the sandbox and the file tools:
  `~/.claude.json` (user-scope MCP servers, a GitHub PAT among them),
  `~/.docker/config.json` (ghcr.io), `~/.npmrc` (npm.pkg.github.com) and
  `~/.config/github-copilot/`, each also where `CLAUDE_CONFIG_DIR`,
  `DOCKER_CONFIG`, `NPM_CONFIG_USERCONFIG` and `XDG_CONFIG_HOME` move it.
  So are the copies Claude Code makes of it: the whole `backups/` directory
  beside its config (`~/.claude/backups`, or under `CLAUDE_CONFIG_DIR`), and
  each `.claude.json.tmp.<pid>.<hex>` and `.claude.json.backup` beside the
  file, named one by one. So is every file a `credential.helper = store
  --file <path>` (or `git-credential-store` by path) names in the human's git
  config, with a leading `~`, `$HOME` or `${HOME}` expanded, read when the
  settings are built.
- **Those named copies aren't switches.** `restart` and `revive` leave them
  out when they compare a running lead's settings with its herd's, as they
  do the named broker and handoff denies, so a copy made since the lead
  started doesn't warn that its sandbox predates its herd's switches.
- **doctor skips the MCP check it can't make.** Inside a credentials
  member's sandbox `~/.claude.json` reads as `/dev/null`, so doctor reports
  it hidden and points to the human's own shell, not a parse failure.
- **More token variables are blanked**: `GITHUB_PERSONAL_ACCESS_TOKEN`,
  `GITHUB_PAT`, `GH_PAT`, `GITHUB_API_TOKEN` and `HOMEBREW_GITHUB_API_TOKEN`,
  beside D114's three.
- **A GUID-tagged virtiofs share is a Windows drive.** Read from WSL's
  source, not seen on a machine: with `virtioFsAggregateShares = false`,
  WSL mounts each drive as its own share tagged with a GUID, which D114's
  `drvfs`/`drvfsa` tags missed.
- **A Windows drive whose mount point isn't UTF-8 refuses the member**,
  since the settings file can't name it to deny it.
- **What the machine holds arrives through one seam.** `/proc/mounts`, the
  environment and the git credential helpers reach `credentials::confined`
  as a `Machine`, so lead and worker settings read them the same way and a
  unit test pins that a mounted drive lands in both `denyRead` and
  `Read(//<drive>/**)`.

## Why

- **The same hole, at other paths.** Each of these files and variables holds
  a token that authenticates as the human, so leaving it readable undoes the
  credentials guard as surely as `~/.config/gh` would.
- **Refuse, don't skip, an unnameable drive**, as D114 refuses a lead whose
  `/proc/mounts` can't be read.

## Limits

- **`/proc/<pid>/environ` stays readable to the file tools.** A process's
  starting environment keeps the tokens its settings' `env` blanks
  afterwards, so the Read tool can still reach any the pane that started
  Claude had. No `Read` deny closes it without breaking the sandbox: Claude
  Code passes `Read` denies to bubblewrap too. `Read(//proc/**)` would hide
  `/proc` from the lead's shell, where loopherd reads `/proc/self/exe`
  (D119) and `/proc/locks` (D109). A glob like `Read(//proc/*/task/*/environ)`
  is expanded to each live process's file, and the live test saw every Bash
  call then fail: `bwrap: Can't mkdir parents for
  /proc/<pid>/task/<tid>/environ`, a thread gone before the sandbox started.
  A sandboxed command can't reach it: Claude Code 2.1.331 starts bubblewrap
  with `--unshare-pid` and a fresh `/proc` unless the weaker nested sandbox
  is on.
- **Helpers other than `store`**, and a `store --file` given a relative
  path or one built from a shell variable other than `HOME`, aren't
  followed. Copies of `.claude.json` written after the
  settings are built stay readable until the next build: a glob would be
  expanded at each sandbox start and fail it once a copy is renamed away. The member's git runs with `credential.helper`
  cleared (D95), so only a direct read of such a helper's file is open.
- **Other tools' token files** past those named here still reach a member,
  as other non-GitHub secrets do (D114).
- **The live probe uses `ssh -F`** with loopherd's ssh config, so it shows the
  carved key reaches GitHub, not that the human's `~/.ssh/config` `Include`
  resolves inside the sandbox. A live test can't fake `~/.ssh/config`
  without moving the home Claude logs in from.
