# D157

## Decision

Existing herds are offered what newer releases of `loopherd init` write,
one named change at a time, each explained and shown as its own diff.
Grilled with the human on LH-559 (2026-11-24); amends D37 (init re-run,
question text) and supersedes D148's `init --grill`.

- **Named migrations.** A Rust table ships with the binary. Each entry has
  an id, an explanation of at most two lines (what it does, why), a check,
  and a change. Three kinds of change: a TOML key or value edited through
  `herd/edit.rs`'s layout-keeping path; an anchored prompt edit; a new
  template (with its prompt file, if any) rendered by init's own code.
  Each release that changes what init writes adds entries.
- **"Already has it" is a content check** in the migration: a template by
  name, a `[lead]` key by presence, a prompt by one fragment init always
  writes. No applied-id list is kept, so hand edits count as applied.
- **Prompt edits are anchored**: insert before, insert after, or replace a
  fragment, in a prompt file or an inline TOML prompt, only when the anchor
  matches exactly once.
- **Values change only on an exact match** with what an earlier init wrote,
  rendered from the herd's own settings. A tailored value (an `other`
  tracker's `source`, `backlog` or `done`; a hand-written `merged`) is
  never edited.
- **Skip and tell.** A change that can't be placed (anchor missing or
  repeated, value tailored) prints the snippet and where it belongs, writes
  nothing, and asks "Stop offering this? [y/N]". A migration that adds a
  routed template (wayfinding, grill-batch) is all or nothing with its
  queue routing.
- **Declines are per herd, in the herd file**: top-level `declined =
  ["<id>", …]`, which `loopherd herds` accepts. A "no" to an offer, or a
  "yes" to "Stop offering this?", adds the id; deleting it brings the offer
  back.
- **Two doors, one engine.**
  - `loopherd herd upgrade [<herd>]` offers pending migrations for one herd
    or every herd. It never asks settings.
  - `loopherd init` in a repo whose herd exists no longer refuses. It
    re-asks settings with the herd's current values as defaults, then
    offers that herd's migrations. A herd name another repo runs stays
    refused.
- **What an init re-run asks:**

  | Setting | Re-run |
  |---|---|
  | repo, herd name | Fixed; not asked. |
  | tracker | Not asked; changing it is a new herd. |
  | max, context_limit, merge_guard | Asked, current value as default. |
  | checks, gh account, default branch | Asked where the text is init's own form; tailored ones are skipped with a line naming where to edit them. |
  | lead | Asked only when the herd has none; removing a lead isn't offered. |
  | lead switches | Not asked, as today (`[lead_defaults]`, `herd set`). |

  Each changed answer is shown as its own diff; Enter through everything
  changes nothing.
- **Every question explains itself.** Fresh init and re-run show at most
  two lines above each settings question: what it controls and when to pick
  otherwise. A migration offer shows its id and explanation, a restart or
  revive note where a running lead needs one, the diff, then `Apply?
  [Y/n]`.
- **Without a terminal nothing is applied.**

  | Case | Behavior |
  |---|---|
  | `init` re-run, nothing to change | `herd <name> is up to date`, exit 0. |
  | `init` re-run, no terminal | Flags change settings as D37's do; no migration applied; pending listed with `loopherd herd upgrade`; exit 0. |
  | `herd upgrade`, no terminal | Per herd, `<herd>: <n> new features: <ids>` and the command; exit 0. No `--yes`. |
  | `loopherd update` | After installing, runs the new binary's `herd upgrade`, also when nothing new was installed. |
  | `update --check` | Adds the current binary's pending count. |
  | `doctor` | One info line per herd with pending migrations; never a failure; declined ones aren't counted. |

- **Backups.** Before its first write to a file in a run, upgrade copies it
  to `<file>.bak-<timestamp>`.
- **First migrations:** `lead-review-rounds` (anchored insert),
  `lead-drained` (anchored replace), `lead-follow-ups-ready` (key add),
  `merged-repo` (exact-match replace). LH-497 adds `grill`; LH-556, 557 and
  558 add `groom`, `wayfinding` and `grill-batch`.

Built as LH-562 (question text), LH-563 (`herd upgrade` with key and value
migrations), LH-564 (prompt migrations), LH-565 (update, `--check`, doctor)
and LH-566 (init re-run), with LH-497 and LH-556–558 amended and LH-498
archived; all in 0.2.1.

## Why

Herd files and lead prompts are written once, so herds fall behind as init
grows; on 2026-11-24 loopherd-cards' lead prompt was missing three lines
and nothing had said so. `init --diff` on that herd is 339 lines, mostly
the human's own tailoring, so it can't be skimmed or applied.

- **Named migrations over diffing against init.** A tailored herd has no
  `issue` template and reworded prompts, so offering every piece init would
  write is the 339-line diff again in smaller pieces; a named migration can
  also change a value it knows the history of.
- **Content checks over an applied list.** loopherd-cards already has every
  first template and two of the three lead lines by hand; a list would
  offer them all again.
- **Anchors over a three-way patch or owned sections.** loopherd never kept
  the text it first wrote, and no existing herd has section markers.
- **Skip and tell, never guess.** An edit to a tailored value or a moved
  anchor would silently undo the human's work; "Stop offering this?" keeps
  one from nagging forever, as D148 avoided.
- **Declines in the herd file.** One herd may want groom and another not;
  the file is what the human reads and backs up, and upgrade writes it on
  a yes anyway.
- **Init re-run as a door.** The human's ask: Enter through init keeps a
  herd as it is, and a changed answer changes only that setting.
- **No `--yes`.** Unattended upgrades would write prompt changes the human
  never saw; the human dislikes installer flags (D154).
- **No `lead-gh-account` migration.** Only a human with several gh
  accounts needs it, and the one who does already added it by hand.
- **Explanations on every question.** A one-word label like `max` doesn't
  say what it controls; the same text serves fresh init and re-run.
