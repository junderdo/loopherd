# D109

## Decision

Amends D28's `after-merge.lock`, which moves and whose wait is bounded.
Every lock wait in loopherd is bounded, and `after-merge.lock` moves to
`<state>/locks/after-merge.lock`, a directory a sandboxed lead's sandbox
denies reading (LH-313; widened in the LH-307/LH-309 grilling, 2026-11-20).

- **One bounded wait.** `Lock::wait(file, bound)` polls a non-blocking flock
  until `bound` and then fails `TimedOut` with `held past <bound> by pid <n>`,
  the PIDs `/proc/locks` lists for the file's inode. When it lists none,
  the error says the holder wasn't found there and gives the inode; off
  Linux it says `holder unknown`. Callers prefix the lock's path. No other
  code blocks on a flock: a unit test greps `src/`, outside each file's
  `mod tests` block, for a flock op without `LOCK_NB`, and `clippy.toml`
  disallows `File::lock` and `File::lock_shared`.
- **Bounds.** Locks held for one read and rewrite (ledger, mailboxes, report
  offsets, `.notified`, `.merges.lock`, `shepherd.json.lock`, herd file
  edits, the ssh config) wait `lock::BRIEF`, 30 seconds. `after-merge.lock`
  waits `FeedRequest::after_merge_wait`, which a broker sets to `FEED_WITHIN`
  (4 hours, as long as a client waits on its broker): the holder keeps it
  across every member's commands, each up to `after_merge_timeout`, and with
  `locks/` hidden from leads a long wait can only be on another feed. Locks
  already taken with a try (feed, watch, revive, restarts, broker) are
  unchanged.
- **`locks/`.** `Paths::locks_dir()` is created with the lead's other state
  dirs and listed in every lead's `sandbox.filesystem.denyRead`, credentials
  or not. A user `allowRead` at or beneath a denied path is a D100
  loosening. One over an ancestor, such as `~/`, isn't, because Claude Code
  keeps the narrower deny. A relative one resolves against `~/.claude`, as
  Claude Code resolves it in user settings, and one that still climbs with
  `..` counts; with credentials to hide, any user `allowRead` still is.
- **`install = true`.** Such a lead's `scripts/install` is an excluded
  command, so it runs outside the sandbox and the `locks/` deny doesn't
  reach it. The script comes from a worktree the lead can edit, so that lead
  can still hold `after-merge.lock`, and feeds then wait out `FEED_WITHIN`
  and fail naming its pid.

## Why

On Linux a process can flock a file it can only open read-only, so denying a
lead writes doesn't stop it holding `feed.lock`, `after-merge.lock`,
`reports/revive.lock`, `restarts/*` or another lead's `.notified` and
`.merges.lock`. A blocking `Lock::wait` on any of those wedged the waiter
forever: a lead flocking `after-merge.lock` stuck its broker, and revive then
found the broker lock held, so a relaunched lead inherited the stuck broker.
Hiding each lock from every reader would mean a deny per lock and per
future lock; bounding the one wait covers every holder, a hung process
included, and the error names who to look at. `after-merge.lock` is also
hidden because its wait is the long one: a lead holding it would stall
every feed for up to `FEED_WITHIN`. Other locks stay readable (out of scope
for LH-313).

During the upgrade a feed on the old binary took the old
`<state>/after-merge.lock` while a new one took the new path, so the two
could run after_merge at once. That overlap ended once each lead's broker
restarted onto the new build. Nothing takes `<state>/after-merge.lock`
since, and loopherd leaves the file where it is; deleting it is safe.
