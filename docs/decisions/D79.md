# D79

## Decision

loopherd sets no cap on running agents across herds. Each herd's `max`
(D14, D25) stays the only limit on what `feed` spawns, and nothing in
`config.toml`, `status`, `feed` or a watch counts agents across herds.

Reopen this when either happens:

- two or more herds run unpaused at the same time, or
- a usage-limit or `rate_limit` stop hits members of more than one herd in
  the same window.

The shepherd notes the trigger and offers the human to reopen it; nothing
acts on it automatically.

A future limit should start from reacting to usage-limit and `rate_limit`
stops, holding feed back for a while, rather than from a fixed agent count.
Where it would live, whether leads count, how free slots are shared between
herds, and how `status`, `feed` and a lead's `claimable` and `running low`
lines (D60, D61) report a herd held back by it all stay open.

## Why

There is one herd today, so a cap across herds would never bind; it would
only add a setting and a second held-back reason to `status`, `feed` and
`running low`. The machine isn't the constraint: WSL2 gets half of the
host's 128 GB and loopherd-cards ran with most of it free on 16 cores.

The limit that bit was the Claude account's usage limit. On 2026-11-18 the
lead, its workers and the shepherd all stopped on it together. That budget
is tokens, shared with agents outside loopherd's ledger and the human's own
sessions, so a count of loopherd agents would be a poor proxy for it, and
reacting to the stops it causes measures it directly.

D25 already bounds the human's review load per herd; how much several herds
add up to is left to the reopening.

LH-243 settled it.
