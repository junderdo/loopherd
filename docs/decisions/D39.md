# D39

## Decision

`loopherd init` gives a local-markdown tracker (D35 item 8; mattpocock-skills'
`issue-tracker-local.md`) working snippets, as built in LH-128:

- A tracker doc titled `Issue tracker: Local Markdown`, in any case, or
  `--tracker local`, gets them; the triage labels then pass the same safe-label
  check as GitHub's, since both put them in shell.
- The source and `done` read issue files at `origin/<default branch>` after a
  `git fetch`, not the working tree: workers' worktrees branch from there, so
  an issue that isn't pushed can't be worked yet. The fetch retries once,
  since two fetches racing to move `origin/<branch>` fail all but the first
  with `cannot lock ref`, and the retry finds the ref current.
- Issues are `.scratch/<feature>/issues/<NN>-<slug>.md` (path parts of
  letters, digits and `. _ -`); any other `.md` under an `issues/` dir in
  `.scratch/` is noted on stderr, not fed. The `Status:` line, first above any
  `## Comments` heading, `**bold**` or not, is read as comma- or
  space-separated labels: claimable is `ready-for-agent` and none of
  `blocked`, `needs-info`, `ready-for-human`, `resolved`, `closed`, `done`;
  type (`bug`→fix, `documentation`→docs) and `skill:<name>` work as on GitHub.
  A `Blocked by:` line, or a `-` list under an empty one, blocks unless it
  is `None…` or each of its comma- or semicolon-separated items names a
  number and every number it names is a resolved issue: of the feature an
  issue path in the item names, else of the issue's own feature. An item
  names the numbers in its first run of words starting with a number, joined
  by `and`, `&` or `/` (`01 and 02`, `#01 / #02`, `see 01`); a title in
  parentheses, after `:` or after the run, and a slug's later numbers, name
  none (`01 (Node 20)`, `01: Login form`, `#01 Node 20 upgrade`,
  `01 - Node 20 upgrade` and `issues/01-step-2-of-3.md` name 01). An item
  with no number, such as a bare title or `Node upgrade (#01)`, and a number
  that is no issue, block with a note on stderr.
- The task is `<id> <type> <skill> <slug> <path>`, the id `<feature>-<NN>`
  when the feature is lowercase letters, digits and `-` and `<herd>-<id>`
  fits 32 characters. Any other feature is cut to fit and takes a
  3-character hash of its name, `<cut>_<hash>-<NN>`, rehashed when another
  feature already holds it, so two features never share an id and starve
  one another (`_` marks a hashed id, and no plain
  one has it). An issue whose id can't fit is skipped with a note on
  stderr. Branches are `<type>/<id>-<slug>`.
- Closed is a `Status:` of `resolved`, `closed` or `done` on the default
  branch; a file missing there is not done. Issue files may lack a final
  newline or use CRLF. The worker claims by setting `claimed` and appending
  `claimed by <member>` under `## Comments`, commits, and before pushing sets
  `resolved`, so the issue closes when its branch merges, as `Closes #<n>`
  does on GitHub. A question sets the needs-info label as the status.
- With a GitHub origin, `merged` is the GitHub PR check and the worker opens
  a PR; init creates no labels.
- Without one, and without `--repo`, the herd has no GitHub: init resolves
  the tracker before asking for the GitHub repo (Enter means none), makes no
  gh call, refuses `--gh-account`, and asks origin for its default branch,
  as the members' worktrees do. It writes no `merged`, saying
  that `after_merge` never runs (in the summary on a terminal, else on
  stderr), and the worker hands in by pushing its
  branch with no PR; the human merges it. No prompt or doc names gh or an
  account.
- `init --diff` (D38) covers a local herd's files the same way, and without
  GitHub it makes no gh call; the `merged` warning is init's only.
- The source's stderr notes show in `loopherd feed --dry-run`, each as
  `source: <note>`, and when the source is run by hand; a real feed and
  `watch` leave them out.
- A local tracker needs an `origin` remote, since members branch from it
  and push to it; init refuses a repo without one.

## Why

Reading the pushed default branch keeps the queue, the worker's checkout and
the done check on one copy of the issues, and closing through the PR's own
diff ties done to the merge, as GitHub does. Treating the status words as
labels reuses GitHub's claimable rule and type and skill mapping, so the two
built-in trackers read the same way. Local markdown is the tracker for repos
without GitHub, so it must work without gh; a `merged` check over plain git
was left out because no herd yet sets `after_merge` without GitHub.
