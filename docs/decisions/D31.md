# D31

## Decision

A lead's six switches (D17) resolve in three layers: the herd file's
`[lead]`, else `[lead_defaults]` in `$LOOPHERD_CONFIG_DIR/config.toml`, else
`false`. `{switches}` in the lead's prompt, the PreToolUse tool hook and a
lead's `feed` all use the resolved value, so a herd file's `merge = false`
turns `merge` off for that herd even when `[lead_defaults]` turns it on.
`[lead_defaults]` takes only the six switch names, each a boolean; any other
key makes `config.toml` invalid. (Amended by D69: it also takes
`review_rounds`, a positive integer.) An unreadable or invalid `config.toml`
fails closed as an unreadable herd file does: the hook counts every switch
off, `loopherd lead` refuses, and `loopherd herds` reports the error and
shows each lead's switches as all off. Otherwise `loopherd herds` shows
each led herd's resolved switches, each with where it came from (`herd
file`, `lead_defaults` or `built-in`).

`scripts/install` sets the defaults. On a terminal, while `config.toml` has
no `[lead_defaults]`, it asks about each switch with a one-line description,
default no, after the agent types and plugin. Once the table exists it asks
nothing unless run with `--lead-defaults`, which asks again with the
current values as defaults. `--lead-defaults <list>` (a comma list, or
`none`) sets those switches on and the rest off without asking. With no
terminal, `--no-extras`, `--remove`, or another extra named alone, it
leaves `config.toml` untouched. The installer writes through `loopherd
lead-defaults [--set <list>]`, which prints the table as `<switch> on|off`
lines (nothing when absent) and, with `--set`, writes all six keys through
`toml_edit`, keeping the file's other keys and comments, refusing any result
that isn't a valid `config.toml`.

The tool hook denies `loopherd lead-defaults --set` and `scripts/install
--lead-defaults` in a lead's pane whatever its switches, as it does `herd
set` (D29), since either could turn the lead's own switches on.

There is no project-level layer: no repo-committed `.loopherd/config.toml`.

## Why

The human wants to choose once, at install, how autonomous leads are by
default (merge verified PRs themselves, or leave every PR to the human),
instead of editing each herd file. A herd works on one project, so its herd
file's `[lead]` is already the per-project layer; a second, repo-committed
project file would only add an override order with nothing gained. Decided
with the human on LH-110 (option A).

Limits as D29's: the hook is a guardrail on the command text, and it binds
only leads' panes, so the shepherd or another member can still change the
defaults, and a lead can still edit `config.toml` by hand.
