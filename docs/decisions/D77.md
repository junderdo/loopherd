# D77

## Decision

A moved member's `env_pane_id` belongs to the process that inherited it.
The Stop and SessionStart hooks drop it when they claim a new process for
the member from its current `pane_id`. Until a herdr restart, every
process in a moved pane inherits the old id, since herdr sets
`$HERDR_PANE_ID` only when it creates a pane's shell. So a claim from the
current id means a restored herdr rebuilt the pane and the old process is
gone. A claim from `env_pane_id`, such as a Claude relaunched in the moved
pane's own shell, keeps it, and so does a member whose process survives.

`revive` still drops it only when it starts the member in a different
pane. It can reuse the moved pane's own shell, which carries the old id
until a restart. With the recorded process cleared, the started Claude's
first hook claims it and drops the id if the shell was restored.

This amends D74: its limit on a reused workspace id handing a moved
member's old id to a new pane is gone, and its other limits stand.

Limits:

- After a restart, a moved member keeps `env_pane_id` until its resumed
  Claude's hook claims it. If herdr and `revive` don't start it again, or
  its hooks can't claim (no usable `$CLAUDE_PID`, or a Stop hook whose
  socket doesn't match exactly), an agent in a new pane with that id
  still resolves to it until it is revived or retired. A stale `pane_id`
  does the same.

LH-271 settled it.

## Why

Only a hook's claim knows both that the member's process was replaced and
which id the new one carries. Revive sees a dead recorded process but not
whether the shell it lands in was restored, so clearing there would orphan
a member resumed in its moved pane's own shell. Clearing on every revive
would also drop the id from a member whose own process still runs and
needs it for its reports and hooks.
