# D77

## Decision

A moved member's `env_pane_id` is pinned to the pane's shell process, and
a caller matches it only when that shell is the caller or one of its
ancestors.

- When the `pane.moved` hook first sets `env_pane_id`, it reads the
  pane's `shell_pid` with `herdr pane process-info` and records that
  process, by pid and start time, as `env_pane_shell`. A `restart` that
  sets `env_pane_id` records the shell of the pane it found the member
  in the same way. A later move keeps both.
- Each lookup by the caller's own `$HERDR_PANE_ID` passes the caller's
  lineage: loopherd's process and its ancestors, read from `/proc`. It
  matches `env_pane_id` only when that lineage holds `env_pane_shell`. A
  match on `pane_id` needs no lineage. The lookups are `report`, the Stop,
  SessionStart and PreToolUse hooks (`lead_in`, including its retired-lead
  fallback), `restart`'s and `retire`'s own-pane refusals, `retire
  --close`'s own-tab check, `watch`, and the workspace that `spawn`, `add`,
  `lead` and `feed` inherit.
- An `env_pane_id` with no `env_pane_shell` matches nothing. Such an entry
  comes from a move hook or restart that couldn't read the shell, which
  each reports, or from a move made before this change.

The id itself is never cleared on a process change. It stops matching
once its shell is gone, which a herdr restart always causes.

This amends D74: its limit on a reused workspace id handing a moved
member's old id to a new pane is gone, its lookups now need the shell, and
its other limits stand.

Limits:

- A move whose shell herdr can't report leaves the member's old id
  unmatched. Its own reports, hooks and lead guardrails then fail from the
  old id until a restored herdr gives its pane the current one. The same
  holds for a member moved before this change.
- `retire --close` run from such a member's pane can close the tab it
  runs in, as before D74 followed moves.
- A stale `pane_id`, one that no move hook or restart updated, still
  matches any process in a pane that took that id.

LH-271 settled it, following review round 1 on PR #250.

## Why

After a herdr restart no pane process survives, and a restored pane's
shell carries its current id. A process carrying an old id must therefore
descend from a shell that was alive before the restart. A live handoff
keeps the shells, reparented away from the new server, so pinning the id
to the herdr server would have dropped it from moved members after every
handoff. A shell survives a handoff and dies in a restart, so it tells the
two apart. The check runs at lookup time, so it holds whether or not the
member is ever revived or claims again. That closes the case where a
stranger's `/clear` in a reused pane was adopted as the member's session.
