# D94

## Decision

Amends D87's "still the shepherd" check and D88's "live shepherd". The
handoff record in `shepherd.json` also keeps `shell`: the pid and start
time of the pane's shell, as `herdr pane process-info` names it at the
handoff, kept only when it is the shepherd's Claude (`exec claude`) or an
ancestor of it. A handoff that can't record the shell warns and records
the rest.

The recorded pane counts as the shepherd's while its shell is that process
(pid and start time) and herdr lists an agent in the pane. Any agent
counts, not only a Claude: herdr's list says a pane runs an agent, not
which. A shell left at a bare prompt doesn't count.

- **`loopherd view --beside-shepherd`** uses that check alone when the
  record has a `shell`. A record without one keeps D87's check, which also
  accepts a Claude that is the pane's shell.
- **`S`** (`shepherd_pane::summon`) decides in this order. An agent named
  `shepherd` is focused. Else, on the view's herdr with an agent in the
  recorded pane, the pane is focused when the recorded Claude still runs
  (D88) or the pane still runs the recorded shell. Else a recorded Claude
  that still runs is D88's "elsewhere", and nothing starts. Else there is
  no live shepherd, and `S` starts one. A shell herdr can't name, or whose
  process can't be read, is not the recorded one. A record without `shell`
  keeps D88's check.

The view's note names the cause: a pane with no shell pid (as while herdr
resumes its agent), a shell whose process can't be read, a shell that
changed or was restarted under the same pid, a pane running no agent, or
(without a recorded shell) a Claude no longer under it.

## Why

LH-291. The record changes only at a handoff, so a Claude restarted in
its pane (`claude --resume`, a crash, an update) left a dead pid in it and
the view stopped finding the shepherd. The shell survives those restarts
and changes when herdr restarts. The shell comes from herdr, not from
walking up to the server, because a live herdr handoff reparents every
pane shell away from the server. The shell alone isn't enough: when the
shepherd's Claude is quit and `S` starts a new one elsewhere, the record
still names the old pane until the next handoff. herdr detects a Claude
by its process name, a hand-started one included, and lists it a moment
after it starts.

LH-300. `S` kept D88's check, the recorded Claude's pid alone, so after a
Claude restarted in the shepherd's pane, before that shepherd named
itself, `S` started a second one beside the first. This replaces D88's
"neither does another agent later in that pane" while the pane's shell is
the recorded one: the cost is that an unrelated agent started in the
shepherd's old shell, after the shepherd quit, is focused as the
shepherd, where a second shepherd running unseen is the worse mistake.

D87's pid-only check still reports a Claude whose process can't be read
as gone, not unreadable. `Procs` answers every question with an `Option`,
so a missing process and an unreadable one look the same. Telling them
apart needs an error-returning read on Linux, macOS and the fake, and
still couldn't on a `/proc` mounted with `hidepid`, where another user's
process reads as missing. The shepherd's Claude runs as the view's user,
whose processes it can always read, so the case is left as it is.
