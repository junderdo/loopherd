# D107

## Decision

Workers get the containment D83 gave leads, opt-in per herd for now (LH-284,
grilled with the human 2026-11-20). Builds on D83, D89, D95, D97, D100 and
D105's `unix_sockets`; amends D95's and D98's "members keep the human's
credentials" and LH-310's scope.

- **`[worker] sandbox = "off" | "require" | "prefer"`**, default `off`. The
  default becomes `require` by a later decision, once the `.git/config.lock`
  placeholder (D104, LH-323) and the herd's socket needs are settled.
  - `require`: `feed`, `add`, `spawn` and `revive` refuse to start a worker
    whose sandbox can't start (D89's probe and D105's socket-filter probe),
    or that a D100 loosening, a non-allowlisted arg or a missing credential
    would weaken. A feed notes the task as not started and goes on with the
    rest.
  - `prefer`: starts it unsandboxed with a warning and flags it `unsandboxed`
    in the ledger, which `view` shows. A `credentials` herd refuses under
    `prefer` too, as D95 does for leads.
  - Doctor stays silent about `off` herds until the default flips; it warns
    for `prefer` herds and for workers running without their sandbox.
- **The files.** As D89 for leads: `<config dir>/sandbox/<member>.json`
  (0600, since it may hold a token) passed as `claude --settings`, and a kept
  `<member>.member.json` (herd, template, args) that `revive` trusts over the
  ledger. `revive` rewrites the settings from the herd's current switches;
  `restart` writes nothing and only checks the recorded args; `retire` removes
  both.
- **Writes.** The worker's own worktree (with the shared `.git` Claude Code
  opens, `hooks/` and `config` denied), its own `handoffs/<name>/` (LH-307),
  its own mailbox directory, and temp. Everything else is read-only: the rest
  of the state dir, the config dir, `~/.claude`, other worktrees and the main
  checkout. Each deny is a sandbox `denyWrite` and an `Edit(…)` rule, as D89.
- **Per-agent mailbox directories, for everyone.** A worker has no broker to
  report through, so mailboxes move from `reports/<name>.jsonl` into a
  directory per agent, as LH-307 does for handoffs, and a worker's
  `allowWrite` names only its own. Readers fall back to the flat files until
  a later release.
- **Unix sockets: none by default.** `[worker] unix_sockets = "all"` opts a
  herd's workers back in, with D105's meaning, probe and doctor warning.
  `loopherd-cards` needs it for live tests against the dev herdr, so its
  workers keep the herdr-socket escape.
- **The lead's other guards apply.** With the sandbox on, D100's settings
  checks run for the worker at spawn, restart and revive; workers start with
  `--strict-mcp-config` and only the servers `[worker] mcp_servers` names;
  LH-316's args allowlist checks the herd's and template's `args`.
- **Credentials follow the herd's merge guard.** A sandboxed worker in a
  `merge_guard = "credentials"` herd gets the herd's split credentials (D95):
  its deploy key through the `loopherd-<herd>` alias, its PR-only token as
  `GH_TOKEN`, D95's environment rewrite and `denyRead`. No second key or
  token. `hook` and `merge = true` herds' workers keep the human's gh. Doctor
  warns for a `credentials` herd whose workers aren't sandboxed. Prompts and
  checks use `${GH_TOKEN:-$(gh auth token --user <account>)}` so they run as
  either.
- **Reads** match a lead's: the config dir (herd files, `trello.env`) stays
  readable. The credential gaps a lead has (every herd's keys and tokens, the
  keyring and ssh agent through sockets) are LH-310's, now for members.
- **The human's own panes are the trust root.** The shepherd and side
  sessions such as grilling run as the human, unsandboxed, and loopherd gives
  them no settings. A session that runs unattended should be a member.

## Why

- **Workers are the hole in every lead guard.** D89 and D98 each note that
  a lead can `tell` a worker to do what its own sandbox refuses. Workers also
  read the most untrusted text: cards, comments, reviews and web pages.
- **Opt-in first, as D83 did for leads.** On by default would today break the
  herd's live tests (no sockets) and fail `git config` writes repo-wide while
  any worker builds (D104's placeholder). One herd proves it first.
- **Directories, not names.** A per-file deny inside an allowed directory
  falls to a rename from outside (D97), so a worker's mailbox is separated by
  directory, the same move LH-307 makes for handoffs.
- **The split already fits workers.** They push feature branches and open
  PRs and never merge, which is exactly what D95's key and token allow. A
  second key and token per herd would add a manual PAT step and buy only
  separate revocation.
- **The sandbox is worth little without the other guards.** A worker writes
  its own worktree's `.claude/settings.local.json`, MCP servers run outside
  the sandbox, and args such as `--add-dir` loosen it; D100 and LH-316 close
  these for leads.
- **The human's panes can't be sandboxed usefully.** The shepherd must start
  brokers from an unsandboxed shell (D98). Attribution (per-agent mailbox and
  handoff directories) and the human's review of merges protect them.

## Limits

- **`unix_sockets = "all"`** reopens the herdr socket, ssh agent, keyring
  and WSL2 interop for that herd's workers; `loopherd-cards` sets it.
- **The deploy key is repo-wide.** A worker can push to any feature branch,
  another worker's or the lead's included; rulesets stop only `main` and
  force pushes.
- **Live settings reloads.** D100's checks run at spawn, restart and revive.
  A worker that writes an `Edit(…)` allow into its own worktree's settings
  mid-session isn't seen until then; `blockWritesOutsideWorkingDirectories`
  keeps such a rule from reaching past the worker's working directories.
- **The `.git/config.lock` placeholder** (D104) is held by every sandboxed
  worker's build; accepted while the switch is opt-in.
- **Hooks** run outside the sandbox in every worker, as for leads.

## Built (LH-340)

The switches, files, writes, sockets, doctor and the ledger flag are built as
decided above, with these specifics:

- **Which members.** A herd member from a template: `add` and `feed`, and
  `revive`. `revive` resumes one from its kept `<member>.member.json` (herd,
  template, args and worktree), and one added while its herd's sandbox was
  off from its ledger entry, keeping it from then on. `loopherd spawn` makes
  no herd member and is untouched.
- **A worker with no worktree** (a template with no `branch`, or a branch
  checked out in the main checkout) would make the main checkout its writable
  cwd, so its sandbox counts as unable to start: `require` refuses it,
  `prefer` starts it unsandboxed and flagged.
- **`prefer` and Unix sockets.** A sandbox that can't block Unix sockets, in a
  herd without `unix_sockets = "all"`, counts as unable to start, so `prefer`
  starts that worker unsandboxed and flagged; there is no worker
  `sockets_unblocked`.
- **A feed** prints `not started: <task>: <why>` for a refused worker, counts
  it as an error, frees its slot and goes on. It probes the sandbox once per
  run.
- **Its own state.** `prepare` creates `handoffs/<name>/` and
  `reports/<name>/`, since Linux drops an `allowWrite` for a missing path, and
  the file tools get `Edit(…)` allows for both, since the Stop hook asks a
  worker to write its handoff with them. Both are `additionalDirectories`,
  and `blockWritesOutsideWorkingDirectories` refuses the file tools' writes
  anywhere else (other agents' handoffs and mailboxes, other worktrees, the
  main checkout) in every permission mode, past any `Edit(…)` allow
  (live-tested under `--permission-mode auto`). Off Linux, other agents'
  handoff and mailbox directories are also denied by name. `revive` starts a
  kept worker in its kept worktree, since a sandbox always lets its cwd be
  written.
- **Git.** `hooks/` and `config` are denied in the repo's common git dir, so
  this holds when the herd's repo is itself a linked worktree. Commits in the
  worker's worktree work (live-tested).
- **Network.** `WebFetch(domain:*)` is allowed, as for a lead (D89), so a
  worker can push, open PRs and fetch dependencies.
- **`herd set`.** It is refused by the config dir's write deny, which fails
  it inside the sandbox. The tool hook still gates only leads; an unsandboxed
  `prefer` worker could edit the herd file directly anyway.
- **Calling lead.** A `<member>.member.json` beside a settings file marks it a
  worker's, so `calling_lead` never takes a sandboxed worker for a lead.
- **Retire** removes the settings and kept record once the worker's Claude has
  ended, whoever retires it: no lead can write the config dir to forge a
  record. `add` checks the name is free in herdr before writing them, so a
  retired worker whose Claude still runs keeps its files. A failed `add`
  removes them only while no ledger entry holds the name.
- **`restart`** writes nothing. It refuses, under `require`, a worker whose
  recorded args don't pass its settings, naming `revive`; under `prefer` it
  warns and keeps the `unsandboxed` flag.
- **A kept worker whose herd file is gone** can't have its settings rebuilt:
  `restart` and `revive` refuse it naming the herd, and doctor warns of it.
- **Status and view** show `(unsandboxed)` beside the worker, and
  `worker, unsandboxed: <why>` in its detail, ahead of `attended`.
- **Not built here:** D100's settings checks, `[worker] mcp_servers` with
  `--strict-mcp-config` and LH-316's args allowlist (built by LH-341, below).
  Credentials for workers are built by LH-342 (D128).

## Built (LH-341)

The lead's other guards apply to a herd member whose herd's `[worker]
sandbox` is on, at `add`, `feed` and `revive` (when it's prepared) and at
`restart` (which writes nothing and judges what the worker started with):

- **D100's settings checks** read the human's `~/.claude/settings.json` and
  the worker's own worktree's `.claude/settings.json` and
  `.claude/settings.local.json`, judged against the worker's own settings,
  naming each file and key. `require` refuses the worker (a feed prints
  `not started`); `prefer` starts it sandboxed with each as a warning and
  doesn't flag it `unsandboxed`, as D100 does for a lead. `add` and `feed`
  check out the worker's worktree first, after spawn's own refusals and the
  args and MCP refusals, so a new one's checked-out project settings are
  read. When the sandbox then refuses the worker they remove a worktree they
  just created, and the local branch they created for it, so a retry checks
  out origin's tip rather than the branch as it was at the refusal. A
  worker whose sandbox can't start isn't checked: it has no settings to
  loosen. `restart` judges them against the settings file the running
  worker started with.
- **MCP.** Every worker in such a herd, sandboxed or started unsandboxed
  under `prefer`, starts with `--strict-mcp-config --mcp-config <config
  dir>/sandbox/<member>.mcp.json` (0600), holding only the user-scope servers
  `[worker] mcp_servers` names. A name not in user scope refuses the worker
  under both modes, before anything is written, as does an unreadable
  `~/.claude.json`, so a feed goes on with its other tasks. `loopherd herds`
  shows the list as `worker mcp_servers:` for a herd whose worker sandbox is
  on, and refuses a blank or repeated name in any herd; doctor reports an
  unknown name as a failure. `restart` warns of a worker running
  without the lock, naming `revive`; `retire` removes the file with the
  worker's settings.
- **The args allowlist** is D100's. `add` and `feed` name each arg's source:
  `herd <h>'s args`, `template <t>'s args`, or the command line; `revive`
  and `restart` judge the args kept when it started and say to retire it
  and add it again from its template. `require` refuses, `prefer` warns. One of loopherd's own
  launch flags (`--settings`, `--mcp-config`, `--strict-mcp-config`) refuses
  the worker under both modes; `revive` drops them from a ledger record or
  kept record that holds them. Doctor reports each bad arg in the herd file
  (the herd's and every template's) as `herd <h> worker args`, a failure
  under `require` and for a launch flag, a warning under `prefer`.
- **In a credentials herd** (D128) a worker whose sandbox can't start is
  refused under both modes. Amended by LH-427 (D151): so are the settings
  and args checks above, since a loosening can reopen reads of the herd's
  deploy key and token, the exposure refusing an unsandboxed worker guards
  against.

## Built (LH-415)

- **A feed dry run** judges a sandboxed worker as far as it can without
  writing or checking anything out: its args and MCP servers, a worktree of
  its own, the probe and a credentials herd's sockets. One `require` (or a
  launch flag or unknown server) would refuse prints `would not start: <task>:
  <why>`, counts as an error and frees its slot; any other error stops it, as
  it stops a feed. It also makes D100's settings checks under `require`: the
  human's `~/.claude/settings.json` in full, and the worktree's project
  settings when it is already checked out. A worktree a feed would check out
  fresh has none to read yet. `claimable` still counts such tasks.
- **A lead's name.** No herd member from a template may take a `lead-*`
  name, in any `[worker] sandbox` mode, whether or not that lead's herd exists
  yet. `add`, `feed` and a feed dry run refuse it as not started, before
  anything else. Sandboxed, its settings and `<name>.member.json` would
  replace the lead's and hide it from `calling_lead`. In an `off` herd it
  writes no sandbox files, but `revive`'s `kept_lead` trusts a kept
  `<name>.lead.json` over the ledger, so it would resume a worker as that lead,
  with the lead's settings and worktree. `kept_lead` can't skip a kept record
  on the ledger's say: a lead can rewrite its own entry. This is the one check
  `off` herds make before spawn.
- **`off` herds** spawn as before LH-340, apart from the lead-name refusal
  above: `add` and `feed` go straight to spawn, with no extra herdr call or
  worktree planning.
- **`revive`** reads a kept worker's record for its cwd, but reports one that
  won't parse only where it would prepare the worker: an alive, colliding or
  skipped worker, or a dry run, reports as before.
- **A worker's question** labels no pane (only a lead's does), so its
  `report` makes no herdr call and prints no warning; the label-failure
  warning is tested for a lead.
- **`herd set`** from inside a worker's sandbox is live-tested refused, the
  herd file left unchanged: loopherd refuses it on finding the ledger
  read-only, before the config dir's deny is reached. Also live-tested: a
  worker's own Write tool call into its `handoffs/<name>/` under
  `--permission-mode auto`.
