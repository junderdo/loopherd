# D100

## Decision

Amends D89's "The human's own settings" gap (LH-304). loopherd reads the
settings Claude Code would merge into a lead's sandbox and acts on what
loosens it, and starts each lead with only the MCP servers its herd names.

- **What's read.** The human's `~/.claude/settings.json`, at `lead`,
  `revive` and `restart` of a lead, and in `loopherd doctor` for each herd
  with a `[lead]`. A missing file is no finding; an unreadable or
  unparseable one is.
- **What's a finding.** Each entry or key, named with its file:
  - `sandbox.excludedCommands`: any command the lead's own settings don't
    already exclude.
  - Writes opened by `sandbox.filesystem.allowWrite`,
    `permissions.additionalDirectories` or an `Edit(…)` rule in
    `permissions.allow`: any path that isn't exactly one the lead may
    already write. A path beneath one counts too, since the lead could
    plant a symlink there before the path exists. A relative path, a glob
    before the end, `..`, or a bare `Edit` counts.
  - `sandbox.filesystem.allowRead`: any path the lead's own settings don't
    list, for a `credentials` lead only. It carves into `denyRead`, which
    only that lead has.
  - `sandbox.filesystem.disabled`, `sandbox.enableWeakerNestedSandbox`,
    `sandbox.allowNestedUserNamespaces`,
    `sandbox.enableWeakerNetworkIsolation`, `sandbox.allowAppleEvents`:
    set to anything but `false`.
  - Booleans the lead's own `--settings` sets (`enabled`,
    `failIfUnavailable`, `allowUnsandboxedCommands`) aren't findings, since
    `--settings` outranks user settings for them. Other `permissions.allow`
    rules aren't either: they skip prompts and leave the sandbox as it is.
  - Not checked: the network keys (`allowUnixSockets`, proxy ports,
    `allowMachLookup`, `allowLocalBinding`). The lead's own settings open
    every host and Unix socket already.
- **What `[lead] sandbox` does with them.**
  - `require` refuses to start the lead, naming each file and key: `lead`
    fails, `revive` reports `failed <lead>: sandbox: …`, and `restart`
    refuses to clear it.
  - `prefer` starts or keeps it sandboxed and prints each as a warning;
    `lead` also notes them in its mailbox. It isn't flagged
    `unsandboxed`.
  - `merge_guard = "credentials"` refuses under both, as for a sandbox
    that can't start, and names `merge_guard = "hook"` as the other way.
  - Doctor reports each as a failure where the lead would be refused, and
    a warning otherwise.
- **No MCP servers by default.** Every lead's Claude starts with
  `--strict-mcp-config --mcp-config <config dir>/sandbox/<lead>.mcp.json`,
  sandboxed or on `prefer` without its sandbox. That file holds only the
  servers `[lead] mcp_servers = ["name", …]` names, copied from the
  human's `~/.claude.json`: local scope for the lead's worktree first,
  then user scope. A name found in neither refuses the lead.
  - Never from the worktree's `.mcp.json`, which the lead can write.
    claude.ai connectors and plugins' servers have no definition there, so
    they can't be given to a lead.
  - `loopherd herds` shows each lead's `mcp_servers` and refuses a blank
    or repeated name. A lead can't change it: `herd set` is denied in its
    pane, and the config dir is write-denied.
  - A lead's own `--mcp-config` or `--strict-mcp-config` is refused, as
    `--settings` is. `restart` warns about a lead started before this,
    naming `revive --name` to resume it with the lock.
  - An allowed server runs outside the sandbox, with the human's access,
    and the lead can call any of its tools.
- **Not read: the lead's project and local settings.** With
  `allowUnsandboxedCommands: false` in `--settings`, Claude Code ignores a
  repo's `.claude/settings.json` and `.claude/settings.local.json`
  sandbox entries.

## Why

- **Tried, not taken from the docs.** With Claude Code 2.1.329, a lead's
  `--settings` and a temporary `CLAUDE_CONFIG_DIR` standing in for
  `~/.claude`:
  - user `excludedCommands` ran its command outside the sandbox, and user
    `allowWrite` opened its directory to writes;
  - user `sandbox.filesystem.disabled: true` turned off every filesystem
    rule, so a write anywhere succeeded;
  - user `permissions.additionalDirectories` and an `Edit(//…/**)` allow
    rule each opened their directory to writes, as Claude Code's sandbox
    docs say;
  - the same three sandbox keys in the worktree's
    `.claude/settings.local.json`, and `allowWrite` in
    `.claude/settings.json`, changed nothing.
- **A guard on the human's own config, not on an attacker.** The lead
  can't write `~/.claude`, so only the human puts these there, and the
  likeliest reason is their own work outside loopherd. Refusing by default
  makes the trade visible; `prefer` keeps it working once they've seen it.
- **Detection can miss.** A key Claude Code adds later, or one this list
  doesn't know, passes unseen. So does a loosening the human adds while a
  lead runs: Claude Code reloads settings files live, and only the next
  `restart`, `revive` or doctor sees it. A `CLAUDE_CONFIG_DIR` set where
  herdr starts the lead's Claude moves its user settings away from
  `~/.claude`, which is the only place loopherd reads. Launching leads without user settings at
  all (`--setting-sources project,local`, with loopherd's hooks moved into
  the lead's own settings file) is the stronger fix if this proves leaky;
  it's left unbuilt because it also drops the human's model, theme and
  other preferences from every lead.
- **MCP is a way out of the sandbox.** The sandbox covers Bash only; MCP
  servers run beside it, so a browser-driving server, say, lets a lead act
  as the human. Tried with Claude Code 2.1.329: `--strict-mcp-config` with
  an empty config dropped user-scope stdio and HTTP servers and both
  claude.ai connectors (33 MCP tools to 0), and a live test starts a lead
  in the dev session and checks it has none. With `playwright` allowed, it
  had playwright's tools and no others.
- **What still runs outside the sandbox.** The human's hooks run in every
  lead, unsandboxed, as they do for the human; a lead can't add one or
  invoke one at will, since `~/.claude` and the repo's settings are
  write-denied. Managed settings under `/etc/claude-code` outrank
  everything here and need root to change, so they're the machine owner's.
