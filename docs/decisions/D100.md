# D100

## Decision

Amends D89's "The human's own settings" gap (LH-304). loopherd reads the
settings Claude Code would merge into a lead's sandbox and acts on what
loosens it, and starts each lead with only the MCP servers its herd names.

- **What's read.** The human's `~/.claude/settings.json`, and the
  `.claude/settings.json` and `.claude/settings.local.json` of the lead's
  worktree, at `lead`, `revive` and `restart` of a lead, and in
  `loopherd doctor` for each herd with a `[lead]`. `lead` creates the
  worktree first, so a new one's checked-out project settings are read,
  and removes a worktree it just created when it refuses the lead, so a
  retry checks out origin afresh. A missing or zero-byte file is no
  finding, so the empty placeholders Claude's sandbox leaves at a
  worktree's `.claude/settings.json` and `.claude/settings.local.json`
  pass, as does an empty `~/.claude/settings.json`; an unreadable or
  unparseable one is a finding.
- **What's a finding.** Each entry or key, named with its file:
  - `sandbox.excludedCommands` in user settings: any command the lead's
    own settings don't already exclude.
  - Writes opened by user `sandbox.filesystem.allowWrite`, or, in any of
    the three files, by `permissions.additionalDirectories`: any path that
    isn't exactly one the lead may already write. A path beneath one
    counts too, since the lead could plant a symlink there before the
    path exists. A relative path or `..` counts.
  - `permissions.allow` rules for a tool that writes files, in any of the
    three: a bare `Edit`, `Write`, `MultiEdit` or `NotebookEdit`, or one
    whose path is `*` or `**`, matches every file. Another `Edit(…)` rule
    counts unless its path, up to its first wildcard, lies beneath one the
    lead may already write; a `Write`, `MultiEdit` or `NotebookEdit` rule
    with any other path matches nothing. An allow rule must match both a
    path and where it resolves, so a symlink beneath the worktree doesn't
    carry it out. `//` starts a rule's path at `/`, `~/` at home, `/` at
    `~/.claude` in user settings and at the worktree in its own, and a
    bare path at the worktree, the lead's working directory; `..` counts.
  - `permissions.defaultMode: "bypassPermissions"` in any of the three:
    the file tools then write anywhere without asking.
  - `sandbox.filesystem.allowRead`: any path the lead's own settings don't
    list, for a `credentials` lead only. It carves into `denyRead`, which
    only that lead has.
  - `sandbox.filesystem.disabled`, `sandbox.enableWeakerNestedSandbox`,
    `sandbox.allowNestedUserNamespaces`,
    `sandbox.enableWeakerNetworkIsolation`, `sandbox.allowAppleEvents`,
    `sandbox.network.httpProxyPort`, `sandbox.network.socksProxyPort`,
    and macOS's `sandbox.network.allowLocalBinding`,
    `sandbox.network.allowMachLookup` and
    `sandbox.network.allowUnixSockets` (D105), in user settings: set to
    anything but `false` or an empty list, which opens nothing. A proxy port hands the lead's network to the human's
    proxy, which turns off Claude Code's own network checks, the one on
    local addresses such as `169.254.169.254` and loopback included. The
    macOS keys count on every OS, since a settings file can move between
    machines.
  - Booleans the lead's own `--settings` sets (`enabled`,
    `failIfUnavailable`, `allowUnsandboxedCommands`) aren't findings, since
    `--settings` outranks user settings for them. `permissions.allow`
    rules for other tools aren't either: Bash runs in the sandbox
    whatever its rules say, and reading tools don't write.
  - Not checked: `network.allowedDomains`. The lead's own settings open
    every host already.
- **What `[lead] sandbox` does with them.**
  - `require` refuses to start the lead, naming each file and key: `lead`
    fails, `revive` reports `failed <lead>: sandbox: …`, and `restart`
    refuses to clear it.
  - `prefer` starts or keeps it sandboxed and prints each as a warning;
    `lead` also notes them in its mailbox. It isn't flagged
    `unsandboxed`.
  - `merge_guard = "credentials"` refuses under both, as for a sandbox
    that can't start, and names `merge_guard = "hook"` as the other way.
  - Doctor reports each as a failure where the lead would be refused, and
    a warning otherwise, even where the lead's own settings can't be built
    (a credentials herd missing its token, say): it then judges them
    against none of the lead's own.
- **No MCP servers by default.** Every lead's Claude starts with
  `--strict-mcp-config --mcp-config <config dir>/sandbox/<lead>.mcp.json`,
  sandboxed or on `prefer` without its sandbox. That file holds only the
  servers `[lead] mcp_servers = ["name", …]` names, copied from the
  human's user scope (`mcpServers` in `~/.claude.json`). A name not found
  there refuses the lead, and doctor reports it as a failure.
  - Never from local or project scope. Claude Code keys a git worktree's
    local scope by its main checkout, which members (unsandboxed) can
    write through Claude, and the worktree's `.mcp.json` is the lead's
    own. claude.ai connectors and plugins' servers have no definition in
    user scope, so they can't be given to a lead either.
  - `loopherd herds` shows each lead's `mcp_servers` and refuses a blank
    or repeated name. A lead can't change it: `herd set` is denied in its
    pane, and the config dir is write-denied.
  - A lead's own `--mcp-config` or `--strict-mcp-config` is refused, as
    `--settings` is; `revive` drops them, with all their values, from a
    lead record kept before this. `restart` warns about any lead running
    without the lock, sandboxed or not, naming `revive --name`.
  - An allowed server runs outside the sandbox, with the human's access,
    and the lead can call any of its tools.
- **A lead's own args: an allowlist (LH-316).** Its args from every
  source (`[lead].args`, else the herd's `args`, then the command line) may
  be only `--model <value>`, `--effort <value>`, `--verbose`, and
  `--permission-mode` with `default`, `manual`, `auto` or `plan`, each flag
  that takes a value also as `--flag=value`. Any other arg, or an allowed flag with another value or
  none, is a finding treated as a settings loosening is, at `lead`,
  `revive` and `restart`, named with the values that follow it and where it
  was set. `lead`, and `lead --dry-run`, name the herd file entry or the
  command line, and where the arg is the herd's shared `args` say to give
  the lead its own `[lead].args`, since dropping it would change the
  workers too; `revive`
  and `restart` judge the args loopherd kept when the lead started, so they
  name those and say to retire it and start it again. Doctor reports the
  herd file's as `herd <h> lead args`, one finding per arg and per launch
  flag. Under `require`, a lead started with an arg the list no longer
  covers can't be restarted or revived until the human retires it and runs
  `lead` again. The flags loopherd adds itself
  (`--settings`, `--strict-mcp-config`, `--mcp-config`) aren't the human's
  args: kept ones are dropped before the check, and a human's own are still
  refused under both modes, as above, which doctor reports as a failure.
- **The worktree's settings: permissions only.** With
  `allowUnsandboxedCommands: false` in `--settings`, Claude Code ignores a
  repo's `.claude/settings.json` and `.claude/settings.local.json`
  sandbox entries, so those aren't read. Their `Edit(…)` rules and
  `additionalDirectories` still steer the file tools, which run outside
  the sandbox, so those are.

## Why

- **Tried, not taken from the docs.** With Claude Code 2.1.329, a lead's
  `--settings` and a temporary `CLAUDE_CONFIG_DIR` standing in for
  `~/.claude`:
  - user `excludedCommands` ran its command outside the sandbox, and user
    `allowWrite` opened its directory to writes;
  - user `sandbox.filesystem.disabled: true` turned off every filesystem
    rule, so a write anywhere succeeded;
  - user `permissions.additionalDirectories` and an `Edit(//…/**)` allow
    rule each opened their directory to writes, as Claude Code's sandbox
    docs say;
  - the same three sandbox keys in the worktree's
    `.claude/settings.local.json`, and `allowWrite` in
    `.claude/settings.json`, changed nothing. Claude Code's sandbox docs
    say the file tools still follow a repo's `Edit(…)` rules and
    `additionalDirectories`, which these experiments didn't cover.
- **Rules, not a lock, for the file tools.** Setting
  `permissions.blockWritesOutsideWorkingDirectories` in the lead's own
  settings would refuse its file tools' writes outside its working
  directories whatever the rules say, but its handoff and mailbox are
  outside its worktree, so they'd need to become working directories,
  and user or project `additionalDirectories` would still add more. It's
  left for a later change; this one reads the rules.
- **A guard on the human's own config, not on an attacker.** The lead
  can't write `~/.claude`, so only the human puts these there, and the
  likeliest reason is their own work outside loopherd. Refusing by default
  makes the trade visible; `prefer` keeps it working once they've seen it.
- **Detection can miss.** A key Claude Code adds later, or one this list
  doesn't know, passes unseen. So does a loosening the human adds while a
  lead runs: Claude Code reloads settings files live, and only the next
  `restart`, `revive` or doctor sees it. A `CLAUDE_CONFIG_DIR` set where
  herdr starts the lead's Claude moves its user settings away from
  `~/.claude`, which is the only place loopherd reads. Launching leads without user settings at
  all (`--setting-sources project,local`, with loopherd's hooks moved into
  the lead's own settings file) is the stronger fix if this proves leaky;
  it's left unbuilt because it also drops the human's model, theme and
  other preferences from every lead.
- **MCP is a way out of the sandbox.** The sandbox covers Bash only; MCP
  servers run beside it, so a browser-driving server, say, lets a lead act
  as the human. Tried with Claude Code 2.1.329: `--strict-mcp-config` with
  an empty config dropped user-scope stdio and HTTP servers and both
  claude.ai connectors (33 MCP tools to 0), and a live test starts a lead
  in the dev session and checks it has none. With `playwright` allowed, it
  had playwright's tools and no others. No plugin with an MCP server was
  installed to try, so dropping plugins' servers rests on the flag's
  documented "only these configs".
- **An allowlist for args, not a denylist.** `--add-dir`,
  `--allowedTools Write`, `--permission-mode bypassPermissions` and
  `--dangerously-skip-permissions` each loosen a lead as the settings keys
  above do, and a list of those misses the next flag Claude Code adds. The
  four allowed forms pick a model, effort, output or a permission mode that
  still asks or classifies; a lead that needs another is started under
  `prefer`, where the arg is a warning. The human chose this on
  2026-11-20, and added `manual` on 2026-11-21 (LH-357): Claude Code
  2.1.329's `--help` names that mode and keeps `default` only as a hidden
  alias for it.
- **What still runs outside the sandbox.** The human's hooks run in every
  lead, unsandboxed, as they do for the human; a lead can't add one or
  invoke one at will, since `~/.claude` and the repo's settings are
  write-denied. Managed settings under `/etc/claude-code` outrank
  everything here and need root to change, so they're the machine owner's.
