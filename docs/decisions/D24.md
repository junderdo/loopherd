# D24

## Decision

`loopherd view` reads again whenever herdr pushes an event, instead of
waiting for D13's 2s poll. It holds two `events.subscribe` connections on the
socket `Herdr::socket()` names: a lifecycle one (`pane.created`,
`pane.closed`, `pane.agent_detected`) and a status one with a
`pane.agent_status_changed` entry for each live pane the view shows (members
and listed strays). When that pane set changes, the status connection is
replaced. A `pane_not_found` rejection triggers a read, and the retry
subscribes to the panes that read finds.

Events are invalidation signals. Any pushed event, of any kind or spelling,
requests the view's existing read at once. If a read is already in flight,
one more follows it. The view never patches itself from an event's data.

While the lifecycle connection is up, the status connection covers the shown
panes, and the last read had no trouble with herdr, the periodic read slows
to every 10s, because the ledger and mailbox push no events. Otherwise
(disconnected, failing to subscribe, after `events_lost`, or after a read
that couldn't see herdr's panes) it polls every 2s as before. It retries
subscribing with a backoff that starts at 1s and doubles to a 30s cap. The
backoff starts over only after the connections stay up for 30s, so a herdr
that keeps accepting and then dropping still backs off. A `pane_not_found`
keeps the lifecycle connection and resubscribes status as soon as the read
it triggers brings the new pane list.

## Why

A blocked member should show at once, not up to 2s later. herdr has no
global status subscription, and a connection's subscription set is fixed
([research](../research/herdr-events.md)). Hence the per-pane connection that
is replaced as a whole. Treating events as invalidations keeps one read path,
so the view can't drift from what `status` shows. The 2s poll stays as the
fallback, so a herdr without the socket works as it did.
