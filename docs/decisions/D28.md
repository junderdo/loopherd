# D28

## Decision

A herd file may set a top-level `after_merge = ["<cmd>", …]`. `loopherd feed`
runs it in the herd's `repo`, in order, stopping at the first failure, once
per member: the first time that member's template `merged` check passes. It
runs whether or not the herd is paused, since a pause stops spawning, not
cleanup.

Feed records the member's after_merge in the ledger as pending, with its
own PID and start time, while it holds `feed.lock`. It then releases that
lock and runs the commands under its own `after-merge.lock`, holding it
across all its members, so two live feeds' after_merge never overlap. Other
feeds, `add` and the leads' claimable checks are not locked out while
`scripts/install` builds. Each command may run for 30 minutes.

The outcome goes to the member's mailbox as a `note`: `after_merge ok`, or
the failing command with its exit (or timeout) and the last 20 lines of its
combined output, cut to their last 4000 bytes. Feed marks the member's
after_merge noted in the ledger, then writes the note. Until it's marked,
every feed keeps the member, done or not. Once it's marked, the next feed
runs its `done` check. A lead's watch counts no slot free for a member that
feed would keep: one pending, or one merged whose after_merge is still due.
It wakes the lead with `<member> merged` for the latter even once `done`
passes, since feed is what runs the commands. A watch reads only unretired
members' mailboxes, so reaping the member any sooner would hide the note. `--dry-run` runs the
`merged` checks and prints the commands it would run.

While after_merge is due:

- A `merged` check that errors keeps the member, done or not, and feed warns.
- A `done` check that passes before `merged` does retires the member, with a
  warning and a note that after_merge never ran. That also fires for a PR
  closed unmerged, so the note says to run the commands only if it merged.
- A template with no `merged` check gets a warning from `herds` and from
  `feed`.

When feed runs in a lead's pane, each command is classified with the tool
hook's matcher. If any of them needs a switch the lead's `[lead]` leaves off
(`install`, `rebase`, `merge`), none of them run, and the note names the
command and the switch. The same goes for a command no switch allows
(`loopherd pause`, `restart --force`), and for a herd file that can't be read,
which counts every switch off. Those notes say so. The held-back run counts
as done: a later feed from another pane doesn't retry it.

Limits:

- After a held-back run, the commands are the human's to run by hand.
- A feed that exits after recording a pending after_merge but before noting
  it, whether killed (a Bash tool's timeout, say) or failing on an error,
  leaves no outcome. A lead's watch wakes the lead with `<member>
  interrupted` once the recorded process is gone. The next feed then marks
  the after_merge noted, only if it is still pending on that process, and
  notes it as interrupted with no outcome. It runs none of the commands
  again, and keeps the member until the feed after that.
- If the ledger can't mark it noted, feed prints the outcome with a
  warning and writes no note; the next feed notes it as interrupted. If
  the mailbox can't be written, feed prints the outcome with a warning,
  and the outcome is only in feed's output. The member retires on the next
  feed whose `done` check passes.
- A feed killed after marking it noted but before writing the note leaves
  no note and wakes nobody; the outcome is only in that feed's output.
- A killed feed's commands run in their own process group and can outlive
  it. Its `after-merge.lock` drops with it, so the next feed's commands can
  overlap them. Run feed in the background when the herd has after_merge.

## Why

The steps after a merge (pull, install, unblock dependents) are routine and
the same every time, so they belong in the herd file rather than in the
shepherd's or lead's judgement. A command feed runs as a child process never
passes the PreToolUse hook, so feed applies the hook's rules itself.
Running none rather than some keeps a half-done sequence (pulled but not
installed) from looking finished. Recording the run before the commands
start, rather than after, means a crash can lose the outcome but never
repeat an install; the recorded owner lets the next feed tell a run in
progress from a dead one. Per-template `after_merge`, retries, and steps for PRs closed
unmerged are left out until a herd needs them.
