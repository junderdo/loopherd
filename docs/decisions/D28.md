# D28

## Decision

A herd file may set a top-level `after_merge = ["<cmd>", …]`. `loopherd feed`
runs it in the herd's `repo`, in order, stopping at the first failure, once
per member: the first time that member's template `merged` check passes. The
ledger marks the member (`after_merge_ran`) before the first command runs, so
a crash mid-run never runs it twice, and a failure or a held-back run is
never retried.

The outcome goes to the member's mailbox as a `note`: `after_merge ok`, or
the failing command with its exit and the last 20 lines of its combined
output. A member whose `after_merge` ran keeps its slot until the next feed,
which runs its `done` check; a watch reads only unretired members' mailboxes,
so reaping it in the same run would hide the note. `--dry-run` runs the
`merged` checks and prints the commands it would run.

When feed runs in a lead's pane, it classifies each command with the tool
hook's matcher. If any needs a switch the lead's `[lead]` leaves off
(`install`, `rebase`, `merge`), it runs none of them and notes which command
needs which switch. Each command may run for 30 minutes.

## Why

The steps after a merge (pull, install, unblock dependents) are routine and
the same every time, so they belong in the herd file rather than in the
shepherd's or lead's judgement. A command feed runs as a child process never
passes the PreToolUse hook, so feed has to apply the hook's rules itself;
running none rather than some keeps a half-done sequence (pulled but not
installed) from looking finished. Per-template `after_merge`, retries, and
steps for PRs closed unmerged are left out until a herd needs them.
