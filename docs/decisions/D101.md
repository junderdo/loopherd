# D101

## Decision

Amends D89 (LH-306).

- **Sparse repos work.** loopherd's pinned worktree git no longer refuses
  a repo just because it sets `extensions.worktreeConfig`. Before each
  call it reads the `config.worktree` git would read for that call's
  directory: the one in that checkout's git dir. It refuses only when the
  file sets a key other than `core.sparseCheckout`,
  `core.sparseCheckoutCone` or `index.sparse`, naming the file and key.
- **The worktree-location check is a lead's.** A herd member's worktree
  must sit beside its herd's worktrees only when a lead runs loopherd.
  The human and the shepherd can `retire --close` or `release` a member
  whose worktree `ensure_worktree` reused from wherever the human made
  it. The repo must still match the herd file for everyone.
- **A gone herd file.** For the human and the shepherd, an entry whose
  herd file no longer exists is checked like a hand-spawned one (lead
  worktrees and the state dir only). A lead is still refused.

## Why

- `git sparse-checkout init` turns on `extensions.worktreeConfig` and
  writes `core.sparseCheckout` into `.git/config.worktree`. So refusing on
  the extension, or on the file existing, refuses every sparse repo.
  Sparse checkout's own keys run no command, so allowing only them keeps
  what D89's refusal protected: no `core.fsmonitor`, `core.sshCommand`,
  `core.hooksPath` or `include.path` from a file the lead can write.
- The file is read just before git runs, so a lead that rewrites it in
  between gets past the check. Refusing the whole repo didn't race, but it
  broke ordinary repos. This is the same gap D89 already lists for git
  that others run in the repo.
- The location check stops a forged entry in a lead's own herd from
  pointing that lead's `retire --close` or `release` at a worktree
  elsewhere. The human chose where their own worktrees go, and
  `ensure_worktree` reuses one wherever it is, so holding the human to the
  herd's dir only stranded their members. The repo check stays for
  everyone, because a forged repo is where a lead's git config would run.
