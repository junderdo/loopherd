# D101

## Decision

Amends D89 (LH-306).

- **Sparse repos work.** loopherd's pinned worktree git no longer refuses
  a repo just because it sets `extensions.worktreeConfig`. Before each
  call it reads every `config.worktree` of the repo: the main checkout's,
  each linked worktree's admin dir's, and the one in the call's own git
  dir. A git call can start git in another worktree (`worktree remove`
  runs `status` in the one it removes), so the call's own file isn't
  enough. It refuses when any of them sets a key other than
  `core.sparseCheckout`, `core.sparseCheckoutCone` or `index.sparse`,
  naming the file and key.
- **The worktree-location check is a lead's.** A herd member's worktree
  must sit beside its herd's worktrees only when loopherd sees a lead
  calling it, by an ancestor Claude started with a lead's settings file.
  Without one (the human, the shepherd, or a hook-only lead on `prefer`)
  the caller can `retire --close` or `release` a member whose worktree
  `ensure_worktree` reused from wherever the human made it. The repo must
  still match the herd file for everyone.
- **A gone herd file.** With no lead caller seen, an entry whose herd
  file no longer exists is checked like a hand-spawned one (lead
  worktrees and the state dir only). A lead is still refused.

## Why

- `git sparse-checkout init` turns on `extensions.worktreeConfig` and
  writes `core.sparseCheckout` into `.git/config.worktree`. So refusing on
  the extension, or on the file existing, refuses every sparse repo.
  Sparse checkout's own keys run no command, so allowing only them keeps
  what D89's refusal protected: no `core.fsmonitor`, `core.sshCommand`,
  `core.hooksPath` or `include.path` from a file the lead can write.
- The files are read just before each git call starts, so a lead that
  writes one in between gets past the check. Refusing the whole repo
  didn't race, but it broke ordinary repos. This is the same gap D89
  already lists for git that others run in the repo.
- The location check stops a forged entry in a lead's own herd from
  pointing that lead's `retire --close` or `release` at a worktree
  elsewhere. The human chose where their own worktrees go, and
  `ensure_worktree` reuses one wherever it is, so holding the human to the
  herd's dir only stranded their members. The repo check stays for
  everyone, because a forged repo is where a lead's git config would run.
- Without the location check, a forged entry in a lead's herd can have
  the human's `retire --close` or `release` remove any clean worktree of
  the herd's repo, not only one in its worktrees dir. D89's open items
  say so; check a member's `worktree` in the ledger before closing it.
