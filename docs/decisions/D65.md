# D65

## Decision

The herdr plugin declares a `view` pane, `placement = "popup"` at 80% of
the width and height, running `sh loopherd.sh view`, and a `view` action
(`loopherd.view`) that runs `open-view.sh`, which asks `$HERDR_BIN_PATH`
(else the `herdr` on `PATH`) to open that pane. `loopherd view` needs no
`HERDR_PANE_ID` and reaches herdr through the `HERDR_SOCKET_PATH` herdr
hands it; `q` and Escape end it, which closes the popup. The manifest's
`min_herdr_version` rises to 0.7.4, the release that added popup panes.

`loopherd.sh` now appends `$HERDR_BIN_PATH`'s directory to `PATH` after
finding loopherd, so loopherd's `herdr` calls still work when the server's
`PATH` lacks herdr, without that directory shadowing the user's loopherd,
`git` or `gh`.

The README and skill give the `[[keys.command]]` snippet, on `prefix+m`,
unbound in herdr 0.9.5's defaults; nothing writes the human's herdr config.

The live test starts a herdr server of its own with a throwaway home
rather than linking through `loopherd-dev`, which runs as the human and so
registers plugins in the human's home (D62). It opens the popup through
both the pane and the action and checks the view's environment. Opened as
a pane, the view quits by itself (SIGTERM, its clean exit path, as on
`q`); opened by the action, herdr's `popup.close` ends it. Either way the
test waits for no loopherd to be left and for `popup.close` to answer
`popup_not_open`. herdr has no way to type into a popup, so `q` and Escape
are tested on a pty in `tests/view.rs`.

LH-226 settled it.

## Why

A popup is the one placement that overlays any focused pane without
changing the layout, and closing with the command is what makes quitting
the view close it. An isolated server is the only live test that links the
plugin and opens a pane without touching the human's herdr.
