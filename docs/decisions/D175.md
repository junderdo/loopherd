# D175

## Decision

Amends D144 (LH-493). A credentials member's file tools can't read `/proc`.

- **A PreToolUse hook in the member's own settings.** `confine_credentials`
  adds a hook on `Read|Grep` running the hidden `loopherd file-hook`, by the
  absolute path of the loopherd that wrote the settings. It refuses any path
  that lands in `/proc`, or on `/` (a Grep from there would search
  `/proc`). A leading `~` is expanded from `HOME`, and the path is taken
  against the call's `cwd` with `..` removed as text, then walked one
  component at a time, reading each symlink with `read_link`. Each link's
  target is checked as written, and with the rest of the path after it, as
  well as the fully followed path. Any of these landing in `/proc` refuses
  the call. A target is checked as written because `/proc/self` in it names
  the process reading it: Claude, not the hook, so a link to
  `/proc/self/task/<claude pid>/environ` that doesn't resolve in the hook is
  still refused. A link the hook can't read, or links that loop, refuse the
  call, as does input it can't read, such as a Read without `file_path`.
- **It fails closed.** Unlike the hooks install-hook adds (`|| true`), a
  file-hook that can't run exits 2, and the hook sets `onFailure: "block"`
  so one that times out refuses the call too.
- **Which loopherd wrote the command isn't a switch.** restart compares a
  running lead's settings with its herd's without the binary's path, so a
  lead started by another loopherd doesn't warn.
- **The settings set `disableAllHooks: false`**, which as `--settings` sits
  above the user's and the project's settings, so neither can turn the guard
  off.
- **The live test** has a credentials lead call Read on
  `/proc/self/environ`, `/proc/<its Claude's pid>/environ` and a symlink to
  `/proc/self/environ`, each refused, and run `ls /proc/<its Claude's pid>`
  in its sandbox, which finds nothing.

## Why

- **No `Read` deny can do it** (D144 Limits): Claude Code hands Read denies
  to bubblewrap too, where `//proc/**` hides the `/proc` loopherd reads and a
  glob breaks every sandbox start.
- **Stripping the tokens from Claude's starting environment isn't enough.**
  The pane's shell, herdr and the human's other processes run as the same
  user and keep them in their own `environ`.
- **Only credentials members carry it.** A global hook would refuse the
  human's own sessions too, and these settings are the ones the member can't
  edit.
- **Claude Code 2.1.332 has a device guard of its own**, which refused the
  live test's direct `/proc/<pid>/environ` Reads ("a device or process
  file") before any hook ran. The symlink's Read reached the hook, which
  refused it. The hook still covers versions without that guard, and the
  guard's exact reach isn't documented.

## Limits

- **A race between parallel calls.** The hook checks the path, then Read
  opens it. A Bash call run alongside could swap a checked file for a symlink
  into `/proc` in between.
- **A sandboxed command can't reach Claude's `environ`**: bubblewrap starts
  with `--unshare-pid` and a fresh `/proc` (D144), and the live test shows
  `/proc/<claude pid>` missing from inside. The weaker nested sandbox would
  reopen this.
- **A member started before this change** keeps settings without the hook
  until its Claude starts again. restart warns about a lead's; a worker gets
  no warning.
- **Managed settings** with `disableAllHooks` or `allowManagedHooksOnly`
  still turn the guard off; they're the machine's administrator's.
- **This Claude Code has no Grep tool**, so the live test doesn't exercise
  Grep; the unit tests do.
