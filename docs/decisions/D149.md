# D149

## Decision

A sandboxed lead gates a merge through its broker (D98): `loopherd gate
<sha>` runs the herd file's `[lead] gate` commands outside the sandbox, so
tests that need Unix sockets pass with `unix_sockets` unset (D105). Chosen
over socket tests that skip in a socketless sandbox. Ends the stopgap of
2026-11-21, where the shepherd gated each reviewed PR and told the lead to
merge (LH-419).

- **Commands come from the herd file.** `[lead] gate = ["<cmd>", …]`, run
  in order with `sh -c`, stopping at the first failure, each within an
  hour. Unset, the broker refuses `gate`. `loopherd herds` shows them as
  `gate:`. A lead can't set it (the tool hook denies `herd set`).
- **What it checks.** The sha must be 7 to 40 hex digits naming a commit
  that, after a fetch, is in the history of a branch `git ls-remote --heads
  origin` lists; anything else is refused before a worktree is touched. The
  fetch prunes nothing, since `release --keep-branch` and `ensure_worktree`
  read a gone branch's tracking ref. The broker checks the commit out
  detached in the lead's own worktree `loopherd-gate-<lead>` beside the
  herd's repo and merges the base into it, then cleans untracked files
  after the checkout and again after the merge, so the tree is exactly
  the sha merged with the base, plus ignored build output.
- **The base.** Origin's default branch, the base of every PR a worker
  opens unstacked, and what the lead merges into. `--base <branch>` names
  another of origin's branches, for a stacked PR (its parent's branch) or
  one into a release branch; it must be a branch `git ls-remote --heads
  origin` lists, else the gate is refused before a worktree is touched.
  The broker doesn't read the PR's base from GitHub: a lead passes what
  `gh pr view <n> --json baseRefName` says, and a wrong base gates against
  the wrong tree but widens no reach. Every git call a
  gate makes runs with `core.hooksPath=/dev/null`, and the merge with
  `merge.ff=true` and no signing, so neither hooks nor the broker's git
  config turn a clean merge into a failure.
- **Its worktree.** Reused, with its ignored files kept, so a build cache
  survives between gates. `git worktree prune` first recovers one deleted
  by hand, and a stale `index.lock` is removed, since a lead's gates run
  one at a time. A worktree at that path with a branch checked out is a
  member's, and is refused untouched.
- **Answer.** `gate <sha> merged with origin/<base> <base sha>: pass`, exit
  0; or `: failed:` naming the command and its exit, then the last 20
  lines of its output, exit 1. A merge that conflicts fails unrun, listing
  the conflicting files, exit 1; any other merge error is an error, not a
  failed gate.
- **Lane.** Gates run one at a time in a fourth lane of their own, beside
  herd changes, status and quick requests. Each command may take an hour;
  a lead waits four hours plus D98's origin wait for the whole gate, so it
  runs `gate` as a background task.
- **Environment.** The broker's, as for `after_merge`: the launch record's
  `PATH`, and on a `credentials` herd the lead's narrowed credentials.
- Run directly (the shepherd's pane, an unled herd), `gate` refuses: run
  the checks directly.

## Why

Skipping socket tests would make the lead's gate pass without running
them, leaving CI or the shepherd to run them; a gate that skips what it
can't run says pass on less than the full gate. The broker already runs
`after_merge` from the herd file outside the sandbox, so the gate is one
more operation of the same shape, and needs no socket reopened.

## What remains

- The gate runs the checked commit's code (build scripts, tests) outside
  the sandbox. Requiring it on origin means the lead must push it first,
  as workers' PRs are; workers already run unsandboxed (LH-284).
- The lead can write the repo's shared `.git` (D89), config included, so a
  planted setting could still run a command in the broker's git, as for
  every other broker git call.
- The commands have no shared deadline: a gate of more than four
  hour-long commands, or one queued behind other gates, can outlast its
  lead's wait, and runs on with nobody reading its answer.
- Nothing removes `loopherd-gate-<lead>`; it stays, with its build cache,
  after its lead retires.
