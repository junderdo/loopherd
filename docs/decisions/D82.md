# D82

## Decision

After its handoff, the human resumes the shepherd with a plain `/clear` and
any short message in its pane. Amends D20's shepherd handoff, which had the
human paste `continue as the loopherd shepherd from <path>` after `/clear`;
that line stays as the fallback.

- **Record.** The watch that prints `shepherd handoff`, as it marks
  `handoff-asked/<session>`, writes `$XDG_STATE_HOME/loopherd/shepherd.json`:
  its `$HERDR_PANE_ID`, its herdr socket, the measured Claude session, that
  Claude's process (PID and start time), the time (RFC 3339, nanoseconds)
  and `used: false`, replacing any earlier record. A watch without a pane or
  socket writes none. A failed write fails the mark, so the line comes back
  on the next watch; rewriting an unused record of the same session and
  place keeps its time, so a handoff written in between still counts.
- **Resume.** The SessionStart hook, on source `clear` only, when the
  caller's pane, socket and Claude process (`$CLAUDE_PID`, counted only as
  an ancestor) equal the record's, the record is unused, and
  `handoffs/shepherd.md` was modified after the record's time: marks the
  record used, then moves the handoff to `shepherd.prev.md`, and prints
  `additionalContext` telling the new session it is the shepherd resuming,
  to run `loopherd --skill`, read the handoff at its `.prev.md` path (naming
  when it was written), run `loopherd status` and `loopherd reports --all
  --tail 40`, re-arm its watch and continue from the handoff's next steps.
  Marking first means a failed move leaves the handoff where the fallback
  line names it; a session given the fallback after a resume already moved
  it reads `shepherd.prev.md` beside it.
- **Otherwise nothing.** Any other source, place, a used record, a missing
  record or handoff, or a handoff not newer than the record adds nothing. A
  failure in this path warns on stderr and the hook still exits 0 and runs
  its member path unchanged. A record never expires; a second `/clear`
  after a used one adds nothing until the next handoff writes a new record.
- **The Claude process stands for the session.** Probed in `herdr --session
  loopherd-dev` on Claude Code 2.1.327: a `/clear` hook's input carries only
  the new `session_id`, and `sessions/<pid>.json` already names the new
  session when the hook runs, so the hook can't see which session was
  cleared. `/clear` keeps the Claude process, and a continuation (D33) stays
  in it, so the process match covers the recorded session and any session it
  continued in. The recorded session id is kept for the record's reader.
- **Probed** in the same session: Claude Code applies a SessionStart hook's
  `additionalContext` on `/clear` (the cleared session answered from it),
  and with `loopherd session-hook` installed, a record for that pane and
  Claude plus a newer handoff resumed the cleared session from
  `shepherd.prev.md` and marked the record used.
- **Skill.** "Your own handoff" step 3 tells the human to run `/clear` and
  send any message (e.g. `go`), with the paste line as the fallback.

## Why

Grilled on LH-273 (2026-11-18). The shepherd isn't a ledger member and the
human types in its pane, so D78's `restart --self` for leads doesn't fit.
Pasting a long path after `/clear` was the one manual step left in a
handoff. Rejected:

- **An automatic self-restart now.** It would type `/clear` into the
  human's pane; left for its own grilling card.
- **`loopherd restart --shepherd` typing into the pane.** It races whatever
  the human is typing there.
- **Resuming any non-member pane.** A `/clear` in an unrelated Claude
  would be told it is the shepherd; the record ties the resume to the pane,
  socket and Claude the watch measured.

Limits: a session the human `/resume`s inside the same Claude process before
the `/clear` still matches, since the process is the same; the handoff
being newer than the record keeps that to the handoff just written.
