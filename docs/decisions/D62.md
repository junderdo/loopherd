# D62

## Decision

loopherd ships as a herdr workflow plugin from `herdr-plugin/` in this repo,
installed with `herdr plugin install junderdo/loopherd/herdr-plugin`. Its
manifest has id `loopherd`, the crate's version (a test keeps them equal),
`platforms = ["linux", "macos"]` and `min_herdr_version = "0.7.0"`, the
release that added plugins with actions and `platforms`. It declares no
build commands.

The plugin requires `loopherd` already installed. It never runs
`scripts/install` or `loopherd install-hook`, so it never writes the Claude
hooks or skill. Every manifest command runs `sh loopherd.sh <args>`, a
wrapper that runs the `loopherd` on `PATH`, else `~/.local/bin/loopherd`
(the install dir, which herdr's server may not have on `PATH`), and
otherwise exits 127 naming the README's install section. The first command
is a `status` action; event hooks, startup hooks, panes and link handlers
come in their own cards.

The live test links the plugin into a throwaway herdr home: `HOME`,
`XDG_CONFIG_HOME` and `XDG_STATE_HOME` in a temp dir and `HERDR_SOCKET_PATH`
at a socket nothing listens on. It never links through a running server,
the dev one included ([research](../research/herdr.md#plugins-095-lh-223)).

LH-223 settled it, with the human's install and live-test choices.

## Why

D17 reserves installing the Stop hook to the shepherd or an `install = true`
lead, and a plugin build that ran `scripts/install` would write it into the
user's Claude settings on every `herdr plugin install` or `update`. Asking
for loopherd first keeps one install path. herdr registers plugins per user,
not per session, so the isolated home is the only way to link one in a test
without touching the human's live herdr.
