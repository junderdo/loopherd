# D129

## Decision

Every member, worker or lead, sandboxed or not, works in its own clone of
the repo, not in a linked worktree of the main checkout (LH-323, decided with
the human 2026-11-21). Amends D89, D104 and D107.

- **How a clone is made.** `feed`, `add` and `spawn` run `git clone
  --reference <main checkout> --dissociate <origin URL> <path>` at the same
  path as before (`worktree_path`). Origin keeps the URL as the main
  checkout's config spells it, so a credentials herd's `insteadOf` rewrite
  (D95) still matches, and the clone gets the main checkout's own `url.*`
  rewrites so it reaches origin the same way. The member's branch is then
  checked out as before: a local branch of the main checkout, else origin's
  branch, tracked, else a new branch from origin's default with no
  upstream. `loopherd lead` makes the lead's clone detached at origin's
  default. A reviewer's verify trees (`git worktree add` from the lead's
  tree) now hang off the lead's clone.
- **How loopherd knows its clones.** A clone's config carries
  `loopherd.checkout = <main checkout>`, read as data (`git config --file`,
  no includes), never by git working in the clone. A directory at a
  member's path without it is not loopherd's: it is refused, never
  removed. Origin's URL isn't compared, so changing the main checkout's
  origin doesn't orphan its members.
- **Removing a clone.** `retire --close`, a feed's reap and `release` delete
  the clone's directory under the rules `remove_if_merged` applied to a
  linked worktree: nothing uncommitted or untracked, no ignored file
  outside `target/` and `node_modules/`, no operation part way. A clone
  holds its branches, so every local branch in it must be merged into
  origin's default branch, not only the checked-out one; a detached HEAD's
  own commits stay unchecked, as before. A clone holding a submodule is
  kept (below). `release`'s count of commits a clone would lose covers all
  its branches.
- **loopherd's git never reads a clone's own `.git`.** D89 kept a member's
  config, hooks and `commondir` away from loopherd's git by pinning it to
  the main checkout's common dir. A clone's whole `.git` is its member's
  to write, and a per-file deny falls to a rename (D97), so loopherd reads
  a clone through a git dir of its own: copies of the clone's `HEAD`,
  branches, index and `info/exclude`, with the clone's objects (and the
  main checkout's) borrowed read-only as alternates. `git status` there runs
  with `--ignore-submodules=all`, since a submodule's git dir is the
  member's too; a clone holding one is never counted clean. The main
  checkout's git counts a clone's commits through
  `GIT_ALTERNATE_OBJECT_DIRECTORIES`.
- **Sandboxed workers.** Their settings also deny writes to their clone's
  own `.git/hooks` and `.git/config`, as D107 does for the shared `.git`,
  for git the human later runs there.
- **Members already in linked worktrees** keep working until retired:
  revive, retire, reap and release find and remove them as before. Nothing
  migrates them.

## Why

On Linux, Claude Code's sandbox holds an empty read-only
`<repo>/.git/config.lock` for the life of every sandboxed command
(claude-code#78818, D104). Linked worktrees share the main checkout's
`.git`, so one member's sandboxed build failed every `git config` write in
every worktree: the human's `git push -u`, cleanup's `git branch -D`,
other members' pushes. With a clone per member the placeholder lands in
that member's own `.git`, and a sandboxed lead's bind list no longer names
the main checkout's `.git/config.lock` (LH-425's bwrap failure). One
layout for every member, sandboxed or not, means no member is hit by
another's lock. The human doesn't rely on seeing members' branches in the
main checkout; branches travel through origin, as they already did.

## What changes

- **D104's remaining window is gone.** A reviewer's sandboxed build holds
  only the lead clone's placeholder.
- **D107's "placeholder accepted while opt-in"** is settled here; making
  `[worker] sandbox = "require"` the default is still a later decision.
- **The main checkout sees members' branches only through origin.**
  `release --keep-branch`, which never asks origin, reports origin's
  branch from the main checkout's last fetch; a member's push no longer
  moves that tracking ref by itself.
- **Each spawn fetches from origin** into the new clone, borrowing the main
  checkout's objects while it copies. A local fast path was left out of
  scope; file a card if spawns prove slow.
- **`loopherd spawn` without `--repo`, run inside a member's clone,** takes
  the clone as its repo, where a linked worktree resolved to the main
  checkout.
