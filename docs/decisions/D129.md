# D129

## Decision

D114's "Workers must be sandboxed" rule, built now that `[worker] sandbox`
exists (LH-340, LH-342; built by LH-360). Amends D114 and D128.

- **Refused, not warned.** `lead` and `revive` refuse a credentials lead
  whose herd's `[worker] sandbox` is `off`, unset or `prefer`, under either
  `[lead] sandbox` mode, naming `loopherd herd set <herd> worker.sandbox
  '"require"'` or `lead.merge_guard '"hook"'`. D114's interim warning is
  gone.
- **`prefer` is refused too,** although D128 already refuses to start an
  unsandboxed worker under it in a credentials herd.
- **An invalid herd.** `loopherd herds` calls such a herd file invalid, so
  doctor fails on it and `herd set` refuses an edit that would make one.
  This replaces D128's doctor warning for `off`, and makes invalid the
  credentials herd with `[worker] sandbox = "off"` and `unix_sockets =
  "all"` that D128 left valid.
- **init** writes `[worker] sandbox = "require"` into a credentials herd.

- **Upgrading.** A credentials herd file without the switch, including one
  from an older `init`, is invalid and its lead won't start until the human
  runs `loopherd herd set <herd> worker.sandbox '"require"'`.

## Why

- **Sandbox both or neither** (D114): a hijacked lead can `tell` or `feed` an
  unsandboxed worker to merge as the human.
- **One value, not a behavior to reason about.** Under `prefer` a
  credentials worker is already refused rather than started unsandboxed
  (D128), but the rule a human can check in the herd file is "`require`",
  and it doesn't lean on that refusal staying in place.
- **Invalid rather than warned,** as D114 did for credentials with open
  sockets: a herd its lead can't start with shouldn't pass `herds`.
