# D89

## Decision

Each lead's Claude runs in the Claude Code sandbox, as D83 decided, from a
settings file loopherd writes for it (LH-280).

- **The file.** `<config dir>/sandbox/<lead>.json`, passed as `claude
  --settings <file>`.
  - `lead` writes the file before starting the lead, and beside it
    `<lead>.lead.json`: the lead's herd and its Claude args without the
    settings. A lead given its own `--settings` is refused, since that
    flag is its sandbox's.
  - `revive` trusts `<lead>.lead.json` over the ledger, which the lead can
    write. Whether an entry is a lead, its herd, its args, and its
    worktree (where `lead` puts it in the herd's repo) all come from that
    file and the herd file. It rewrites the settings from the herd's
    current switches and resumes the lead in that worktree. A lead entry
    with no kept file (started before it existed) fails a plain or
    startup `revive`; only `revive --name <lead>`, the human's, adopts it
    from its ledger entry. A sandboxed lead can't run that adoption, since
    it writes the lead's settings into the config dir. Members' args are
    resumed as recorded.
  - `restart` sends `/clear` to the running Claude, so it writes nothing.
    It checks that the lead's recorded args hold `--settings <its file>`,
    and warns when that file differs from what the herd's current
    switches would write.
- **What it sets.**
  - Sandbox: `enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`.
  - Network: `allowAllUnixSockets` for the herdr socket, and
    `WebFetch(domain:*)` so every host is reachable.
  - Permissions: `denyInsteadOfPrompting`.
  - Writes allowed: the lead's own worktree and loopherd's state dir.
    Claude Code adds the repo's shared `.git` for a linked worktree, so
    the lead can commit. Its members' worktrees and the main checkout stay
    read-only to it.
  - Writes denied: loopherd's whole config dir (herd files, `config.toml`,
    and these settings files) and `~/.claude`. Each deny is both a sandbox
    `denyWrite` entry and an `Edit(//…/**)` rule.
  - Run outside the sandbox, with a `Bash(…)` allow rule so it isn't
    denied for want of a prompt: `loopherd watch` (D104), and with
    `install = true`, `scripts/install`.
    `feed`, `add`, `prompt`, `restart` (`--self` included), `retire` and
    `release` run in the lead's broker (D98), in any form. `install =
    true` also allows writes to `~/.local/bin`. Claude Code matches an
    excluded command against the command as the lead wrote it, so only a
    bare call runs outside: a `cd x &&`, pipe, redirect or `$(…)` keeps
    `scripts/install` sandboxed. The skill says to run it bare. A gap in
    Claude Code's parser that matched a compound command would run all of
    it outside.
- **loopherd's worktree git reads only the repo's own config.** Each git
  call loopherd makes to spawn, check, clear or remove a member's worktree
  (in `spawn`, `add`, `feed`, `retire --close` and `release`, and
  `release`'s look-up of origin for open PRs) sets `GIT_COMMON_DIR` to the
  repo's common git dir. It finds that dir by walking up to `.git`, not by
  asking git. A worktree's `.git` file, an admin dir's `commondir`, or a
  `commondir` planted in the shared `.git`, all of which a lead can write,
  can't then point git at a config (`core.fsmonitor`, `core.sshCommand`,
  hooks) the lead wrote. The repo's own `config` and `hooks/` are
  write-denied. A repo with `extensions.worktreeConfig` on (sparse
  checkout turns it on) reads `config.worktree` files the lead can
  write, so loopherd refuses to run git while any of the repo's sets
  anything but sparse checkout's keys (D101). The repo is made absolute
  before it's pinned, since git reads a relative `GIT_COMMON_DIR` from
  its `-C` dir. The pin reaches hooks too, so a hook that runs git in
  another repo must unset `GIT_COMMON_DIR`. The
  branch look-up in `status`, `view` and the PR-link popup runs the
  pinned, guarded git too, checking each repo's `config.worktree` files
  once per read; a refused repo shows `-` for its members' branches and
  one warning. The PR look-up only reads and stays unpinned.
- **Ledger entries are checked before git runs on them.** `retire
  --close`, `feed`'s retire step and `release` act on an entry's repo and
  worktree, which the ledger names and a lead can write.
  - A lead running loopherd, known by an ancestor Claude started with its
    settings file (a command line it can't change), may act only on its
    own herd's members. Anything else is refused before it's retired or
    its tab closed.
  - A herd's member must match its herd file: its repo the herd's, and
    neither its worktree nor the one its branch would get may be another
    lead's. When loopherd sees a lead calling it, the member's worktree
    must also sit beside the herd's worktrees. With no lead caller seen (the human,
    the shepherd, or a hook-only lead on `prefer`) it needn't, since
    `ensure_worktree` reuses a branch's worktree wherever it is (D101).
  - An entry with no herd (a hand-spawned one) has no herd file to
    match, nor, with no lead caller seen, does one whose herd file is
    gone. It's refused only when its repo sits in a lead's worktree or
    the state dir, or it names a lead's worktree; see below for what that
    leaves open.
  - `retire` keeps a worktree that fails; `release` refuses. A lead may
    not pass `release --drop-branch`, which deletes commits; its broker
    refuses it.
  - `spawn --worktree` stays inside the sandbox, so it fails for a lead;
    it's the human's, and a lead hand-spawns with `add`.
- **`[lead] sandbox`.** `require` (the default) or `prefer`.
  - `lead` and `revive` probe the machine first. Claude Code must be
    2.1.319 or later (older prompts where these settings deny, and lets a
    repo's settings loosen the sandbox). On macOS the sandbox is built in.
    On Linux and WSL2, `bwrap` and `socat` must be on PATH and `bwrap`
    must make a sandbox (this catches WSL1 and blocked user namespaces).
    Anything else can't run it. Each failure names its fix.
  - `require` refuses with the reason: `lead` fails, `revive` reports
    `failed <lead>: sandbox: …`, and `restart` refuses a lead whose
    recorded args lack its settings.
  - `prefer` starts or keeps the lead without the sandbox, guarded by its
    tool hook alone, with a warning. Since D83 that hook reads only plain
    forms, so such a lead's herd files, config and switches are protected
    against plain forms only. `lead`, `revive` and `restart` record
    why on the lead's ledger entry (`unsandboxed`), which `view` shows as
    `(lead, unsandboxed)`. `lead` also leaves the warning as a note in the
    lead's mailbox. The flag is advisory: it sits in the ledger, which the
    lead can write, so a lead can clear it. Doctor's check of the lead's
    recorded args reads the same ledger.
- **Doctor** runs the same probe. It fails when the sandbox can't start
  and some herd has a lead, and only warns while none does. It warns for
  each herd on `prefer`, and for each running lead without its sandbox
  (flagged, or started before it), naming `loopherd revive --name` to
  resume it in one.
- **Credentials stay readable.** `merge = true` and `hook` leads use the
  human's gh credentials. The deny on them is LH-281's, for `credentials`
  leads only.

## Why

- **Only the worktree, so nothing that runs outside the sandbox is
  writable.** Claude Code protects `.claude`, `.mcp.json` and the like
  only in the working directory and above it. A sibling worktree's or the
  main checkout's settings, hooks or `.git/hooks` would run with full
  access in another session. A lead's `feed`, `add` and `retire --close`
  make and remove its members' worktrees, `release` clears one for
  re-feeding, and `feed` runs `after_merge` in the main checkout, so those
  run outside the sandbox instead, in the lead's broker (D98). They take
  repos and commands from herd files the lead can't write, and check
  every herd member's ledger path against them before running git there.
- **One deny covers the config dir.** Herd files, `config.toml`, the
  settings files and the kept lead records all sit in it, so one deny
  covers them. `revive` builds a lead's sandbox only from them, so a lead
  can't loosen its own sandbox by editing its existing ledger entry. The
  kept record protects only that entry: a forged entry under another
  name is the state dir's problem, below. It's also why
  `restart` writes nothing: its `--self` waiter runs on the lead's behalf.
- **The sandbox ends every process a command leaves behind.** A detached
  `setsid` child of a sandboxed Bash call didn't outlive the call (tried
  live), so `restart --self`'s waiter has to run outside the sandbox; the
  lead's broker starts it (D98), from `loopherd` on `PATH` once a
  reinstall has replaced its binary. That needs a `loopherd` the lead
  can't replace, which holds while `install` is off.
- **`install = true` is a trust grant, not a contained path.** The sandbox
  protects most of `~/.claude`, whatever `allowWrite` says, and the
  installer writes hooks, the skill and agents there, so it runs outside
  the sandbox. A lead with `install` on can edit `scripts/install` in its
  worktree before running it, and can replace `~/.local/bin/loopherd`,
  which hooks run outside the sandbox. Either way, `install = true` lets
  the lead write anything the human can. Turn it on only for a lead
  trusted with that.
- **Unix sockets can't be narrowed on Linux.** Claude Code ignores
  `allowUnixSockets` on Linux and WSL2, so a lead's Bash can reach any
  socket the human can, an ssh agent included.
- **The network stays open.** D83 left merges to credentials, and leads
  reach GitHub, their tracker, and whatever their members' builds need.
  On macOS, git over an SSH remote fails inside the sandbox, so a lead
  there needs an HTTPS remote.
- **Restart can't relaunch.** A lead started before its sandbox, or on
  `prefer`, stays unsandboxed until `revive` or a fresh `lead`. So under
  `require`, `restart` refuses instead of passing it as sandboxed. A
  switch changed since the lead started reaches its sandbox at the next
  `revive`.

## What the sandbox doesn't stop

It keeps a lead from writing outside its worktree and the state dir by
accident or on a whim. It does not contain a lead set on getting out:

- **The herdr socket and WSL2 interop**, closed by D105: a lead gets no
  Unix sockets unless its herd sets `[lead] unix_sockets = "all"`, which
  reopens both, and the human's ssh agent. Members run unsandboxed
  (LH-284), so a lead can have one do what its sandbox refuses.
- **The human's own settings.** Claude Code merges `~/.claude/settings.json`
  into the lead's sandbox, so an `excludedCommands` or `allowWrite` there
  loosens every lead's. D100 detects these: `require` refuses the lead,
  `prefer` warns. The commands the human's settings name still run
  outside the sandbox in every lead: hooks, `statusLine.command`,
  `apiKeyHelper`, `awsCredentialExport`, `awsAuthRefresh`,
  `gcpAuthRefresh`, `otelHeadersHelper`, a `"command"` `fileSuggestion`,
  and the `headersHelper` of a marketplace source in
  `extraKnownMarketplaces`. Plugins that `enabledPlugins` turns on can
  bring hooks, which run outside it too, and MCP servers (below). All of
  these are the human's, and D100 doesn't refuse a lead over them. Claude
  Code adds keys like these over time, so its settings reference is the
  full list.
  - A lead can't add one or choose what it runs, though its tool calls
    fire the human's hooks with input it picks. It can trigger a
    marketplace's `headersHelper` at will: starting `claude` runs it, as
    Claude Code fetches each declared marketplace at startup (tried with
    2.1.331 outside a sandbox: `claude -p` ran it even when not logged
    in; `claude plugin marketplace update` and `add` didn't). Started from
    the lead's Bash, that Claude and its helper run inside the lead's
    sandbox, so the lead gains nothing its sandbox refuses. Untried from
    inside a lead's sandbox.
- **The repo's committed settings.** These keys may sit in any settings
  file, and Claude Code merges the worktree's `.claude/settings.json` into
  the lead too, so a repo's checked-in hooks and helpers run outside every
  lead's sandbox. D100 reads that file only for the permission keys that
  steer the file tools, not for these. A repo's `extraKnownMarketplaces`
  is the exception: Claude Code uses it only once the worktree folder
  itself is trusted, which is unchecked for a lead's. The lead can't edit
  its own worktree's `.claude`, which Claude Code protects in the working
  directory, but others can put commands there:
  - A new lead worktree is checked out from origin's default branch, so
    whatever reaches it (a member's PR, a lead's merge under
    `merge = true`) reaches the next lead created.
  - Members run unsandboxed, so a lead can have one write its kept
    worktree's `.claude/settings.json` directly, and `revive` resumes the
    lead there with the new hooks.
- **MCP servers.** The sandbox covers Bash only, so an MCP server is a way
  out. D100 starts leads with none but those `[lead] mcp_servers` names,
  which run unsandboxed. That a plugin's MCP servers are dropped too rests
  on the CLI reference, which says `--strict-mcp-config` skips servers
  configured "in places such as `.mcp.json`, `~/.claude.json`, or a
  plugin"; no plugin with one was installed to try (D100's Why).
  Launching leads without the human's user settings at all
  (`--setting-sources`, with loopherd's hooks moved into the lead's own
  settings file) is the stronger option if D100's detection proves
  leaky.
- **The state dir.** A lead can write it all: the ledger, mailboxes,
  `paused/` and `shepherd.json`. It can forge a worker entry, its own
  session under a new name included, that `revive` resumes unsandboxed
  with whatever args the entry names.
- **The repo's shared `.git`.** Claude Code opens it so a linked worktree
  can commit, with `hooks/` and `config` denied. The rest stays writable,
  so a lead can plant a `commondir` that points git at a config it wrote.
  loopherd's worktree git ignores it (above), but git anyone else runs in
  the repo or its worktrees follows it and can run a command the lead chose,
  outside the sandbox: the human's own git, git in the herd's `source`,
  done checks and `after_merge`, and tools like gh that call git.
- **Hand-spawned entries.** A lead can rewrite a herd-less entry to name
  a repo it built somewhere it can write but loopherd doesn't check: its
  sandbox's temp dir, a dir inside the shared `.git`, or `~/.local/bin`
  with `install = true`. When the human then runs `retire --close` or
  `release` on that entry, git runs there, pinned to the lead's own
  config, and its commands run outside the sandbox. Check a hand-spawned
  entry's `repo` in the ledger before closing it.
- **Clean worktrees of its repo.** A forged entry in the lead's own herd
  can still have the lead's `retire --close` or `release` remove any
  clean worktree in the herd's worktrees dir that isn't a lead's, the
  human's own included, and delete its branch when it looks merged. When
  loopherd sees no lead calling it (the human, the shepherd, or a
  hook-only lead on `prefer`), the entry's worktree isn't held to that
  dir (D101), so it can name any clean worktree of the herd's repo that
  isn't a lead's. A lead can write `refs/` in the shared `.git`, so it
  can make a branch look merged; it could already delete branches
  itself.
- **`install = true`**, as above.
