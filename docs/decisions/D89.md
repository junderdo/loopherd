# D89

## Decision

Each lead's Claude runs in the Claude Code sandbox, as D83 decided, from a
settings file loopherd writes for it (LH-280).

- **The file.** `<config dir>/sandbox/<lead>.json`, passed as `claude
  --settings <file>`.
  - `lead` writes the file before starting the lead, and beside it
    `<lead>.lead.json`: the lead's herd and its Claude args without the
    settings. A lead given its own `--settings` is refused, since that
    flag is its sandbox's.
  - `revive` trusts `<lead>.lead.json` over the ledger, which the lead can
    write. Whether an entry is a lead, its herd, its args, and its
    worktree (where `lead` puts it in the herd's repo) all come from that
    file and the herd file. It rewrites the settings from the herd's
    current switches and resumes the lead in that worktree. Only a lead
    started before the file existed falls back to its ledger entry, once.
    Members' args are resumed as recorded.
  - `restart` sends `/clear` to the running Claude, so it writes nothing.
    It checks that the lead's recorded args hold `--settings <its file>`,
    and warns when that file differs from what the herd's current
    switches would write.
- **What it sets.**
  - Sandbox: `enabled`, `failIfUnavailable`, `allowUnsandboxedCommands: false`.
  - Network: `allowAllUnixSockets` for the herdr socket, and
    `WebFetch(domain:*)` so every host is reachable.
  - Permissions: `denyInsteadOfPrompting`.
  - Writes allowed: the lead's own worktree and loopherd's state dir.
    Claude Code adds the repo's shared `.git` for a linked worktree, so
    the lead can commit. Its members' worktrees and the main checkout stay
    read-only to it.
  - Writes denied: loopherd's whole config dir (herd files, `config.toml`,
    and these settings files) and `~/.claude`. Each deny is both a sandbox
    `denyWrite` entry and an `Edit(//…/**)` rule.
  - Run outside the sandbox, each with a `Bash(…)` allow rule so it isn't
    denied for want of a prompt: `loopherd restart --self`, `loopherd
    feed`, `loopherd add` and `loopherd retire` always, and with `install
    = true`, `scripts/install`. `install = true` also allows writes to
    `~/.local/bin`.
- **`[lead] sandbox`.** `require` (the default) or `prefer`.
  - `lead` and `revive` probe the machine first. Claude Code must be
    2.1.319 or later (older prompts where these settings deny, and lets a
    repo's settings loosen the sandbox). On macOS the sandbox is built in.
    On Linux and WSL2, `bwrap` and `socat` must be on PATH and `bwrap`
    must make a sandbox (this catches WSL1 and blocked user namespaces).
    Anything else can't run it. Each failure names its fix.
  - `require` refuses with the reason: `lead` fails, `revive` reports
    `failed <lead>: sandbox: …`, and `restart` refuses a lead whose
    recorded args lack its settings.
  - `prefer` starts or keeps the lead without the sandbox, guarded by its
    tool hook alone, with a warning. `lead`, `revive` and `restart` record
    why on the lead's ledger entry (`unsandboxed`), which `view` shows as
    `(lead, unsandboxed)`. `lead` also leaves the warning as a note in the
    lead's mailbox.
- **Doctor** runs the same probe. It fails when the sandbox can't start
  and some herd has a lead, and only warns while none does. It warns for
  each herd on `prefer`, and for each running lead without its sandbox
  (flagged, or started before it), naming `loopherd revive --name` to
  resume it in one.
- **Credentials stay readable.** `merge = true` and `hook` leads use the
  human's gh credentials. The deny on them is LH-281's, for `credentials`
  leads only.

## Why

- **Only the worktree, so nothing that runs outside the sandbox is
  writable.** Claude Code protects `.claude`, `.mcp.json` and the like
  only in the working directory and above it. A sibling worktree's or the
  main checkout's settings, hooks or `.git/hooks` would run with full
  access in another session. A lead's `feed`, `add` and `retire --close`
  make and remove its members' worktrees, and `feed` runs `after_merge` in
  the main checkout, so those run outside the sandbox instead. They are
  loopherd's own commands, reading herd files the lead can't write.
- **One deny covers the config dir.** Herd files, `config.toml`, the
  settings files and the kept lead records all sit in it, so one deny
  covers them. `revive` builds a lead's sandbox only from them, so a lead
  can't loosen its own sandbox by editing its ledger entry. It's also why
  `restart` writes nothing: its `--self` waiter runs on the lead's behalf.
- **The sandbox ends every process a command leaves behind.** A detached
  `setsid` child of a sandboxed Bash call didn't outlive the call (tried
  live), so `restart --self`'s waiter has to run outside the sandbox. That
  needs a `loopherd` the lead can't replace, which holds while `install`
  is off.
- **`install = true` is a trust grant, not a contained path.** The sandbox
  protects most of `~/.claude`, whatever `allowWrite` says, and the
  installer writes hooks, the skill and agents there, so it runs outside
  the sandbox. A lead with `install` on can edit `scripts/install` in its
  worktree before running it, and can replace `~/.local/bin/loopherd`,
  which hooks run outside the sandbox. Either way, `install = true` lets
  the lead write anything the human can. Turn it on only for a lead
  trusted with that.
- **Unix sockets can't be narrowed on Linux.** Claude Code ignores
  `allowUnixSockets` on Linux and WSL2, so a lead's Bash can reach any
  socket the human can, an ssh agent included.
- **The network stays open.** D83 left merges to credentials, and leads
  reach GitHub, their tracker, and whatever their members' builds need.
  On macOS, git over an SSH remote fails inside the sandbox, so a lead
  there needs an HTTPS remote.
- **Restart can't relaunch.** A lead started before its sandbox, or on
  `prefer`, stays unsandboxed until `revive` or a fresh `lead`. So under
  `require`, `restart` refuses instead of passing it as sandboxed. A
  switch changed since the lead started reaches its sandbox at the next
  `revive`.

## What the sandbox doesn't stop

It keeps a lead from writing outside its worktree and the state dir by
accident or on a whim. It does not contain a lead set on getting out:

- **The herdr socket.** A lead needs it, so its Bash can ask herdr to
  start a process in any pane (`herdr agent start`), outside the sandbox,
  or send prompts and keys to the shepherd and members. Members run
  unsandboxed (LH-284), so a lead can have one do what its sandbox
  refuses.
- **WSL2 interop.** The setting that opens Unix sockets also opens WSL2's
  Windows interop socket, so a Windows binary (`wsl.exe -e …`) runs
  outside bubblewrap.
- **The human's own settings.** Claude Code merges `~/.claude/settings.json`
  into the lead's sandbox, so an `excludedCommands` or `allowWrite` there
  loosens every lead's.
- **The state dir.** A lead can write it all: the ledger, mailboxes,
  `paused/` and `shepherd.json`, and forge an entry for a member that
  `revive` resumes unsandboxed.
- **`install = true`**, as above.
