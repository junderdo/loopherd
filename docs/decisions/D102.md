# D102

## Decision

Amends D97 and D98 (LH-320).

- **A lead's file tools are denied what is in `<state dir>/broker/`
  except its own `requests/`, each path named.** That is every other
  lead's folder, and anything in its own folder beside `requests/`, as
  they stand when its settings are written. The blanket
  `Edit(//<state>/broker/**)` is gone. The broker's replies and lock live
  in the config dir, which stays denied whole.
- **`lead`, `revive` and `restart` make `reports/`, `handoffs/` and
  `broker/<lead>/requests/` before they start or `/clear` a sandboxed
  lead's Claude**, refusing with the path they couldn't make.
- **`restart`'s stale-settings warning ignores the broker denies**: they
  change when another lead starts, not with the herd's switches.

## Why

- **An `Edit` deny is also a sandbox write deny, and a deny beats
  `allowWrite`.** Claude Code turns the file tools' `Edit` denies into
  sandbox write denies, so the blanket deny made the lead's own
  `requests/` read-only. Every feed, tell, restart and prompt a lead
  handed its broker failed with `Read-only file system (os error 30)`.
  The live sandboxed-lead test now sends `prompt` and `feed --dry-run`
  through the broker. It goes red with the blanket deny.
- **Globs can't do the carve-out.** Probed on Claude Code 2.1.329: the
  Linux sandbox skips glob write denies, so they protect nothing there.
  The file tools match `[!x]` and `[^x]` as plain character sets (no
  negation), so "every name but this one" can't be written as a glob.
  Literal paths behave the same in both layers.
- **The lead's Bash needs none of these denies.** Its sandbox writes only
  what `allowWrite` names, and that holds only its own `requests/`. The
  denies cover the file tools, which run outside the sandbox.

## Still open

- **A lead started later isn't covered** for an earlier lead's file
  tools until that lead's Claude starts again (`revive`). Its Bash still
  can't write there.
