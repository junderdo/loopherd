# D102

## Decision

Amends D97 and D98 (LH-320).

- **A lead's sandbox no longer denies its own `broker/<lead>/requests/`.**
  The blanket `Edit(//<state>/broker/**)` is gone. In its place:
  - On Linux, `Edit(//<state>/broker/*)`, a glob: it denies the file tools
    all of `broker/`, the lead's own folder and folders made later
    included. The Linux sandbox skips glob denies, so Bash keeps its
    `allowWrite` to `requests/`.
  - Off Linux (on every platform before D125), a literal deny on each
    entry of `broker/` but the lead's own, and each entry of its own
    folder but `requests/`, as they stand when its settings are written.
  - The broker's replies and lock live in the config dir, which stays
    denied whole.
- **`lead` and `revive` make `broker/lead-<herd>` for every herd file**
  before writing a lead's settings, each with mode 0700 whatever the
  umask, as the broker makes its own. A herd whose lead hasn't started
  yet then already has a folder that a literal deny names.
- **`lead`, `revive` and `restart` make `reports/`, `handoffs/` and
  `broker/<lead>/requests/` before they start or `/clear` a sandboxed
  lead's Claude**, refusing with the path they couldn't make. An existing
  shepherd's watch file is left as it is, so a read-only sandbox
  placeholder for it doesn't stop them.
- **`restart`'s stale-settings warning ignores the literal broker
  denies**, which change as leads and herds come and go. It still
  compares the globs, so a lead started with the blanket deny is told to
  revive.

## Why

- **An `Edit` deny is also a sandbox write deny, and a deny beats
  `allowWrite`.** Claude Code turns the file tools' `Edit` denies into
  sandbox write denies, so the blanket deny made the lead's own
  `requests/` read-only. Every feed, tell, restart and prompt a lead
  handed its broker failed with `Read-only file system (os error 30)`.
- **Probed on Claude Code 2.1.329:**
  - The Linux sandbox skips glob write denies.
  - The file tools honor `broker/*` for everything beneath it.
  - The file tools match `[!x]` and `[^x]` as plain character sets, so
    no glob can mean "every name but this one".
- **The lead's Bash needs none of these denies.** Its sandbox writes only
  what `allowWrite` names, which holds only the lead's own `requests/`.
  The denies are for the file tools, which run outside the sandbox.
- **The live sandboxed-lead test checks both layers.**
  - Bash: the lead sends `prompt` and `feed --dry-run` through its broker.
  - File tools: with the state dir opened to them by an allow rule, the
    lead's Write tool is still refused another lead's requests folder,
    one made before the lead started and one made after.
  - It goes red with the blanket deny, and red without the glob.

## Still open

- **macOS** sandboxes apply globs, so a lead there gets only the literal
  denies. Its file tools can write the folder of a lead whose herd file
  was added after the lead's settings were written, until the lead's
  Claude starts again (`revive`). Its Bash still can't. Not run on macOS.
- **Whether Seatbelt honours a `broker/*` glob**, as the bullet above
  assumes, and so whether macOS could take it. Needs a macOS host; until
  then the unit tests assert no `broker/` glob off Linux.
