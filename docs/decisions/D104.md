# D104

## Decision

A lead's `loopherd watch` runs outside its sandbox. Amends D89, D95 and D98.

- **Excluded as `loopherd watch`.** The lead's sandbox settings list
  `loopherd watch` and `loopherd watch *` in `excludedCommands`, with a
  matching `Bash(…)` allow rule, as D89 does for `scripts/install`. A call
  holding any command that doesn't match (`cd x &&`, a redirect, `$(…)`),
  or a path to the binary, stays sandboxed and behaves as before. Claude
  Code strips wrappers such as `timeout`, `nice` and `nohup` before
  matching, so `timeout 3600 loopherd watch` likely runs outside too; the
  rules below hold for every form that does.
- **Only the lead's own watch.** Run outside the sandbox, the watch sees
  the lead's Claude among its ancestors (D89's `calling_lead`). It then
  refuses, naming why, to be anything but that lead's watch: a pane the
  ledger doesn't give that lead (which would make it the shepherd's
  watch, a stale socket's case included) and a pane holding another lead.
  Naming another herd was already refused. An ancestor running a lead's
  settings from another config dir (a `<name>.lead.json` beside it) is
  refused too, rather than read as no lead. `--timeout` only bounds the
  wait, and the lead's watch refuses `--settings`, which would read any
  file outside the sandbox; it checks Claude's own settings.
- **As the lead, not the human.** The lead's watch runs its herd's
  `merged`, `done`, `source` and `backlog` checks and its merge lookups,
  which now run outside the sandbox too. So, as its broker does (D98), it
  first takes on the lead's narrowed credentials when its herd guards
  merges by credentials, and won't start while they're missing. It does
  so whenever the watch resolves to a lead's, found by its Claude or by
  its pane. D95's "the lead's watch runs the checks sandboxed" becomes
  "with the lead's narrowed credentials".
- **The watch calls herdr itself.** Polls, notifications and pane labels
  go straight to herdr, not through the lead's broker. This is a stated
  exception to D98's "a lead's pane makes no herdr calls". The watch is
  loopherd's own code, read-only toward herdr but for its notifications
  and labels, and its reach rule above bounds it to its own herd. Routing
  it through the broker would also queue it behind the broker's one
  request at a time (LH-311). LH-301's routing of `status` and `read`
  no longer covers the watch.

## Why

On Linux, Claude Code's sandbox puts an empty read-only placeholder at
each denied path that doesn't exist, `<repo>/.git/config.lock` among them,
for the life of every sandboxed command, and defers cleanup while any
other sandboxed command in that Claude still runs. A lead keeps `loopherd
watch --timeout 3600` running, so for up to an hour every `git config`
write in the repo failed with `could not lock config file …: File exists`,
the human's worktrees included (`git push -u`, `git branch
--set-upstream-to`). No Claude Code setting exempts one path; upstream
[claude-code#78818](https://github.com/anthropics/claude-code/issues/78818)
is open.

The watch is the lead's one long-lived command, so taking it out of the
sandbox removes the hour-long window. What it runs comes from files the
lead can't write: its herd's checks from the herd file and its
notifications from `config.toml`. It writes its own lock, fired file and
mailbox marks in the state dir.

## What remains

- **Sandboxed builds still hold the placeholder.** A lead's reviewer
  subagents build and test in the sandbox, so for minutes at a time
  `git config` writes in the repo can still fail. Accepted; LH-323
  rechecks once upstream ships a fix.
- **A watch run in another form** stays sandboxed and holds the
  placeholder for its whole run, as before. The skill tells leads to run
  it bare.
- **The checks' git follows the shared `.git`.** D89's planted
  `commondir` already reached the checks the broker's `feed` runs. Now it
  also reaches the watch's `merged` and `backlog` checks and its merge
  lookups, which run every 60s while the lead keeps a watch going. Under
  `credentials` they run with the lead's narrowed credentials; under
  `hook`, with the human's.
- **Matching is Claude Code's.** The exclusion holds only while Claude
  Code matches `loopherd watch *` against the command as written. A form
  that set `LOOPHERD_CONFIG_DIR` before the call and still ran outside
  would hide the lead's settings file from `calling_lead`, and the watch
  would read herd files and `[notify]` commands from where the lead
  pointed it. The allow rule doesn't match past such an assignment, so
  `denyInsteadOfPrompting` denies it. Claude Code's sandboxing docs warn
  that "an excluded command runs with your full access."
- **The shell picks the `loopherd`.** The exclusion matches the text
  `loopherd watch`, so the shell runs the first `loopherd` on PATH. An
  empty or relative PATH entry, or one inside the lead's worktree or the
  state dir, would let the lead plant its own, so `lead` and `revive`
  refuse to start one under such a PATH, before writing any of the
  lead's files. The check reads the PATH `lead` runs with, which is not
  the PATH the lead's Claude gets. Its pane is a herdr tab whose shell
  inherits the herdr server's environment and then runs the human's
  shell rc, and loopherd sees neither before it starts Claude there; a
  PATH entry either adds goes unchecked. The check also misses dirs the
  human's own settings add to `allowWrite`, which `sandbox = "prefer"`
  only warns about, and `restart` doesn't repeat it.
  With `install = true` the lead can write `~/.local/bin`, but it can
  already run `scripts/install` outside the sandbox.
- **Herd names are checked before use.** The watch validates each herd
  it's given as a name before looking for its herd file, so a path can't
  probe for files outside the sandbox.
