# D141

## Decision

Amends D114 and D121 (LH-399). A credentials member's confinement also
covers the GitHub tokens that live outside D114's fixed list:

- **More of the human's files are denied** to the sandbox and the file tools:
  `~/.claude.json` (user-scope MCP servers, a GitHub PAT among them),
  `~/.docker/config.json` (ghcr.io), `~/.npmrc` (npm.pkg.github.com) and
  `~/.config/github-copilot/`, each also where `CLAUDE_CONFIG_DIR`,
  `DOCKER_CONFIG`, `NPM_CONFIG_USERCONFIG` and `XDG_CONFIG_HOME` move it.
  So is every file a `credential.helper = store --file <path>` names in the
  human's git config, read when the settings are built.
- **More token variables are blanked**: `GITHUB_PERSONAL_ACCESS_TOKEN`,
  `GITHUB_PAT`, `GH_PAT`, `GITHUB_API_TOKEN` and `HOMEBREW_GITHUB_API_TOKEN`,
  beside D114's three.
- **The file tools can't read `/proc/*/environ`** or
  `/proc/*/task/*/environ`. A process's starting environment keeps the
  tokens its settings' `env` blanks afterwards.
- **A GUID-tagged virtiofs share is a Windows drive.** With
  `virtioFsAggregateShares = false`, WSL mounts each drive as its own share
  tagged with a GUID, which D114's `drvfs`/`drvfsa` tags missed.
- **A Windows drive whose mount point isn't UTF-8 refuses the member**,
  since the settings file can't name it to deny it.
- **What the machine holds arrives through one seam.** `/proc/mounts`, the
  environment and the git credential helpers reach `credentials::confined`
  as a `Machine`, so lead and worker settings read them the same way and a
  unit test pins that a mounted drive lands in both `denyRead` and
  `Read(//<drive>/**)`.

## Why

- **The same hole, at other paths.** Each of these files and variables holds
  a token that authenticates as the human, so leaving it readable undoes the
  credentials guard as surely as `~/.config/gh` would.
- **Not `Read(//proc/**)`.** Claude Code's sandboxing docs merge permission
  rules' paths into the sandbox's, so a deny on all of `/proc` risks hiding
  it from the lead's shell, where loopherd reads `/proc/self/exe` (D119) and
  `/proc/locks` (D109). The `environ` rules have a glob mid-path, which the
  Linux sandbox skips (as with the lead's `broker/*` deny), so they reach
  the file tools alone.
- **Refuse, don't skip, an unnameable drive**, as D114 refuses a lead whose
  `/proc/mounts` can't be read.

## Limits

- **The sandboxed shell and `/proc`.** Whether a sandboxed command can read
  the Claude process's `/proc/<pid>/environ` depends on bubblewrap's PID
  namespace, which this decision doesn't verify. Its tokens are the human's
  only while the pane that started Claude had them in its environment.
- **Helpers other than `store`**, and a `store --file` given a relative
  path, aren't followed. The member's git runs with `credential.helper`
  cleared (D95), so only a direct read of such a helper's file is open.
- **Other tools' token files** past those named here still reach a member,
  as other non-GitHub secrets do (D114).
- **The live probe uses `ssh -F`** with loopherd's ssh config, so it shows the
  carved key reaches GitHub, not that the human's `~/.ssh/config` `Include`
  resolves inside the sandbox. A live test can't fake `~/.ssh/config`
  without moving the home Claude logs in from.
