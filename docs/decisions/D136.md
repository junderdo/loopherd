# D136

## Decision

A token count in `loopherd setup`, `setup --context`, `loopherd config
set` and `init --context-limit` is a whole number with optional decimals
and a `k` (×1,000) or `m` (×1,000,000) suffix in either case: `250000`,
`250k`, `1.5M`. `_` or `,` may separate groups of three digits
(`1,000,000`); anywhere else they're refused, so `1,5M` isn't read as 15M.
A form that isn't a whole number of tokens (`1.5`, `1.2345k`) is refused,
naming the accepted forms. Setup and `config set` write tokens as plain
integers; a limit in a file may also be a string in any of these forms.

A limit (`default_context_limit`, `[shepherd] context_limit`, a herd's
`context_limit`) may instead be a whole percentage, 1% to 100%, of the
effective `context_window`, stored as a string (`"65%"`). It is resolved
wherever the limit is computed, so it follows a later window change; the
80%-of-window cap still applies to the result, so 81% to 100% is accepted
in files and `config set` but runs at 80%; setup refuses it as over the
cap, as it does an over-cap token count. `context_window` itself is tokens
only. A percentage never resolves under the 10000-token minimum: a small
one at a small window (1% of 200k) runs at 10000, as the floor is applied
to the resolved value, which follows the window.

Setup echoes each answer's value (`= 250,000 tokens`, or `= 650,000 tokens
(65% of 1,000,000)`). While a limit is unset, its question shows the
current effective limit as the whole percentage of the window under it
(`[80%]` at the default 200k window); Enter still writes nothing, as D39
has it. In `--context`, a comma not followed by `name=` belongs to the value
before it, so `window=1,000,000` works.

## Why

New users typed `250000` wrong and think in `250k` and `1M`, and a raw
token limit stops fitting when the model's window changes. Keeping Enter
write-free leaves D39's contract intact; showing the percentage still
offers that form as the default to type.
